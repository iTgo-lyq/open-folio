# 发布 PR

仅在用户明确要求正式版本时执行。读取 integrationBranch / releaseBranch 和项目版本约定，固定发布目标基线与候选提交，核对实际 diff、已集成 Change、关联 PR 和验证记录。默认以集成分支提交 PR；需要冻结候选时才建短期发布准备分支。

操作发布 PR/MR 时，先执行[合并方式检查](integration.md#合并方式检查)。

版本或范围尚未明确时，按项目约定提出有依据的候选。创建或更新同一发布 PR，正文集中说明：

- 版本号及本次发布范围。
- 面向使用者的功能、修复和必要升级影响，省略空分类。
- 实际包含的 Change / PR，以及验证结果与已知限制。

提交标题仅作线索，不代替内容整理。候选改变时更新说明和验证；实质修复先经 Change 集成。正文不要求 SpecTrail 标记。CI 按固定源目标差异确定新增归档，并逐项核实其关闭、项目集成和归档只读约束；无新增归档的维护发布同样允许。

版本沿用项目约定，在已有项目版本文件或 Git tag 中维护，不额外创建 CHANGELOG.md、GitHub Release 或版本清单副本。工作台读取对应发布提交中的常见静态版本文件，无文件版本时接受精确指向该提交的版本 tag；缺失或冲突不猜测。

准备 PR 不等于授权合并。清单内 Change 须已归档并完成项目集成；子项可通过原父目标 PR 的 M 已进入项目集成历史核实，已接入的归档 CI 须通过。集成分支中的规划、分支登记记录随发布保留，不因对应 Change 在其他分支实施而剔除。沿用会话授权，以普通 merge 保留历史；核对预期源 SHA。候选推进后重查范围与 CI，合并失败或结果未知先核实，不回退直推。确认实际合并提交已在 releaseBranch 后报告合入；PR、服务部署分别说明，不把规划文档或 PR 合入当作功能上线。

工作台从 `releaseBranch` 当前固定快照中的有效归档判断已合入，不以 PR 清单或 PR 可读性作为前提。沿发布分支第一父链定位归档首次进入发布分支的提交，精确关联该提交的已合并发布 PR；有唯一 PR 和可靠 `mergedAt` 时按其分组。无可核实 PR、时间或历史时仍进入“已归档”的“合入时间未知”，不使用归档时间或提交时间替代。当前发布归档只验证一次，历史追溯不重演历史归档校验；目录日期变化不改变 Change ID。交付前的归档与集成 CI 要求继续适用。
