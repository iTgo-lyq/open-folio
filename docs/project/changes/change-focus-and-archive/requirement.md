# Changes 默认关注本人并分离已发布记录

用户首次进入 Changes 时，默认聚焦自己创建的记录，并通过可见的筛选条件让用户知道列表支持筛选。已经发布、通常无需继续跟进的 Change 自动进入独立的“已归档”页签，减少日常列表干扰。

## 已明确的范围

- 用户首次打开 Changes 时默认筛选“我创建的”，筛选状态清楚可见，用户可以移除条件查看其他创建者。
- 增加“已归档”页签，已确认发布的 Change 自动归入；“已完成”保留待集成、待发布和交付待核实的记录。
- “已归档”仍可查阅详情、材料、合入与发布依据，既有详情链接继续有效。
- 保留“进行中”“已取消”及来源异常入口。列表与看板沿用当前能力，看板仍只用于进行中。

本次是列表体验优化；“已归档”页签按交付结果分类，不新增 SpecTrail 流程状态、不改写已完成归档，也不删除历史记录。

## 默认筛选的需求细化建议

“我”指当前选用 Token 所属的 GitHub 身份，与 Change 首次 Git 提交作者的可识别平台身份对应；OpenFolio 登录名与 GitHub 身份不同，不直接拿登录名或显示名猜测归属。无法可靠归属的历史作者仍可通过既有创建者筛选查看，不能误归到其他用户。

首次默认仅用于没有显式筛选、没有已保存选择的列表入口；已有链接中的筛选和指定 Change 的深链接优先。用户移除“我创建的”或选择其他创建者后保留其选择，返回列表或刷新不自动强加默认条件。具体偏好作用域及身份缺失时的展示方式在技术方案中落实，避免不同账号、Token 或仓库互相覆盖。

显示可移除的“创建者：我”筛选条件，并允许从筛选菜单继续选择其他作者。默认筛选无匹配时，提示“暂无你创建的 Change”并提供清除筛选入口；不能让用户误认为仓库没有任何 Change，也不静默改为全量列表。

## 已归档的判定与交互

使用现有交付状态的“已发布”判定（releaseMerged，包括有效的历史发布补记）自动分类；仅工程文档已完成归档、仅合入 develop 或待发布均不进入此页签。沿用现有发布证据与错误处理，不因单次 PR 查询失败把待核实记录误归档。

已完成与已归档互斥；页签数量、列表过滤、详情前后切换和延续组聚合使用一致的范围判定。进入详情、返回、刷新及浏览器前进后退保留当前范围和筛选；即使某条记录不在当前列表筛选内，指定 id 的详情链接仍可打开。新页签在桌面及窄屏均可访问。

## 验收场景

1. 首次进入列表，清晰显示本人筛选，且匹配当前 GitHub 身份创建的记录；可移除并查看其他记录。
2. 清除或修改创建者条件后，返回、刷新不再次强制恢复默认；显式筛选链接、详情深链接及账号/Token 切换不发生串用。
3. 无本人记录或作者无法可靠识别时，提供明确说明和查看其他创建者的入口，不错误匹配同名作者。
4. 已发布记录仅出现在已归档；待集成、待发布和待核实记录继续出现在已完成；进行中、已取消及来源异常行为保持可用。
5. 新一次成功更新确认发布后，记录自动切换到已归档；详情、历史链接、延续组、筛选和页签数量保持一致。
6. 桌面及窄屏、列表/看板切换、浏览器前进后退和已有筛选回归通过。

## 规模与准备边界

暂按 medium 管理：需要联动默认入口与用户偏好、身份匹配以及交付范围分类，涉及共享查询/偏好契约。当前先准备需求，不修改运行代码；技术方案及计划确认后实施。截图缓存优化不在此次范围中。

## 澄清

Q1：已归档是自动收纳已发布 Change，还是由用户手动归档不再关注的记录？推荐自动收纳已确认发布的 Change。用户选择：“已发布后自动进入已归档（推荐）”。
