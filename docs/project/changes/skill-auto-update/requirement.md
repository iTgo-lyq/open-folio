# SpecTrail skill 自动更新机制

## 背景与目标

SpecTrail 已通过 OpenFolio 的发布分支自动同步到公开分发仓库，但发布新版本与使用方更新已安装的 skill 是两个环节。需要准备自动更新机制，让使用方能够及时获取已发布的 skill，减少手动检查和替换目录的成本。

需求来源：用户提出“先记录一个需求，我们得准备一个 skill 自动更新机制”。最初仅登记需求；现已开始讨论，具体范围与验收尚待确认。

## 初步范围

- 面向已安装的 SpecTrail skill，识别当前使用版本与公开发布版本的差异。
- 提供自动更新能力，并让使用方能够了解更新结果及失败原因。
- 更新时考虑项目配置、本地修改和正在使用的 skill，避免更新造成项目内容丢失或安装不可用。

暂按 medium 估算，依据是版本识别、安装内容更新与触发入口可能需要联动设计；实际边界明确后再复核规模。

## 讨论方向：复用现有脚本提醒更新

用户提出在现有脚本中顺带检查更新，发现新版后通过日志或返回值的追加字段提醒。以下作为候选方向，尚未替代完整需求确认，也未决定首期是否包含自动安装。

现有入口：

- Setup 推荐接入 PR 归档 CI，模板为 `setup/assets/github-pr-archive.yml`，执行 `setup/scripts/check-pr.mjs`；当前输出 JSON，校验失败使用非零退出码。
- 本地提交 hook 调用 `setup/scripts/pre-commit.js`，输出文本日志；当前负责暂存区校验，不 fetch。
- `setup/scripts/check-setup.mjs` 输出接入准备情况的 JSON；`scripts/change.mjs`、`scripts/workspace.mjs` 和 `scripts/integration.mjs` 等日常命令也提供 JSON 结果。
- OpenFolio 的 `.github/workflows/sync-spec-trail.yml` 和 `scripts/sync-spec-trail.sh` 负责向公开仓库发布 skill，属于发布方入口。

建议先复用 PR CI、接入检查与高频状态命令发现更新。文本入口追加简短日志，JSON 入口在原结果旁追加独立的更新提示字段，保持标准输出可直接解析为 JSON；CI 可同时展示 notice。提示属于命令输出，不写入 `change.json` 等项目流程记录。

发现新版或检查更新失败均不改变原校验、状态操作的成败与退出码；检查使用有时限的请求并控制重复频率。本地提交 hook 建议只展示已有检查结果，不在提交时等待联网。具体首批入口及检查频率留待方案明确。

当前发布同步脚本未生成随安装交付的版本标识，版本识别方式仍需设计。仅增加提示入口也不能让尚未包含检查逻辑的旧安装自行获得该能力，首次接入方式仍需明确。

## 待讨论事项

- 首期支持哪些安装位置与运行环境：项目内安装、用户级安装，以及 Codex / Claude Code 等使用入口。
- 如何触发检查与更新：使用 skill 时、显式命令或其他自动触发方式；是否区分自动检查与自动安装。
- 如何标识已安装版本，以及跟随最新发布还是固定版本。
- 遇到本地修改、网络失败、版本不兼容或更新中断时如何处理，是否需要恢复能力。
- 现有安装如何接入新机制，以及是否需要同步关联的 hook 或其他安装资源。

## 验收方向

- 新版本发布后，已接入的安装能够按约定策略发现并完成更新。
- 已是目标版本时不会重复修改安装内容。
- 更新结果和异常可辨识；失败时不损坏原有可用安装或项目配置。
- 本地修改与版本固定行为符合后续确认的策略。

以上为需求草稿，验收细节随需求澄清确定。
