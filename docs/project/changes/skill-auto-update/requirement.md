# SpecTrail 版本标识与更新检查

## 背景与目标

SpecTrail 已通过 OpenFolio 的发布分支自动同步到公开分发仓库，但安装副本尚无统一版本标识，使用方也不会自动获知新版。本次为发布内容增加版本标识，并在项目日常操作中检查和提醒更新。

需求最初以“skill 自动更新机制”登记，讨论后用户明确：“我们只负责检查更新，也要支持关闭检查”，并要求只选择一个高频、能定位项目工作区和读取更新配置的脚本入口。本次不自动下载、替换或安装 skill。

## 范围与行为

### 发布版本标识

- 已发布的 skill 携带可供脚本读取的版本号，安装副本保留该标识；公开分发来源提供最新发布版本供比较。
- 在现有发布同步链路中自动生成、递增版本号。仅在 skill 交付内容实际变化时递增补丁号，例如 `0.1.0 → 0.1.1`；重复运行同一发布或 skill 内容未变化时保持原版本。
- 当前 `.github/workflows/sync-spec-trail.yml` 调用 `scripts/sync-spec-trail.sh` 完成发布，在现有发布链路中接入版本处理，无需另建发布工作流。标识格式与起始版本由技术方案确定。

### 项目内的检查入口

- 只选择一个日常高频脚本承载更新检查，不扩散到所有命令、提交 hook 或 PR 校验入口。
- 唯一入口为 `scripts/change.mjs`：需求澄清、阶段确认、任务开始和完成等操作都会调用它，已有 JSON 输出，并通过当前目录或 `--repo` 确定目标 Git 工作区及读取 `docs/project/workflow.json`。
- 检查使用目标项目工作区的配置，不依赖 skill 安装目录作为当前目录；项目内安装或其他位置的安装均应按实际目标项目读取配置。
- 发现比本地安装版本更新的已发布版本时，在原 JSON 结果外层追加独立更新提示，包含当前版本、最新版本和简短说明，保持原结果结构与标准输出的 JSON 可解析性。提示不写入 `change.json`。

### 关闭检查与异常行为

- 通过现有 `docs/project/workflow.json` 中的可选项目开关关闭更新检查，默认开启；关闭后不发起检查请求，也不展示缓存的更新提醒。配置字段名由技术方案确定。
- 发现新版或更新检查失败均不改变原状态操作的成败、退出码和项目流程记录。请求有等待上限，并短期复用结果以减少重复联网；具体频率与超时留待技术方案确定。
- 已是最新版本时不报告可更新；无法取得或比较版本时如实说明未知，不将网络失败或版本缺失判断成发现新版。
- 检查过程不修改已安装的 skill 或项目业务内容；可重建检查缓存不作为流程事实提交。

## 既有安装

尚未包含检查逻辑的旧安装需要先更新一次，之后才能自动检查。缺少版本标识的安装不能可靠比较版本，首次接入方式需在交付说明中明确；本次不增加自动安装、安装目录替换、备份恢复或固定版本管理。

规模为 medium，涉及发布版本生成、检查提示与项目配置校验的联动。

## 验收标准

- skill 内容变化并发布后，交付物包含新的版本号；同一内容重复发布不递增版本。
- 在已接入的项目中调用选定高频入口，存在新版时能看到当前版本、最新版本及提示，原 JSON 结果仍可解析。
- 从项目子目录执行或显式指定其他项目工作区时，读取实际目标项目的开关；两个项目可以分别开启或关闭。
- 关闭检查后无更新检查请求和更新提醒，原状态操作照常运行。
- 当前版本已是最新时不误报；网络不可用、超时或版本缺失时不影响原状态操作的结果与退出码。
- 其他脚本无需新增更新检查，检查过程不下载安装或替换 skill，不向项目流程记录写入更新信息。
