# 单个 Change 的公开只读分享

## 目标

Change 的发起者需要把需求和推进详情发给评审者或其他协作者，对方不应为了阅读一个 Change 而配置 GitHub Token。目前「复制链接」仅恢复工作台阅读位置，接收者仍须登录并具备仓库读取权限；无需登录的公开链接只支持原型。

用户要求：“加一个分享模式吧，生成单个 Change 的分享链接，让其他人不用配置 Token 就能只读查看详情。”

本次新增单个 Change 的独立分享入口。接收者持链接即可阅读，不要求登录 OpenFolio、配置 Token 或取得仓库权限。用户进一步要求自动跟随 Change 最新内容、包含全部详情，并在编写技术文档或制作原型后由 Agent 主动提供分享链接。

暂按 medium 推进，复用现有 Change 详情、文档、原型与合入差异阅读能力，新增分享存储、访问接口及 Skill 调用支持。技术调查若表明需要大范围重写现有读取或页面，再按实际实现规模调整。

## 范围与行为

有仓库读取权限的用户从 Change 详情创建分享链接，页面明确说明链接持有者可以阅读所分享的内容。原有「复制链接」继续保留原有访问语义，公开分享使用独立入口，避免混淆。

分享页包含指定 Change 当前可展示的全部详情：概览、任务、需求、技术方案、计划、执行与评审记录、澄清问答、阶段确认与关闭依据、图片和图表、原型，以及代码合入记录、文件列表与差异。尚未产生的材料或合入记录按当前工作台语义显示缺失或未就绪，不以扩大分享范围的方式补齐。

页面支持桌面与手机阅读，不提供任务编辑、阶段确认或仓库写入。其他 Change、关联 Specs 及仓库浏览不因这条链接而获得访问权限；正文中的关联引用只能在已分享范围内打开，范围外引用提供明确提示。“全部详情”指该 Change 的完整阅读能力，不包括账号数据、凭据或整个仓库的浏览权限。

分享链接保持稳定，打开、刷新及页面活跃期间的自动检查跟随中心 Git 最新已推送内容，沿用当前工作台的刷新节奏与来源解析规则。规划移交到工作分支、归档和合入后仍定位同一个 Change，不要求重新生成链接；本地未提交或未推送的修改不属于“最新内容”。一次阅读所用的文档、原型与代码差异须对应明确来源，避免把不同版本混为一次交付。

分享者退出当前设备不使分享失效。分享所依赖的 Token 解绑、失效或仓库失权后，服务不得继续依赖该授权交付内容；恢复有效授权后的可用性由明确的分享状态表达。临时网络失败或限流提示同步失败，不冒充已取得最新内容。

分享者可以复制链接、查看分享状态和停止分享。停止后原链接与该分享的正文、图片入口均不可继续读取；重新分享生成新链接，旧链接不会重新开放。管理分享需要验证登录账号及分享归属，不能仅凭公开链接修改或撤回其他人的分享。退出登录不等同于停止分享。

第一版不增加密码、指定收件人、评论、编辑、访问统计或自动过期配置。公开读取不向接收者交付创建者的 Token、Cookie、连接标识或私有工作台数据；分享标识不可根据仓库或 Change 名称推算，也不提供公开枚举入口。

## 服务地址与 Agent 提供链接

复用项目 `docs/project/workflow.json` 顶层已有的 `openfolioUrl`，作为接收者实际可访问的 OpenFolio 服务地址，不新建与其重复的分享域名配置。该字段已获现有校验器支持，当前仓库尚未填写；现有原型设置命令可用 `--configure --openfolio-url <地址>` 写入并保留已有托管选择。`.env` 的 `OPENFOLIO_VERIFY_BASE_URL` 仅供冒烟检查使用，`prototype.hosting.uploadUrl` 是原型上传入口，两者均不能代替分享服务地址。

Skill 在完成并推送技术文档，或完成原型发布与引用登记后，主动提供对应 Change 的可用分享链接，尽可能定位到本次文档或原型。已有分享复用原链接；尚未分享时，使用项目已配置且获授权的访问方式创建，不要求用户每次手动复制。

服务地址与创建分享所需的授权分别配置。授权秘密留在 Git 忽略的本地配置或已有安全凭据存储，不写入 workflow、Change、文档或分享 URL。实现须提供 Agent 可调用的链接获取方式及配置说明，不能只修改 Skill 提示词而让 Agent 猜测接口或伪造 URL。未配置服务、缺少授权或服务不可用时如实说明，并提供可用的仓库文档或已发布原型入口，不把失败当作已分享。

Skill 更新保持精简：主流程说明何时提供链接，具体配置与调用方式放到适当的现有入口或专项参考，不修改需求、技术确认及验收规则。配置了服务地址不等同于授权公开项目内容；本项目本次分享授权沿用当前对话，其他项目遵循各自已有授权。

## 产品取舍

- **Q1（需求：更新方式）**：用户选择“自动跟随 Change 最新内容”，已落实为稳定链接跟随最新已推送的权威来源，不采用固定分享快照。
- **Q2（需求：内容范围）**：用户要求“包含所有内容即可”，包含代码合入差异；同时补充技术文档或原型就绪后主动贴链接，已纳入上述服务地址与 Agent 能力。

## 验收

1. 已登录且有仓库读取权限的用户，可从一个 Change 详情生成并复制独立分享链接；失败时明确提示，不产生半成品页面。
2. 全新浏览器在没有账号会话和 GitHub Token 时，可以阅读同一 Change 的全部详情、文档、图片、原型与代码合入差异；未产生的内容显示明确状态。
3. 推送新文档或更新 Change 后，同一链接在刷新及自动检查后显示新内容；从规划移交、归档到集成的来源变化不使链接失效。未推送内容不出现，不混用不同来源版本。
4. 分享页中的文档、原型及合入文件接口仅使用该 Change 的分享范围；修改 URL、文档标识、提交或资源路径不能读取其他私有记录。现有私有 API 仍执行原有权限检查。
5. 无权限用户不能创建分享；其他账号不能管理该分享。退出分享者当前设备不影响有效分享；停止分享、解绑或确认失权后不能继续通过分享接口读取，重新分享不恢复已撤销的旧链接。
6. 正文含关联文档、外部链接、图片或缺失材料时，仍可安全阅读并获得可理解的状态；不能执行正文内的任意 HTML 或脚本。临时同步失败有明确提示。
7. 桌面与手机可完成复制、打开、阅读和停止分享的闭环；原有阅读链接及原型公开链接的行为保持有效。
8. 在项目配置有效服务地址与创建权限后，Agent 可获取或创建可访问的 Change 分享链接；技术文档推送或原型发布完成后主动给出链接。缺失配置与接口失败不输出伪造或未经确认可用的分享地址，秘密不进入 Git。

## 现状依据

- [个人访问与分享](../../specs/project-knowledge/access/spec.md)规定工程阅读链接不携带可转让权限，原型使用独立公开入口。
- `src/components/changes.tsx` 的详情工具栏使用 `CopyPageLink`；`src/components/document.tsx` 仅复制仓库身份与阅读参数。
- `src/server/repository-api.ts` 与 `src/server/repositories.ts` 将工程读取绑定当前账号、工作台及仓库权限。
- `src/server/public-previews.ts` 已实现原型公开版本持久化；其固定版本读取可供后续方案参考，不能直接代替 Change 文档分享。
- `src/server/personal-sessions.ts` 当前读取入口需要设备会话；自动跟随最新内容且退出设备仍可访问，需要新增基于持久分享授权的读取路径，不能复用用户 Cookie。
- `src/server/schema.ts`、`.agents/skills/spec-trail/prototype/scripts/contract.mjs` 已校验可选 `openfolioUrl`；`.agents/skills/spec-trail/prototype/scripts/setup.mjs` 提供现有写入入口。当前 CLI 尚无 Change 分享接口或对应授权配置。
- 现有 `change-labels-urgency` 处理标签与紧急程度；`frontend-style-interaction-refactor` 处理现有能力的视觉重构。两者均未覆盖本次新增分享授权能力，本次独立建立 Change。
