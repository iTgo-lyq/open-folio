# 单个 Change 的公开只读分享

## 目标

Change 的发起者需要把需求和推进详情发给评审者或其他协作者，对方不应为了阅读一个 Change 而配置 GitHub Token。目前「复制链接」仅恢复工作台阅读位置，接收者仍须登录并具备仓库读取权限；无需登录的公开链接只支持原型。

用户要求：“加一个分享模式吧，生成单个 Change 的分享链接，让其他人不用配置 Token 就能只读查看详情。”

本次新增单个 Change 的独立分享入口。接收者持链接即可阅读，不要求登录 OpenFolio、配置 Token 或取得仓库权限。按 medium 推进，因为需要联动新增分享存储、访问接口与页面，并定义公开内容与私有仓库读取之间的契约。

## 范围与行为

有仓库读取权限的用户从 Change 详情创建分享链接，页面明确说明链接持有者可以阅读所分享的内容。原有「复制链接」继续保留原有访问语义，公开分享使用独立入口，避免混淆。

分享页仅呈现指定 Change 的只读内容，不提供任务编辑、阶段确认或仓库写入。页面支持桌面与手机阅读。其他 Change、关联 Specs 及仓库浏览不因这条链接而获得访问权限；正文中的关联引用只能在已分享范围内打开，范围外引用提供明确提示。

分享者可以复制链接、查看分享状态和停止分享。停止后原链接与该分享的正文、图片入口均不可继续读取；重新分享生成新链接，旧链接不会重新开放。管理分享需要验证登录账号及分享归属，不能仅凭公开链接修改或撤回其他人的分享。退出登录不等同于停止分享。

第一版不增加密码、指定收件人、评论、编辑、访问统计或自动过期配置。公开读取不向接收者交付创建者的 Token、Cookie、连接标识或私有工作台数据；分享标识不可根据仓库或 Change 名称推算，也不提供公开枚举入口。

## 待定的产品取舍

- **Q1（需求：更新方式）**：已询问固定分享时的版本并支持主动更新，还是自动跟随 Change 最新内容。推荐前者，便于围绕同一份内容评审；回答前不确定公开读取的数据来源及刷新语义。
- **Q2（需求：内容范围）**：已询问是否包含代码合入差异。推荐包含概览、任务、需求、技术方案、计划、执行/评审记录、澄清问答和原型，代码合入差异留在原工作台。回答前不确定差异页及代码内容是否纳入公开范围。

## 验收

1. 已登录且有仓库读取权限的用户，可从一个 Change 详情生成并复制独立分享链接；失败时明确提示，不产生半成品页面。
2. 全新浏览器在没有账号会话和 GitHub Token 时，可以打开分享页并阅读已确认范围内的详情、文档与图片，按所选更新方式展示内容。
3. 分享页中的内容、文档切换和原型入口仅使用该 Change 的分享范围；修改 URL、文档标识或资源路径不能读取其他私有记录。现有私有 API 仍执行原有权限检查。
4. 无权限用户不能创建或更新分享；其他账号不能管理该分享。停止分享后旧链接及对应资源不可读取，重新分享不恢复旧链接。
5. 正文含关联文档、外部链接、图片或缺失材料时，仍可安全阅读并获得可理解的状态；不能执行正文内的任意 HTML 或脚本。
6. 桌面与手机可完成复制、打开、阅读和停止分享的闭环；原有阅读链接及原型公开链接的行为保持有效。

## 现状依据

- [个人访问与分享](../../specs/project-knowledge/access/spec.md)规定工程阅读链接不携带可转让权限，原型使用独立公开入口。
- `src/components/changes.tsx` 的详情工具栏使用 `CopyPageLink`；`src/components/document.tsx` 仅复制仓库身份与阅读参数。
- `src/server/repository-api.ts` 与 `src/server/repositories.ts` 将工程读取绑定当前账号、工作台及仓库权限。
- `src/server/public-previews.ts` 已实现原型公开版本持久化；其固定版本读取可供后续方案参考，不能直接代替 Change 文档分享。
- 现有 `change-labels-urgency` 处理标签与紧急程度；`frontend-style-interaction-refactor` 处理现有能力的视觉重构。两者均未覆盖本次新增分享授权能力，本次独立建立 Change。
