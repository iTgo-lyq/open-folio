# 精简技术方案追问并说明实现重点

## 目标与范围

用户以需求和交付结果为中心使用 Agent 开发，希望技术方案也能按依赖关系分轮澄清，同时少问技术细节，并通过问询了解本次实现重点。

现有 SpecTrail 已定义需求分轮澄清、问答记录和技术就绪条件，但技术阶段仅引用提问边界，缺少具体问询节奏、较小额度与面向用户的解释方式。本次补齐 skill 与相关说明，沿用既有问答命令、JSON 结构和工作台展示。

## 方案要点

- 技术阶段复用决策树与 frontier：先调查事实，只问前置已明确、需要用户或责任人决定的关键取舍；根据回答继续展开相关分支。
- 问询前用简短、易懂的说明介绍实现路径、主要复用或新增机制，以及与用户有关的影响。解释本身不算问题；无须追问时仍介绍实现重点。
- 只追问影响用户体验、数据处理、兼容迁移、成本运维、安全边界或核心可行性的必要决策；常规实现细节由 Agent 按项目约定决定。每题说明取舍、推荐及其影响，不要求用户替 Agent 选内部实现细节。
- 保留 Change 总预算，技术问询另受较小上限约束：small 在需求澄清中最多 1 题；medium 最多 1 轮、每轮 2 题、总计 2 题；large / xlarge 最多 2 轮、每轮 2 题、总计 4 题。不为技术阶段重置总额度，明确时零追问。
- 技术问答继续使用稳定 Q 编号与全 Change 递增轮次；结论写入 Technical，small 写入 Requirement。涉及目标、范围、行为或验收变化时按需求返工处理。额度用尽不掩盖关键缺口，不将解释、推荐或沉默视为确认。

## 验收

- 技术规则明确引用既有分轮机制，保留依赖未决时只暂停相关分支的行为。
- 用户能在问询前理解实现重点；每题围绕有实际影响的取舍，解释和普通实现选择不增加提问数量。
- 规模额度比需求上限更小，说明共享总预算、跨会话与返工不重置、撤回不退额度、零追问与到限处理；small 不新增技术阶段或审批。
- 问答记录与结论回写适用于需求和技术，方案确认继续遵循技术就绪条件与原规模规则。
- skill 校验通过，相关 Markdown 引用有效，差异检查无空白问题；以无技术决策、依赖追问、总额度耗尽与需求变化等场景自查规则的一致性。

本次仅调整协作规则文档，规模为 small；无运行服务实现改动。
