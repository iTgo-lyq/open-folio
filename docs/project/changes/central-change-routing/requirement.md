# 集中管理 Change 入口与独立工作区执行

## 背景与目标

用户通常从主工作区发起会话。现有 SpecTrail 在创建 Change 时就切到独立分支，后续又可能通过 shell 创建 worktree，但会话本身仍驻留原工作区。多个任务并行时，恢复上下文依赖会话记忆、当前目录和跨分支查找；OpenFolio 为发现 Change 也需要读取全部分支。

本次建立固定的 Change 讨论入口：主工作区固定检出协作分支，集中规划与发现；进入实现前，将该 Change 交给独立工作分支、worktree 和执行会话。协作分支保留工作分支入口，最新流程状态和执行材料取目标分支。

用户已经明确的边界：

> “主工作区就是固定分支用于 change 讨论。其他工作区用于任务推进。”
>
> “我的意思是保存工作分支入口。最新状态以目标分支为准。”

“固定”约束主工作区的分支角色，分支上的规划材料仍正常更新。主工作区不等于 Git 的 `main`；`main` 继续作为交付代码和 Specs 基线。

本轮按用户要求同时整理[技术方案](technical.md)与[执行计划](plan.md)，供整体评审；阶段确认仍由 `change.json` 记录，不把创建授权当成全部方案批准。预期至少六项需要集成的交付，且改变流程来源契约，按 large 管理。

## 范围

- SpecTrail 的配置、创建与发现、阶段来源、移交、恢复、取消、归档、依赖核对及提交校验。
- 从主工作区定位工作分支和本地 worktree，并新建或继续实际绑定该工作区的执行会话；跨会话恢复使用仓库记录。
- OpenFolio 的仓库发现、定向 Git 读取、增量缓存、Change 主来源、依赖与原型来源、来源异常展示。
- 旧项目接入迁移、本仓库试运行及必要的规则与 Specs 更新。

不建设通用 Agent 调度服务或分布式锁服务，不要求所有人把实现代码合到一个共享开发分支，不将本机路径、会话 ID、未提交现场同步到共享 Change 记录。不新增会话管理 UI；工作台继续只读，沿用现有列表、详情和来源异常入口。

## 行为变化

### MODIFIED：从固定入口讨论与发现 Change

主工作区固定检出已配置的协作分支。新 Change 在这里保存完整需求、方案、计划和规划阶段状态；读取前核对远端差异。主工作区不因某个 Change 开始实现而切换分支，也不执行产品代码修改。

协作分支允许多个规划中的 Change。多个会话可以并行调查和准备材料，但共享工作树、暂存区的写入与发布须协调；取消一个规划 Change 不冻结其他 Change。

### ADDED：移交后只保存工作分支入口

进入实现前，先在工作分支发布该 Change 的完整记录，再将协作分支中的完整目录替换为明确的引用记录。工作分支从已核对的交付基线创建，只带入本 Change 材料，不继承其他未归档 Change。

引用记录只回答“去哪个分支读取”，不复制阶段、任务、等待、审批或完成状态。移交后，即使返工回需求阶段，完整记录仍在工作分支；协作分支入口保持稳定。目标缺失或非法时报告来源异常，不采用集中分支旧副本猜测进度。

### ADDED：在正确的工作区和会话继续执行

从任意同仓库 worktree 发起继续操作，均能通过配置与集中入口定位 Change，再通过 Git 登记确定本地工作区。已有 worktree 时优先复用；没有时从目标分支建立；本地存在未推送提交、脏文件或路径失效时保留现场并明确恢复步骤。

默认由主工作区发起新的执行会话，或继续已经绑定目标 worktree 的会话。执行前核对仓库身份、实际 cwd、检出分支、Change 来源及本地写入占用。shell 的 `cd` 或 `git worktree add` 成功不代表会话绑定已改变。

当前客户端不能创建或继续准确绑定的会话时，输出可执行的人工打开入口与最小续接提示，保留已完成的准备工作；在绑定得到验证前不开始实现。Handoff 可作为有能力客户端的备选，不依赖“让子 Agent 迁移父会话”作为标准路径。

### MODIFIED：后台按登记入口读取最新状态

新模式下，后台读取默认分支上的配置和稳定 Specs，再读取指定协作分支，随后仅读取引用指向的工作分支及必要的原型保留来源。未登记的分支不会通过全量扫描自动进入工作台。

协作分支未变但某个工作分支发生变化时，后台仍更新该 Change。两个 Change 不因共享分支副本重复计数；损坏或失效入口保持可见且不能冒充有效状态。原型、任务、澄清、关系及文档深链接继续指向相同的权威来源。

### MODIFIED：生命周期与历史可持续读取

移交中断可重试，不能出现对读者而言两个同时有效的写入来源。取消、返工、归档都按当前归属处理。新 Change 的归档沿稳定入口继续可读；清理 worktree 不删除流程记录或默认删除远端工作分支。既有归档不批量改写，已有原型保留引用继续有效。

旧配置项目在明确的旧模式中继续可读；启用新模式需要显式迁移并核对登记覆盖。新模式发生错误不能静默退回全分支扫描。

## 验收标准

| 编号 | 可观察结果 |
| --- | --- |
| A1 | 创建两个 Change 后，主工作区仍在协作分支，两份规划都可发现；开始其中一个 Change 不带走另一个的材料。 |
| A2 | 移交前读取集中完整记录；移交后集中目录只有引用，读取目标分支的最新状态；在两次发布之间中断并恢复不重复创建或误选来源。 |
| A3 | 在主工作区、另一个 worktree、新克隆中按同一 ID 都定位同一远端工作分支；本地工作区存在、缺失、脏状态、领先、分叉和路径失效分别有确定行为。 |
| A4 | 目标会话实际 cwd、命名分支及仓库身份核对通过才开始实现；模拟会话仍绑定原目录、异步创建未完成或客户端不支持时，不误报执行就绪。 |
| A5 | 两个 Change 并行修改时各自文件与暂存区独立；同机重复启动同一 Change 被占用检查拦截；共享规划工作区不会将另一会话的修改一起提交。 |
| A6 | 为新模式仓库增加大量无关分支，不增加正文扫描来源；命令记录中无用于 Change 发现的 `refs/heads/*` 拉取。协作分支不变、目标提交变化仍更新视图。 |
| A7 | 目标删除、同 ID 多份 live/archive、分支声明不匹配、入口与完整记录共存、配置非法都显示具体来源问题；不使用旧缓存或其他副本充当当前状态。 |
| A8 | 取消规划不影响其他规划；移交后返工不迁回主工作区；执行归档后入口仍能读取材料，清理本地 worktree 后仍能恢复。依赖和父子关系按权威记录核对。 |
| A9 | 旧项目迁移可预览、发现冲突并重复运行；未登记工作不被误认为迁移完成；既有归档、Specs、当前原型和固定原型仍可读。 |
| A10 | 新模式读取失败可保留上次成功快照并标明过期/失败，正常条目级错误可被展示；读取过程中来源变化不会混合出不一致的 Change 状态。 |

## 约束与边界

共享事实仍以中心仓库已推送提交为准；未提交或未推送工作只能在原机器恢复。worktree 隔离文件与暂存区，但不消除同模块语义冲突、同机服务端口和数据目录冲突。同机执行占用不能声称提供跨机器排他保证。

跨 Change 的实现依赖、阶段确认、验收和合码授权沿用现行规则。协作分支不整体合入 `main`；产品实现从各工作分支独立交付。长期服务发布从已验证的交付基线进行，不能把主工作区固定到协作分支误当成已切换部署来源。
