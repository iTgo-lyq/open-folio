# 集中管理 Change 入口与独立工作区执行

## 背景与目标

用户通常从主工作区发起会话。现有 SpecTrail 在创建 Change 时就切到独立分支，后续又可能通过 shell 创建 worktree，但会话本身仍驻留原工作区。多个任务并行时，恢复上下文依赖会话记忆、当前目录和跨分支查找；OpenFolio 为发现 Change 也需要读取全部分支。

本次建立固定的讨论与预发布入口：主工作区固定检出协作分支，默认名为 `develop`，集中规划、发现并集成各 Change 的交付。进入实现前，将该 Change 交给独立工作分支、worktree 和执行会话；完成后默认合回 develop。集中记录通过 `change.json.branch` 保留工作分支入口，最新流程状态和执行材料取目标分支。

用户已经明确的边界：

> “主工作区就是固定分支用于 change 讨论。其他工作区用于任务推进。”
>
> “我的意思是保存工作分支入口。最新状态以目标分支为准。”
>
> “就靠 change.json 记录 branch 就行了。”
>
> “协作分支预期也是预发布分支，所有 change 默认合入这里。至于保护分支，用户主动要求时才合入或创建 PR。这个协作分支默认叫 develop。Setup skill 也要引导提前配置好。”
>
> “对于 v1 的工作台查看处理，我们只需要展示协作分支内容就够了。旧的全量扫描可以完全下线。”

“固定”约束主工作区的分支角色。develop 既保存规划材料，也接收完成的代码、Specs 与归档，形成预发布版本；主工作区不用于直接实现任务。保护分支（本仓库为 main）保留正式交付，只有用户主动要求时才向其合入或创建 PR。

本轮按用户要求同时整理[技术方案](technical.md)与[执行计划](plan.md)，供整体评审；阶段确认仍由 `change.json` 记录，不把创建授权当成全部方案批准。预期至少六项需要集成的交付，且改变流程来源契约，按 large 管理。

## 范围

- SpecTrail 的配置、创建与发现、阶段来源、移交、恢复、取消、归档、依赖核对及提交校验。
- 从主工作区定位工作分支和本地 worktree，并新建或继续实际绑定该工作区的执行会话；跨会话恢复使用仓库记录。
- OpenFolio 的仓库发现、定向 Git 读取、增量缓存、Change 主来源、依赖与原型来源、来源异常展示。
- Setup 提前配置 develop、保护分支及默认合入方向，旧项目接入迁移、本仓库试运行和必要的规则与 Specs 更新。

实现工作在独立分支进行，完成后的交付默认集成到 develop。不建设通用 Agent 调度服务或分布式锁服务，不将本机路径、会话 ID、未提交现场同步到共享 Change 记录。不新增会话管理 UI；工作台继续只读，沿用现有列表、详情和来源异常入口。

## 行为变化

### MODIFIED：从固定入口讨论与发现 Change

Setup 在开始 Change 前引导确认并登记协作分支（默认 develop）、保护分支与默认合入规则，检查分支存在性和实际写入权限。主工作区固定检出协作分支，新 Change 在这里保存完整需求、方案、计划和规划阶段状态；读取前核对远端差异。主工作区不因某个 Change 开始实现而切换分支，不直接编写产品实现。

协作分支允许多个规划中的 Change。多个会话可以并行调查和准备材料，但共享工作树、暂存区的写入与发布须协调；取消一个规划 Change 不冻结其他 Change。

### MODIFIED：用 change.json 的 branch 定位工作分支

移交时协作分支保留原有 `change.json` 和规划文档。工作分支从已核对的最新 develop 创建，继承其代码与文档基线；只推进本 Change，其他 Change 的继承副本按 branch 读取来源，不在本分支维护。集中 `change.json.branch` 随规划交付检查点登记工作分支，不为替换文件格式或清空规划目录额外制造提交。

读取时先看 `branch`：指向协作分支自身时，采用此处记录；指向工作分支时，到该分支读取最新状态与正文。协作分支原有的阶段、任务、审批和文档可以停留在移交时，不再同步，也不作为当前进度的依据。移交后返工仍在工作分支进行；目标缺失或非法时报告来源异常，不用集中分支旧值补成最新状态。

### ADDED：在正确的工作区和会话继续执行

从任意同仓库 worktree 发起继续操作，均能通过配置与集中入口定位 Change，再通过 Git 登记确定本地工作区。已有 worktree 时优先复用；没有时从目标分支建立；本地存在未推送提交、脏文件或路径失效时保留现场并明确恢复步骤。

默认由主工作区发起新的执行会话，或继续已经绑定目标 worktree 的会话。执行前核对仓库身份、实际 cwd、检出分支、Change 来源及已有 worktree/会话。shell 的 `cd` 或 `git worktree add` 成功不代表会话绑定已改变。

当前客户端不能创建或继续准确绑定的会话时，输出可执行的人工打开入口与最小续接提示，保留已完成的准备工作；在绑定得到验证前不开始实现。Handoff 可作为有能力客户端的备选，不依赖“让子 Agent 迁移父会话”作为标准路径。

### MODIFIED：后台按登记入口读取最新状态

后台从默认分支读取项目入口配置，再从 develop 的活动及归档目录发现 `change.json`，随后仅读取其 `branch` 指向的工作分支及必要的原型保留来源。工作台只展示协作来源，旧的全量扫描直接下线；未登记的分支不会自动进入工作台。项目当前 Specs 和当前原型跟随 develop，明确标识预发布来源；保护分支仍保留正式基线，不把预发布内容表述为已正式交付。

协作分支未变但某个工作分支发生变化时，后台仍更新该 Change。两个 Change 不因共享分支副本重复计数；损坏或失效入口保持可见且不能冒充有效状态。原型、任务、澄清、关系及文档深链接继续指向相同的权威来源。

### MODIFIED：生命周期与历史可持续读取

移交中断可重试，不能出现对读者而言两个同时有效的写入来源。取消、返工、归档都按当前归属处理。达到已有验收和关闭条件后，Change 默认合入 develop，无需再次选择合入目标；这不跳过该规模所需的阶段确认与验收。代码、Specs 与归档一起集成，原集中目录随该 Change 的正常归档合码成为归档记录，继续由其中的 branch 定位来源；不需要另做指针清理或状态同步提交。取消的实现不自动合入。

保护分支合入或 PR 由用户主动要求触发，普通 Change 完成不自动发起。默认以已验证 develop 提交的完整交付内容发布，明确源/目标差异并排除未完成规划目录；不建设按任意 Change 组合发布的引擎。发布过滤不能反向删除 develop 上的规划，保护分支独立热修复须先核对保留。清理 worktree 不删除流程记录或默认删除远端工作分支，既有归档不批量改写，已有原型保留引用继续有效。

旧配置项目由 Setup 引导补齐协作分支与已知入口，未接入时显示具体配置问题，不再保留旧扫描模式或自动降级。已有完整状态格式、归档和固定原型继续可读，不因扫描方式调整批量重写历史。

## 验收标准

| 编号 | 可观察结果 |
| --- | --- |
| A1 | Setup 在创建 Change 前引导配置 develop 和保护分支；创建两个 Change 后主工作区仍在 develop，两份规划都可发现；工作分支可继承其他记录，但只能推进所属 Change。 |
| A2 | 移交后协作分支保留原 `change.json` 和正文，仅通过 `branch` 指向工作分支；不新增入口文件或清空目录。集中副本与目标进度不同时采用目标最新状态，目标发布或分支登记中断后可恢复。 |
| A3 | 在主工作区、另一个 worktree、新克隆中按同一 ID 都定位同一远端工作分支；本地工作区存在、缺失、脏状态、领先、分叉和路径失效分别有确定行为。 |
| A4 | 目标会话实际 cwd、命名分支及仓库身份核对通过才开始实现；模拟会话仍绑定原目录、异步创建未完成或客户端不支持时，不误报执行就绪。 |
| A5 | 两个 Change 并行修改时各自文件与暂存区独立；发现已有 worktree 时定位并复用，不为同一分支另建工作区；规划提交按 Change 路径隔离，不带入其他暂存修改。同一 worktree 的多个写入会话须协调，不声称自动互斥。 |
| A6 | 增加大量无关分支，不增加正文扫描来源；命令记录中无用于 Change 发现的 `refs/heads/*` 拉取，代码中不保留旧全量扫描兼容路径。未接入项目提示 Setup；协作分支不变、目标提交变化仍更新视图。 |
| A7 | 目标删除、目标分支同 ID 多份 live/archive、目标声明分支不匹配、入口 branch 非法或配置非法都显示具体来源问题；集中与目标分支各有一份 change.json 属正常情况，不重复计数、不拼接状态、不以旧缓存回填。 |
| A8 | 取消规划不影响其他规划；移交后返工不迁回主工作区；完成 Change 默认合入 develop，其他活动 Change 继续可读；归档中的 branch 仍能定位材料。清理本地 worktree 后可恢复，依赖和父子关系按权威记录核对。 |
| A9 | 旧项目迁移可预览、发现冲突并重复运行；未登记工作不被误认为迁移完成；既有归档、Specs、当前原型和固定原型仍可读。 |
| A10 | 新模式读取失败可保留上次成功快照并标明过期/失败，正常条目级错误可被展示；读取过程中来源变化不会混合出不一致的 Change 状态。 |
| A11 | 完成 Change 时不自动向保护分支合入或创建 PR；用户主动要求后，候选明确源/目标和交付范围，排除活动规划目录；连续发布保留 develop 规划，保护分支独立修改不会被覆盖。 |
| A12 | 项目当前材料显示实际的 develop 预发布来源，保护分支尚未发布的内容不被显示为正式交付；原型固定版本与权限保持有效。 |

## 约束与边界

共享事实仍以中心仓库已推送提交为准；未提交或未推送工作只能在原机器恢复。worktree 隔离文件与暂存区，但不消除同模块语义冲突、同机服务端口和数据目录冲突。不新增执行占用登记或强制会话互斥；同一 Change 的写入者仍须协调。

跨 Change 的实现依赖、阶段确认和验收沿用现行规则；合码默认目标调整为 develop，保护分支操作另需用户主动要求。依赖已归档并集成到 develop 后，下游即可按现有可用性条件推进，不必等待发布到 main。预发布服务只运行已集成并验证的 develop 代码，构建和部署使用干净的专用 checkout，避免占用正在讨论的主工作区；切换生产或正式发布目标仍由明确指令触发。
