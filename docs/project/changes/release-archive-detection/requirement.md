# 按发布分支归档识别已合入 Change

## 目标与范围

当前工作台依赖 Change PR、发布 PR 正文清单与 Git 祖先关系共同判断发布状态。已经进入发布分支的归档会因 PR 缺少标记、历史 PR 不可读而留在“已完成”。本次以单一 `workflow.releaseBranch` 当前远端快照中的有效归档判断已合入，使这些 Change 统一进入“已归档”tab。

沿发布分支的第一父链定位首次引入对应 Change 有效归档的提交，再匹配目标仓库、发布分支、已合并状态和合并提交一致的 PR。关联不依赖 PR 正文中的 SpecTrail-Includes。可唯一核实且有可靠 mergedAt 的 PR 用于发布批次和日期；查不到、无权限、歧义或缺少时间时保留已合入，归入“合入时间未知”。

继续只支持一个发布分支。有效归档沿用既有关闭、目录与流程校验，不接受仅修改 completed 字段的记录。发布分支读取失败或归档不合法不能新增已合入结论。集成分支的 Change 来源、原始合入差异和交付前 CI 不在本次调整范围；既有历史人工补记保留兼容。已合入不代表已部署。

## 验收

补充发布版本展示：从归档首次有效引入的发布提交中读取常见项目版本文件，不读取最新分支版本。支持根目录 package.json、Cargo.toml、pyproject.toml、pom.xml、pubspec.yaml、VERSION 和 version.txt 中的静态版本；Go 没有统一的自身版本字段，使用项目已有 VERSION/version.txt，不把 go.mod 的 Go 版本或依赖版本当作发布版本。没有静态文件版本时兼容精确指向对应提交的 v1.2.3、1.2.3、release-1.2.3、release/v1.2.3 等 Git tag，支持轻量和附注 tag，不取祖先提交的最近 tag；不要求创建 tag，不执行动态构建求值。多个来源版本不一致时不猜测。既有 PR 版本标记仅保留为没有文件版本时的展示兼容；标记删除与交付前 CI 改造仍另行讨论。

版本文件结果按发布提交持久缓存，包括确定的缺失、无效和冲突结果；tag 因可移动和后补而单独缓存 5 分钟，包括无 tag 结果，缓存过期后重查远端；临时读取失败可重试。版本不可得不影响归档归类、PR 关联或合入时间。

- 发布分支存在有效归档时，即使没有 Change PR、发布清单漏项或 PR 查询不可用，也显示已合入，进入已归档 tab，不留在已完成 tab。
- 沿发布分支第一父链找到实际引入提交；后续发布、目录改名和正文修改不替换首次交付批次；不能把工作分支原始归档提交当作发布提交。
- 唯一匹配到已合并发布 PR 且有有效 mergedAt 时，按该 PR 分组；无可核实 PR 或可靠时间时进入“合入时间未知”。
- 无效归档、重复 ID、残留活动目录不能凭 completed 声明判定已合入；发布分支快照变化后刷新结论。
- 单发布分支配置、仓库访问校验、原有集成进度与历史补记继续可用。
- 无版本标记的发布 PR 可展示对应提交中的静态项目版本；后续版本变更不改写旧批次版本，刷新和服务重启复用版本缓存。

## 确认依据

用户已确认：“那先保持单发布分支，按 releaseBranch 中的有效归档判断已合入，再从 Git 历史反查 PR，查不到 PR 就丢进合入时间未知分类中。保证都转到已归档的 tab”。方案沿用此前已讨论的发布分支快照、第一父链引入提交和 PR 精确匹配流程。

用户继续补充：“SpecTrail-Version 可以从 package.json 反推……可以补一些常见的”，以及“常见的 Git tag 模式也可以兼容一下”。本轮据此追加版本文件与 tag 推断；是否整体删除 SpecTrail-Change 等交付协议仍为讨论项。
