# 发布历史冷重建测量

测量时间：2026-11-12。基线为 T2 提交 `2711c13b4865725d22a3a838cc5e4dd0f7b1fd53`，优化版本为本 Change 的 T3。均在同一 Linux 开发机、Node 24.21.0、同一套真实本地 Git 仓库数据上运行。各规模串行执行，测量期间未运行构建或全量测试。

## 旧成本及约束依据

| 环节          | 基线成本                                                         | T3 处理                                                                                                           |
| ------------- | ---------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| 当前文档/归档 | 每个 blob 分别启动大小和内容读取；每个 Change 过滤全体文档、路由 | ls-tree 携带大小；目录、路由、ID、路径索引；分阶段 cat-file --batch                                               |
| 发布历史      | 第一父链各节点重复读树、解析及校验归档全集                       | 当前有效归档只验证一次；一次新增路径日志按 ID 找首次进入发布提交                                                  |
| 集成历史      | 每个 Change 读合并元数据、归档树并查询祖先                       | 一次批量合并元数据/新增路径；每个目标 tip 一次祖先集；缓存有效边界                                                |
| PR 关联       | 按目标分支全量分页，历史页条件请求仍逐页访问                     | 一份仓库目录；本地按登记分支/发布提交关联；首屏 ETag 与更新时间增量分页；容量计数仅累计变更记录，不逐页序列化全集 |
| 版本          | 每个发布提交分别读取多个对象                                     | 仍按发布提交读文件路径和模式；所有缺失 blob 去重后一次批读；已有文件结果和 tag TTL 复用                           |
| 首次工作台    | 全部历史完成才可读                                               | 当前归档快照先发布，既有自动刷新等待同一任务补齐历史                                                              |

Spec 已规定归档只读、普通 merge、单分支归属及同仓库交付，所以历史逐节点重验、逐 Change 全树扫描没有必要。当前归档有效性、真实合并双亲/祖先、同仓库及权限边界保留。三个正文标记协议按用户要求移除；源分支登记和固定提交差异提供关联依据。

## 数据与口径

脚本：`scripts/benchmark-release-history.ts`。每个 Change 有集中规划、工作分支提交和普通双亲集成；每批另有普通发布 merge。发布批次依次采用 20、35、15、30 个 Change，循环分布；1k/3k/5k 分别 40/120/200 批。80% 为 small，20% 为 medium；包括 Change JSON、需求、执行记录，medium 另有 Technical 和 Plan，共 3,402 / 10,202 / 17,002 份文档。每批有 package.json 版本，无故意构造的目录损坏或超长历史。材料使用简短文本，没有图片或大型原型；样本是已发布历史集合，不用于证明 5k 个同时活动工作分支的性能。

每次新建进程，删除应用缓存、快照、blob、PR、版本及本地 bare Git 缓存后重建。保留作为远端的 fixture 仓库；操作系统页缓存未清空。这是应用和 Git 缓存全丢失的冷启动，不是机器重启后的冷磁盘测量。

计时覆盖 Git 初始化/获取、当前读取/解析/校验、归档验证、历史、PR 投影、版本与文件落盘。列表时间为第一份全部条目可读且归档状态已核实的服务端快照可用时间；不等于浏览器渲染完成时间。历史时间为整个 refresh 完成，均自同一起点累计。

Git 为 `file` 协议真实获取，计入总耗时；GitHub 使用有 100 条分页的 Provider fixture，无网络延迟。优化运行刻意将所有 PR 正文换成普通说明，确认不依赖标记；基线保留合法标记以测其正常路径。超时保持默认 120 秒，没有扩大并发。默认文档限额 10,000；3k/5k 测量分别显式配置为 10,302 / 17,102，其他字节限额不变。不能据此宣称默认限额能读取 5k Change。

## 结果

| Change / 发布批次 | 基线列表 / 历史        | 优化列表 | 优化历史 | Git 调用：基线 → 优化 | GitHub fixture 请求：基线 → 优化 |
| ----------------- | ---------------------- | -------- | -------- | --------------------- | -------------------------------- |
| 1,000 / 40        | 45.387 s / 45.387 s    | 2.567 s  | 3.071 s  | 10,744 → 64           | 12 → 11                          |
| 3,000 / 120       | 120.088 s 超时，无列表 | 8.542 s  | 10.462 s | 22,862（中止时）→ 144 | 0（未到 PR 阶段）→ 32            |
| 5,000 / 200       | 120.023 s 超时，无列表 | 17.167 s | 21.295 s | 27,753（中止时）→ 224 | 0（未到 PR 阶段）→ 52            |

1k 完整历史耗时下降约 93.2%，Git 调用下降约 99.4%。3k/5k 基线未完成，不能计算完成耗时加速比。三个优化样本都读到全部 Change，且全部为 releaseMerged。

优化后每个样本的 Git 结构为：init 1、for-each-ref 3、ls-remote 3、fetch 2、rev-parse 3、cat-file 4、log 4、rev-list 1，以及 `发布批次 + 3` 次 ls-tree。4 次 log 包括当前作者/参与者信息、发布首次引入和合并差异批读；版本路径/模式仍每发布提交一读。1k/3k/5k 的本地 fetch + ls-remote 累计为 0.401 / 1.756 / 3.663 秒，已包含在上表。

## GitHub 策略成本

完整工作台需要 Change PR 和发布 PR；本地先确定登记分支、实际目标和归档引入提交，关联/版本/差异只对相关候选计算。所测样本的全仓 PR 数为 1,040 / 3,120 / 5,200，实际 fixture 分页为 11 / 32 / 52 次，没有逐 Change 请求。若只按每个发布提交查询，理论上至少需要 40 / 120 / 200 次，且还未获得 Change PR 数据；此处是按批次数推算，未声称有真实千级 GitHub 延迟测量。

另用已登录 `gh api` 对真实 `iTgo-lyq/open-folio` 做了串行只读测量，含 gh 进程及网络耗时，无人为延迟。该仓库当时 60 个 PR，26 个已合并到 main 的不同发布提交：

| 实测请求范围                           | 请求数 | 累计墙钟耗时 | 响应正文大小 | 返回 PR 条目 |
| -------------------------------------- | ------ | ------------ | ------------ | ------------ |
| 全仓 PR 按 updated desc 分页，每页 100 | 1      | 1.612 s      | 980,403 B    | 60           |
| 26 个发布 SHA 的 commits/{sha}/pulls   | 26     | 28.629 s     | 426,196 B    | 26           |
| 首屏携带 If-None-Match 重查            | 1      | 1.020 s      | 0 B，304     | 复用缓存     |

按提交减少响应体但增加请求与延迟；本仓库及正常完整重建规模采用仓库目录更简单且请求更少。不能把这次网络时延外推到千级样本。若仓库绝大多数 PR 与 SpecTrail 无关、只有极少发布提交，按提交可能更便宜；当前未实现策略自适应切换。

暖刷新首屏 304 的一次请求已真实核实；更新时间变化、旧 PR reopen/retarget、同时间戳跨页和失败页不落盘由回归测试验证。发布分支、ID 集及规则不变时不再遍历归档历史；版本正负结果按提交复用，tag 过期时单独读取。

## 复现与限制

```sh
BENCHMARK_UNMARKED=1 node --conditions=react-server scripts/benchmark-release-history.ts . 1000 /tmp/openfolio-release-scale-1000
BENCHMARK_UNMARKED=1 node --conditions=react-server scripts/benchmark-release-history.ts . 3000 /tmp/openfolio-release-scale-3000
BENCHMARK_UNMARKED=1 node --conditions=react-server scripts/benchmark-release-history.ts . 5000 /tmp/openfolio-release-scale-5000
```

基线用 `git archive 2711c13` 解包到独立目录并链接锁定的依赖，再将脚本的第一个参数改为该目录，不设置 BENCHMARK_UNMARKED。脚本输出 JSON，包含实际限额、耗时、Git 命令次数和 fixture 请求数。真实接口对比使用 GET `/repos/iTgo-lyq/open-folio/pulls?state=all&sort=updated&direction=desc&per_page=100&page=1`（按 Link 翻页），从返回中取 main 已合并 PR 的 merge_commit_sha，再逐一 GET `/repos/iTgo-lyq/open-folio/commits/{sha}/pulls?per_page=100`；条件请求使用首屏返回的 ETag。

上表采用最终代码各规模的单次重测值；开发过程另有中间测量，不混合为统计样本，没有统计置信区间或跨机器保证。Git 对象传输、仓库规模、文档体积和真实网络可能改变时间。默认文档限额、120 秒整体刷新限额及既有 Git 输出限额仍生效；超限不能伪装为完整结果。首次列表可读不意味着历史已经补齐；未知 PR/时间保留已归档。版本只支持已列的根静态文件和精确 tag；不执行动态版本逻辑，不推断 monorepo 多包独立版本。当前保留按发布提交的 ls-tree 和顺序文件写入，5k 列表仍需约 17.2 秒，未宣称瞬时可用。
