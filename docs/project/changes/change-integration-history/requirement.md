# 以合并提交保留 Change 交付历史并清理工作分支

## 目标

每个 Change 归档并合入协作分支后，工作台仍能查看本次任务整体合入时的 diff 和对应原型，原始远端分支、本地分支及工作区可以自动清理。历史交付通过 Git 中的合并提交定位，不依赖 PR、长期保留工作分支或额外保留标签。

需要解决的是分支和工作区的长期积累，不限制创建频率，也不统一既有分支前缀或增加日期命名规则。

当前 SpecTrail 在工作分支完成归档后快进集成；工作台可以阅读集中归档，但没有 Change 整体 diff，历史原型依赖 `spec-trail/archive-v2/<id>` 标签。本次同时调整交付流程和工作台读取方式，保证清理后仍有明确的交付入口。

## 范围与取舍

### 一次归档对应一次正式合入

Change 完成验证、验收、Specs 同步并提交归档后，先推送工作分支，再通过一个显式合并提交合入配置的协作分支，推送并核实远端记录。保留原始提交，不 squash、不改写已推送历史；可快进时也产生合并提交。

合并提交以结构化标记关联唯一 Change，标题同时提供可读说明。`change.json` 不新增合并提交字段，也不在合入后回填 SHA；原有 `branch` 保留历史归属。归档内容继续只读，后续修改新建 Change。

本次不支持同一 Change 提前分批合入或一个合并提交交付多个 Change。协作分支到工作分支的同步、任务分支的内部合并不作为正式交付记录。保护分支发布仍按项目原有授权规则执行。

### 工作台查看“合入变更”

Change 详情增加“合入变更”入口。存在有效记录时，展示合入时间、合并提交、变更文件及增删统计，并可逐文件阅读只读 diff。

整体 diff 比较“合入前的协作分支”与“合并提交结果”，覆盖本次合入的所有文件，包括代码、工程文档和 Git 原型快照。可以分组和折叠，不隐去归档移动或其他目录。二进制、超大文件和不可展示内容明确说明限制；不能把部分结果显示为完整结果。

此视图表达当时的合入效果，不推断其中代码现在是否仍然生效。无需创建 PR，也不增加评审、评论、批准或进行中差异预测功能。

没有可识别的合入记录时显示“暂无合入记录”，不宣称该 Change 从未合入。重复、冲突或不可读取的记录显示诊断，与正常空态区分。

### 原型使用同一交付入口

已合入 Change 的历史原型从其合并提交读取归档记录。Git 原型读取该提交中的固定 HTML；托管原型使用归档中已有的固定版本、地址、摘要及截图。`artifact.sourceCommit` 仍表示构建源码提交，不替换为合并提交。

不再创建原型保留标签。项目原型总览继续读取协作分支当前清单；进行中及已归档但尚未合入的 Change，继续允许从自身已推送分支的固定提交准备原型。原始分支删除后，新的已合入 Change 仍可准备和分享历史原型。

### 合入成功后自动清理

确认合并提交已保存在远端协作分支、原始交付可从中读取后，自动清理该 Change 的原始远端分支、本地工作分支和 worktree，不逐次询问是否删除。

清理须核对分支实际提交、工作区归属、未提交或未推送内容、其他有效 Change 的依赖，以及会话或服务占用。存在未保存内容、未合入新提交、无法判定的本地资料或仍在使用的工作区时，保留受影响对象并说明原因。协作分支、保护分支、主工作区、活动或取消 Change 的有效来源不在清理范围。

远端推送或核实失败时，不删除原始交付来源。合入已成功而清理失败时，分别报告合入结果和待清理对象，支持继续清理；不能因为清理失败重复创建合并提交。

### 旧标签与旧记录

用户已明确接受不保留历史兼容：旧原型或 Change 找不到符合新规则的关联提交，可以留空，不补映射、不追溯构造合并提交、不改写历史。

新读取方式生效且停止创建旧标签后，删除本仓库已有的 `spec-trail/archive-v2/*` 保留标签，以及工作台用于这些标签的可重建缓存引用。执行时重新核对清单，只处理该命名空间；调查时共有 8 个标签，详见 [Research](research.md)。

旧归档的需求、任务、验收等正文仍可阅读。无合入记录的旧 Change 显示“暂无合入记录”；其历史原型显示“未记录可定位的交付版本”。不回退到当前分支最新版本，不通过旧标签或 `sourceCommit` 猜测交付版本。未关联原型的 Change 保持原有空态。

本次不删除外部托管原型、现有公开发布内容、当前原型清单或用户持久数据。旧内部链接不承诺兼容，已有公开发布内容不因移除 Git 标签被主动回收。

## 工作边界

本次作为一个 large Change：合并提交协议与识别、交付及清理命令、工作台整体 diff、历史原型读取、旧标签切换均有独立验证边界，预计生产实现超过 1000 行。它们共同完成“清理来源后仍可回看交付”的目标，统一验收和合入。

此前 `archive-workspace-cleanup` 在自身分支归档的“保留远端分支”草案与本次最终方向不同，不作为执行依赖，不自动合入其实现，也不修改其归档。旧分支的去留不能仅凭归档状态判断，仍须核对是否实际集成。

技术方案确认后形成正式执行计划，并准备对应交互原型供审阅；实现、实际清理与服务更新在相应确认后推进。现行 Specs 在最终交付验收后再同步，不提前写入未实现行为。

## 验收

| 编号 | 场景与预期结果 |
| --- | --- |
| A1 | 已归档 Change 正式合入时生成唯一、带 Change 标记的双亲合并提交；即使可快进也如此，原始提交仍可追溯。 |
| A2 | 原始远端分支、本地分支和 worktree 删除后，从只拉取协作分支的新缓存仍能找到合入记录并阅读完整文件清单及逐文件 diff。 |
| A3 | 工作台整体 diff 与合入前协作提交到合并结果的 Git diff 一致；归档移动、增删、重命名、二进制和展示限制均有准确表达。 |
| A4 | 新交付的 Git 和托管原型在删除工作分支与保留标签后仍可定位；托管构建源码提交保持原值，当前总览和进行中固定版本预览正常。 |
| A5 | 推送失败、远端并发推进或源分支出现新提交时，不丢失交付或删除新工作；重试不会造成重复合入记录。 |
| A6 | 未保存文件、未知忽略文件、有效来源依赖或工作区占用阻止相应清理；合入已成功时仍准确展示成功记录和清理遗留。 |
| A7 | 缺失记录显示正常空态；重复标记、非法归档、历史读取失败等显示对应诊断，不猜测或悄悄使用其他版本。 |
| A8 | `change.json` 不记录合并提交；合入与清理不修改归档正文、状态或原型引用，后续调整通过新 Change 交付。 |
| A9 | 新流程不创建保留标签；切换后旧保留标签及其缓存引用被清理，旧归档正文仍可读，无关联的旧 diff 和历史原型正确留空。 |
| A10 | 仓库访问控制、已准备的公开原型、用户登录和持久数据保持正常；普通归档不触发保护分支发布。 |
