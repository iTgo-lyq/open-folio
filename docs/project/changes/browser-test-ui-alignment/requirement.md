# 浏览器回归对齐当前看板与连续交付分组

## 目标与范围

修复当前 main 上因界面演进而过期的浏览器断言，恢复看板、连续交付与详情导航的有效回归覆盖。按 small 推进：优先仅修改测试，不增加产品能力或调整无关行为。用户已明确要求在 develop 创建 Change、独立分支实现并提交 PR。

## 方案要点

- 逐个核对看板测试的目的。上下文保留、紧急程度排序与相邻导航使用当前默认处理状态分组，断言对应名称及四列；确需阶段语义的测试显式选择阶段并保留五列断言。`change-reader` 当前入口显式使用不分组，核对切换看板时真实采用的分组后再调整断言。
- 对照 [连续交付需求](../../archive/2026-10-18-change-follow-ups/requirement.md) 与 [归档时间线需求](../../archive/2026-10-27-archive-merge-timeline/requirement.md)，结合当前 [Change 追踪 Spec](../../specs/project-knowledge/change-tracking/spec.md)，判断已完成范围的分组预期并记录依据。若既定行为要求按交付阶段拆分，则保留产品逻辑，分别验证各阶段中的连续交付与普通列表中的组内排序；若要求整组唯一，则仅修正相关产品逻辑。
- 每项修改前在最新远端 main 的未修改测试上复现；核对 `change-directory` 已显式选择阶段的断言是否本来通过。测试使用独立 fixture 数据与端口，不接触长期服务数据。

## 验收

1. 记录当前 main 的提交及五个目标场景的原始执行结果，区分实际失败与本来通过项。
2. 看板断言与测试所选分组一致：处理状态四列、阶段五列、不分组一列；原有筛选、排序、详情导航及上下文检查继续有效。
3. 连续交付分组的处理有两边需求与当前 Spec 的依据，测试覆盖真实交付阶段与筛选、排序、深链接，避免通过移除有效断言掩盖失败。
4. 五个相关 spec 与完整 `npm run test:e2e` 均执行，记录结果；不改变无关产品行为。
5. 自查、按 small 自验收并归档，通过目标为 develop 的 PR 交付。
