# 浏览器回归对齐当前看板与连续交付分组

## 目标与范围

修复当前 main 上因界面演进而过期的浏览器断言，恢复看板、连续交付与详情导航的有效回归覆盖。按 small 推进：优先仅修改测试，不增加产品能力或调整无关行为。用户已明确要求在 develop 创建 Change、独立分支实现并提交 PR。

## 方案要点

- `changes` 的上下文保留与 `change-labels` 的紧急程度排序使用默认处理状态分组，断言「按处理状态看板（只读）」及四列。`change-reader` 入口已显式指定 `group=none`，切换看板不改变分组，断言「不分组看板（只读）」及一列。`change-directory` 已显式选择阶段，其「按阶段看板（只读）」及五列断言保留。
- 连续交付保留产品逻辑：已完成范围先按交付阶段分组，同一延续组可在不同阶段各出现一次。测试先验证「待集成」与「交付待核实」各包含正确的唯一成员，再显式选择「不分组」，验证整组展示、排序、筛选和深链接。
- 每项修改前在最新远端 main 的未修改测试上复现；核对 `change-directory` 已显式选择阶段的断言是否本来通过。测试使用独立 fixture 数据与端口，不接触长期服务数据。

## 连续交付判断依据

[连续交付需求](../../archive/2026-10-18-change-follow-ups/requirement.md) 要求延续链分组、各成员保留真实状态和独立入口，当时验收要求两个归档成员放在同一外框。后续 [界面重构方案](../../archive/2026-10-22-frontend-style-interaction-refactor/technical.md) 明确「已完成按交付标签分组」；[归档时间线需求](../../archive/2026-10-27-archive-merge-timeline/requirement.md) 则要求归档记录按真实日期与 PR 批次组织，每条 Change 只出现一次，方案明确跨日期连续交付不挪动真实日期。当前 [Change 追踪 Spec](../../specs/project-knowledge/change-tracking/spec.md#交付进度) 明确「已完成按待集成、待合入、待核实分组」。这些规则保留成员的真实交付阶段，未要求延续组跨阶段合并。

因此本次采用后续已验收规则：分组标题可在不同交付阶段重复，每个 Change 仍只出现一次；选择不分组时，匹配的连续交付成员聚合在一处。额外核实 Git 历史：分阶段逻辑由 `9d1a92b2` 引入，`0a3b016b` 在此处统一交付文案并增加归档时间线，并非首次引入该逻辑。本次只修测试，产品源码、Specs 与数据契约无需改变。

## 验收

1. 记录当前 main 的提交及五个目标场景的原始执行结果，区分实际失败与本来通过项。
2. 看板断言与测试所选分组一致：处理状态四列、阶段五列、不分组一列；原有筛选、排序、详情导航及上下文检查继续有效。
3. 连续交付分组的处理有两边需求与当前 Spec 的依据，测试覆盖真实交付阶段与筛选、排序、深链接，避免通过移除有效断言掩盖失败。
4. 五个相关 spec 与完整 `npm run test:e2e` 均执行，记录结果；不改变无关产品行为。
5. 自查、按 small 自验收并归档，通过目标为 develop 的 PR 交付。
