# 背景与目标

OpenFolio 需要在当前 Git 仓库内沉淀可复用的基础 UI 组件和前端开发规范，供主应用和后续维护者直接使用。项目的协作、构建和运行只依赖仓库源码与普通项目依赖。

OpenFolio 的原型模块服务于所管理的第三方仓库，读取各项目已交付的原型。本仓库自身的 UI 组件库采用独立预览页面，与被管理项目的原型展示分别维护。

本次在现有 workspace 内新增 UI 库包，集中维护组件导出、公共样式和包内预览页面，形成“维护共享组件 → 主应用消费 → 独立预览展示”的完整路径。预览与主应用使用同一份组件实现，开发规范明确如何复用、扩展和验证这些组件。用户追加授权在基础库完成后全局安装 shadcn skill/MCP，使用 shadcnuikit 引入代表性组件并优化组件预览；认证仅保存在个人环境。

本次同时改造 OpenFolio 的原型模块，使用户能从一个集中入口发现、直接打开当前所选项目的各种页面，不必逐个寻找业务入口、走完前置流程或构造特定状态。原型工程维护源码和当前入口描述，宿主负责构建并将产物上传到自己的存储或静态托管，OpenFolio 按约定读取发布后的地址与版本。总览只展示被管理项目 main 中登记的当前入口，Change 保留当时的版本引用；直接将产物提交 Git 作为兜底方案。UI 包的独立组件预览与项目原型模块均在本次范围内，各自承担不同的展示职责。

# 范围

## UI 库包与主应用消费

- 在当前仓库新增独立维护的 `packages/ui` 包，纳入现有 workspace 与 Git，对外导出可复用 React 组件、必要的主题样式及类型，并维护依赖声明与使用约定。包名及具体导出组织在技术阶段明确，不要求发布 npm 包或建立独立远程仓库。
- 主应用通过 UI 包提供的入口消费组件。业务数据获取、路由和页面业务逻辑保留在主应用，UI 包提供可由调用方传入内容、状态和交互处理的组件接口。
- 优先复用项目已有组件；新增或扩展组件时按项目设计规范、组件接口与依赖约束维护，避免同时维护同职能的多套基础组件或公共主题定义。
- 主应用和包内预览页直接使用同一份组件实现及适用的主题规则。组件维护以共享源码为准，消费方无需复制组件代码。
- 首批接入覆盖有代表性的实际使用场景，至少一个组件由主应用真正消费，并在包内预览页展示；具体组件在技术阶段结合现有 UI 确定。不将全站组件化或视觉改版纳入本次范围。

## UI 包内独立预览

- UI 包除导出组件外，还维护自己的预览页面及必要的开发、构建和预览命令。维护者按项目指引可独立启动并浏览组件示例，入口无需经过 OpenFolio 工作台。
- 预览页提供清晰的组件名称、查找或导航方式，以及有代表性的状态和交互示例，帮助维护者发现组件并理解用法。基础组件可共用一个页面，按需组织复杂组件示例，不为每个组件建立独立工程。
- 示例直接引用 UI 包的组件，只维护实例参数、状态组合、布局及必要的内存 mock。组件实现或公共样式变化后，通过预览开发服务或重新构建即可查看变化。
- 预览页面采用适合独立浏览的普通前端构建，由 UI 包的工具链处理 React、样式及资源；不要求导出自包含单文件 HTML，也不要求将生成的预览产物作为组件源码手工维护。产物是否由部署流程保存及其位置在技术阶段明确。
- 组件预览无需登记 Change 的 `previews`，不参与原型总览、原型归档或历史版本选择，不使用现有 `packages/prototype` 作为展示载体。
- 预览页只展示组件及示例数据，不依赖配置被管理的仓库、启动 OpenFolio 的 Git 采集服务或调用真实业务接口。
- UI 包的公共导出与预览入口有明确边界，主应用正常引用组件时不引入整个预览页面或演示数据。
- 本次交付可运行、可构建的预览入口和使用指引；实际外部托管或发布另按已有授权处理。

## 前端开发规范

- 在根 AGENTS.md 直接维护精简的前端开发规范，供开发者和 Agent 在新增页面、修改组件时使用，不另建前端规范文档。
- 明确基础 UI 组件、业务组件、路由页面和预览示例的职责边界；先查找和复用现有组件，公共组件通过包入口使用，避免复制实现、深层导入和反向依赖主应用。
- 明确共享设计 token、组件样式、页面布局及主题覆盖的维护方式，遵循现有视觉语言；新增基础组件和示例使用同一套公共规则，不为预览单独复制主题。
- 规定必要的组件接口、受控状态与事件、React 客户端/服务端边界，以及加载、禁用、空态、错误、键盘操作、可访问名称、焦点和响应式行为；根据组件实际能力采用相应规则，不要求每个组件实现全部状态。
- 提供安装、独立开发、类型检查、格式检查、构建和交互验证的明确命令。首批实际组件、主应用消费和预览示例应遵守这些约定，确保规范可执行。

## 可选原型协作与 skill 建议

- 原型协作保留项目级可选接入：未选择时按实际需要征求同意，disabled 时不反复建议启用，pending 时先完成接入，enabled 时复用项目已有原型工程。
- 项目已启用原型协作，且 Change 对产品 UI 有明显影响时，skill 建议优先制作或更新相关原型来辅助设计讨论。建议针对本次页面、布局或交互变化，不要求每个 Change 都有原型，也不要求补齐所有已有页面。
- 是否采用建议由具体协作决定；未制作原型不阻断需求、技术方案、实施或验收，不新增审批、强制确认记录或提交门禁。已实际交付的原型仍按正常产物和关联约定校验。
- skill 要求宿主工程自行保证所选源码和组件能正常构建、发布并供浏览器查看。React 或其他框架的构建配置由宿主维护，OpenFolio 不提供框架专用编译器；UI 包组件复用按普通工程依赖处理。

## 被管理项目的页面总览与直接预览

- 原型总览以发现项目页面和直接进入预览为核心。用户可以看到项目已提供预览的页面及代表性场景，通过清晰的名称、内容截图和必要的查找方式定位内容并直接打开，无需知道页面在真实应用中的导航路径。
- 页面示例可呈现不容易从产品首页触达的详情、设置、空状态、异常状态及其他深层场景；演示所需上下文由项目提供的原型和 mock 表达。总览可发现的内容以项目实际交付的预览入口为准。
- 总览只读取被管理项目 main 的当前状态，从原型工程的当前入口描述及其发布引用建立页面清单，不再扫描各 Change 来推算哪个产物最新；描述从固定 Git 提交读取，预览使用该描述指定的产物版本。
- 页面从 main 的当前入口描述中移除后不再出现在总览，即使已发布产物或 Change 历史引用仍保留。新发布引用随项目提交进入 main 后更新展示；上传成功本身不会改变 main 总览，无关 Change 或文档提交也不改变页面内容。
- 当前预览表示项目最近一次成功构建、发布并登记到 main 的参考结果。实际交付时记录入口描述、源码版本与发布引用；仅改变源码或产品样式不要求重新构建、上传所有已有原型，旧的参考结果仍可展示。
- 未合入 main 的新增、修改或删除不影响总览；总览不聚合开发分支，不提供分支、Change 来源或原型历史版本切换。溯源信息可按需查看，不要求用户先理解 Change、提交或源码路径才能浏览页面。
- 进行中 Change 的原型查看与分享通过 Change 页面的原型模块完成，读取其已推送记录中的已发布版本引用并提供固定版本分享链接，不要求先合入 main。
- 现存入口尚未交付产物、产物缺失或无法读取时提供准确提示，不用其他分支的内容替代当前项目状态。既有项目组件原型可继续按其交付入口查看，本仓库 UI 包的独立预览不由该模块托管。

## 宿主构建与发布接口

- 被管理项目在自己的原型工程维护源码、演示入口和构建配置，使用宿主正常的开发与 build 流程生成浏览器可查看的静态页面。源码可使用 HTML、React 及项目组件库，具体框架、依赖、路由和资源构建由宿主保证。
- OpenFolio 定义宿主可实现的原型发布接口或适配协议，明确上传、更新的输入及结果。宿主实现面向其存储或静态托管的上传逻辑；OpenFolio 不接收和托管产物文件，只保存或读取发布地址、产物版本、原型身份和源码提交等必要引用。
- 宿主发布结果提供可被工作台展示的页面地址，页面所需脚本、样式和资源由宿主托管。OpenFolio 不要求正常上传链路的页面打包为自包含单文件，也不提供额外导出操作；已发布页面应能在约定的隔离预览方式下加载并进行局部交互。
- “更新”发布新的固定版本，并更新项目当前引用，不覆盖 Change 已引用版本的内容。同一次发布可同时被当前入口描述和 Change 记录引用，无需为两者重复上传或保留两份相同文件。
- 发布成功并取得可用引用后再登记新版本；失败或部分上传不替换当前有效引用。接口需区分成功、失败及可重试结果，具体调用方式、去重与完整性检查在技术阶段明确。
- 宿主负责已发布版本的可访问性和保留期限，归档引用需能持续回看；缺失、过期或不可访问时给出明确说明，不静默改为其他版本。访问所需凭据通过宿主环境或受控配置提供，不把秘密值、上传凭据或临时访问令牌提交到项目描述文件。

## 当前入口描述与 Change 版本引用

- 原型工程约定源码及本地构建目录，并维护项目级描述文件，候选名称为 `prototype.json`。描述文件作为当前入口的唯一清单，表达稳定 id、名称、类型、适配信息、源码入口及当前发布引用；具体目录、字段及构建来源记录在技术阶段确定。
- 源码和描述文件继续随 Git 维护，正常发布链路不要求将构建产物提交 Git。总览通过 main 的描述读取当前地址，页面源码是否引用 UI 包不改变该读取机制，也不自动将 UI 包自身的预览页登记为项目原型。
- Change 关联记录本次涉及的原型身份、固定发布地址或版本引用、适配信息及生成产物所用源码的确定 Git commit。Change 归档保留这些引用，后续更新项目当前引用不改变它们；项目描述维护当前清单，Change 记录当时交付。
- Git 内保存静态产物为兜底交付方式。选用该方式时，原型工程可保存当前产物，Change 目录保留当时快照；兜底来源有明确类型及路径，技术阶段明确其支持的文件格式。上传失败不自动向 Git 写入大量产物或切换为兜底发布。
- 当前内容由总览展示，各 Change 保存自身交付引用；不新增原型迭代时间线或独立历史管理页面。既有 HTML 产物直接迁移为新格式；工作台不保留旧 path 格式兼容，迁移后提供新固定链接。
- 原型页面提供演示所需的局部状态与 mock，不依赖真实业务后端或持久存储。OpenFolio 继续隔离第三方页面与工作台，技术阶段核对宿主地址的访问和嵌入方式。
- 原型协作、发布、关联、校验和归档指引同步上述规则，说明宿主构建与上传责任、当前引用更新和历史版本保留；不因样式变化而要求重新发布全部参考原型。

## 不包含

- 通用素材管理平台、自动同步或批量获取；本次仅按追加授权完成 shadcn 全局工具接入和代表性 shadcnuikit 组件适配。
- 主动检查素材更新、追踪上游版本、自动同步或覆盖已入库组件。
- 私人素材归档数据库、完整素材镜像、复杂的跨机器恢复或按项目管理的长期下载仓库。
- 将 UI 组件库预览集成进 OpenFolio 工作台或现有原型包，或为了组件预览建设 Change 历史管理。
- 在 OpenFolio 内安装、编译或运行第三方项目源码，自动遍历真实应用路由并推定所有页面已具备预览，或为浏览原型连接真实业务后端。
- OpenFolio 自建产物上传接收服务、对象存储或静态托管平台，统一接管各宿主的构建工具链，或将构建产物提交 Git 作为正常发布的必要条件。
- 原型总览的多分支聚合、跨分支最新版本判定、迭代时间线或历史版本切换。
- OpenFolio 侧的原型导出功能、专用手工导出操作，或要求每个 Change 必须制作原型的门禁。
- 全站视觉重做、全面替换现有组件、与首批复用场景无关的重构。
- 模板商城、公共素材分发、在线编辑服务、npm 发布或独立远程仓库建设。

# 行为变化

- ADDED — `ui-development/component-library`：维护者可在仓库内发现、使用和修改 UI 包导出的组件；主应用通过包入口消费组件及适用的主题规则，普通构建和维护不依赖私人资源访问。
- ADDED — `ui-development/component-preview`：维护者可独立运行 UI 包内的预览页面，查看同一份组件实现的状态、交互和示例；查看组件无需使用 OpenFolio 的原型模块或配置来源仓库。
- ADDED — `ui-development/frontend-conventions`：维护者可根据项目级指引找到共享组件、判断组件放置位置，遵守样式和交互规则，并按明确命令开发、预览和验证前端改动。
- ADDED — `project-knowledge/prototype-preview`：提供宿主实现的发布接口或适配协议，宿主自行构建并上传到自己的存储或静态托管，OpenFolio 使用版本固定的地址与来源引用展示页面，Git 产物作为兜底交付。
- MODIFIED — `project-knowledge/prototype-preview`：总览从跨分支 Change 关联汇总改为读取 main 的当前原型描述及发布引用，以发现项目页面及直接进入预览为核心；Change 保留当时版本地址和源码提交，进行中原型仍在 Change 页面查看和分享。
- REMOVED — `project-knowledge/prototype-preview`：总览中的多分支来源选择和原型历史版本切换；各 Change 自身的交付记录及固定版本分享继续保留。
- MODIFIED — `change-workflow`：原型协作保持可选；已启用时对明显影响 UI 的 Change 建议优先制作原型，不增加强制门禁。指引明确宿主构建及上传责任、项目当前发布引用与 Change 固定版本引用的维护方式；组件库独立预览不使用该关联流程。

# 验收标准

1. 在不提供个人密钥、不安装个人接入 skill 的干净环境中，协作者可按仓库指引安装依赖，构建主应用及 UI 包预览，并修改已入库组件。
2. 至少一个代表性组件由主应用和 UI 包预览直接使用同一份实现；修改共享样式或交互后，两处均可通过各自的正常开发或构建流程体现变化，无需同步组件副本。
3. 不配置被管理仓库、不启动 OpenFolio 工作台，仍能通过明确的命令独立打开预览页面，找到首批组件并操作关键状态。
4. 示例直接使用组件公共入口及适用的主题规则，演示所需数据留在预览侧；主应用消费组件不依赖预览入口、演示数据或真实演示后端。
5. 组件预览的开发、构建和浏览无需生成 Change 原型快照、登记 `previews` 或修改既有原型包；现有原型能力不成为组件库使用的前置条件。
6. 从项目协作入口可以找到前端开发指引，并依据指引完成一次已有组件修改或新示例添加：放置位置、公共导出、样式与状态处理明确，相应类型、格式、构建和交互验证命令可运行。
7. 审阅新增的受 Git 跟踪文件、依赖与构建产物，确认不包含秘密值、个人工具配置或非必要的私人供应商标识；普通构建、测试和运行不发起私人资源请求。
8. 前端开发指引和 UI 包说明明确组件导出、主应用接入、独立预览、共享样式及维护方式；首批组件的可访问名称、键盘操作、焦点及适用状态有可检查的示例，正常维护不要求个人工具或私人资源配置。
9. 使用已交付多个页面及深层场景原型的项目，用户能够在原型总览发现、查找并直接打开这些内容，无需经过真实应用的层层入口或操作前置业务流程；预览在声明视口中可查看并操作关键状态。
10. 构造 main 中描述文件登记、已移除、没有 Change 历史关联，以及仅在开发分支新增或修改的原型，验证总览只展示 main 当前清单与对应发布地址；上传成功但引用尚未进入 main 时不改变总览，无关 Change 或文档提交也不改变展示结果。
11. 同一原型由两个 Change 先后发布时，项目当前引用可指向新版本，各 Change 保留当时的固定地址及源码提交；后一次发布不改变前一次页面内容，同一次发布可被当前清单与 Change 共同引用。
12. 未合入 main 的 Change 可以通过其已推送版本引用打开并分享原型，固定链接保持指向分享时的产物；总览无历史列表、版本切换或多分支来源选择，既有归档迁移后生成的新固定链接经验证，旧格式链接不再支持。
13. 源码或产品样式变化但未登记新发布引用时，既有参考结果仍可查看；发布地址失效或兜底产物缺失时显示准确提示。OpenFolio 不安装、编译或托管第三方项目，不依赖真实业务接口或持久存储来展示演示状态。
14. 使用宿主自行构建的 React 原型验证发布适配协议、当前地址展示及 Change 固定版本分享，可使用 UI 包组件及普通构建资源；无需将产物提交 Git 或执行专用手工导出，页面可在工作台隔离环境中加载并操作关键状态。
15. 审阅原型协作指引并用未启用、已禁用、已启用且明显影响 UI、已启用但不涉及 UI 的场景验证建议规则；不采用原型建议或没有 previews 的 Change 仍能按既有流程推进，不新增强制记录或门禁。
16. 使用可验证的宿主发布实现覆盖成功、失败和重复提交：只有成功结果会更新发布引用，失败不破坏现有预览，不会隐式把构建产物提交 Git；公开返回及 Git 元数据不含上传凭据或临时访问令牌。
17. 显式使用 Git 产物兜底时，main 当前预览和 Change 历史快照均可读取；已有 HTML 归档迁移为新引用和 Change 内快照，运行时代码拒绝旧格式，新固定链接可回看。
18. 全局 shadcn skill/MCP 和 shadcnuikit 接入经过实际调用验证；引入代表性组件并用于独立预览优化，源码、构建产物及提交均不包含 API key，协作者无需个人凭据即可维护已入库组件。

# 约束与后续设计事项

- 基础 UI 库先从现有主应用提取，再按追加授权试用 shadcnuikit；已入库组件不得在运行或构建时依赖个人认证。
- 技术阶段明确 UI 包的组件边界、首批组件、主题规则的唯一来源、包名与导出方式，以及主应用和预览构建对共享源码与依赖的处理。
- 前端开发规范需与实际源码、构建命令和预览示例一致，给出日常维护路径，不引入与本次交付无关的框架迁移或全站重构。
- 技术阶段明确预览工具链、启动与构建命令、组件示例的组织方式和构建产物管理，复用适用的项目规范。预览页的普通前端产物无需遵循第三方原型的自包含 HTML 交付协议。
- 技术阶段明确原型工程描述、入口稳定身份、删除和重命名的行为，以及当前发布引用、Change 固定版本引用和源码 commit 的记录与校验方式。Git 继续保存项目清单与 Change 记录，不再以 Change 排序计算当前版本。
- 技术阶段明确宿主发布协议的调用形式、输入输出、失败处理、幂等、版本不可变约定和引用登记路径，并用一个实际可运行的宿主适配验证；不将特定存储供应商或宿主凭据写成通用工程依赖。
- 当前工作台没有上传接收服务或外部产物发布协议，只读取 Git 内自包含 HTML；现有 skill 也明确不使用独立原型清单。需同步调整 skill、状态类型、引用校验、工作台读取、截图和归档流程，执行显式历史迁移并验证新固定链接，不保留旧格式兼容分支。
- 宿主地址接入需验证允许的来源、私有访问、iframe 嵌入、脚本与资源加载、隔离边界、失效提示、截图方式及历史版本保留。技术阶段确定远端托管地址与 Git 兜底的读取协议和限制，不把构建责任交给宿主等同于任意网址都可直接展示。
- UI 包独立预览和原型模块改造均需交付，展示入口及产物协议分别维护；OpenFolio 作为示例被管理项目时，也按普通项目的原型交付契约提供页面预览，不将 UI 包预览自动当作项目原型。
