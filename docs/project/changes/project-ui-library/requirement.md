# 背景与目标

OpenFolio 需要在当前 Git 仓库内沉淀可复用的 UI 组件，让主应用、原型和后续维护者使用同一份组件实现。个人拥有的 Shadcn 相关素材可以用于按需接入，但其获取方式、凭据和私人供应商配置不应成为项目协作、构建或运行的前提。

项目已启用唯一原型包，支持页面与组件预览、Change 关联、固定 Git 版本和归档保留。现有原型采用静态 HTML 与共享 CSS，尚未直接复用 React 组件；HTML 产物保存在原型包中，总览跨分支聚合 Change 关联并支持切换来源。此次需要打通共享组件的编译与交付路径，将持续维护的原型源码和各 Change 的交付快照分开，并将总览收敛到 main 的当前内容。

目标是形成“个人按需获取素材 → 适配并沉淀到项目组件库 → 主应用与原型共同使用 → 通过现有原型系统展示”的完整路径。组件入库后以本地源码为准，后续维护不依赖素材提供方。

原型总览用于展示工程中沉淀的页面、组件与设计场景，让只看到简洁产品入口的用户能发现背后的内容与深度。原型是阶段性的设计参考，允许与后续产品样式存在差异；重点是内容可发现、可查看和可操作，以及产物能够低成本交付，不要求原型持续追随产品样式或展示迭代历史。

# 范围

## 项目组件库与个人资源协同

- 在当前仓库建立独立维护的组件库，纳入现有 workspace 与 Git，沉淀可复用组件、必要的主题样式、依赖声明及使用约定。包边界和导出方式在技术阶段明确，不要求发布 npm 包或建立独立远程仓库。
- 主应用与原型可以消费同一份可复用组件。业务数据获取和页面业务逻辑保留在相应消费方，演示需要的数据由原型提供 mock。
- 优先复用项目已有组件；接入新素材时按项目设计规范、组件接口与依赖约束适配，避免同时保留同职能的多套基础组件或主题定义。
- 个人获取资源所用的 skill、连接配置和凭据放在用户级环境。仓库只保存协作维护需要的通用规范、适配后的组件源码及普通项目配置，不要求协作者安装个人工具或持有资源下载凭据；协作使用仍须满足适用授权。
- 个人接入 skill 说明首次使用与后续维护方式：真正需要获取新素材时，检查个人环境，按需初始化最小临时工作区；完成适配后交付项目源码。缺少凭据时说明缺失项，不向项目写入私人配置。临时工作区不作为长期维护对象。
- 项目文档、配置、提交说明和交付产物不主动记录私人供应商名称、registry 命名空间、来源链接或账户信息；依法或依授权必须保留的声明仍须保留。不承诺组件外观或源码无法被辨认来源。
- 首批接入覆盖有代表性的实际复用场景，验证主应用与原型的共同消费；具体组件在技术阶段结合现有 UI 确定，不将全站组件化或视觉改版纳入本次范围。

## 原型源码与 Change 交付

- 继续使用项目已启用的唯一原型包维护源码、演示入口与构建配置，支持直接引用项目 React 组件及设计规范；源码可以由后续 Change 继续修改。
- 新组件应有可观察、可操作的展示入口，优先复用已有页面或展示页。基础组件可共用展示入口，独立且复杂的可复用模块可建立组件预览，已由业务页面充分展示的组件无需再建同内容的预览。
- 演示只负责实例、状态、布局和 mock 数据，不复制组件实现。修改或交付某个原型时构建并验证相关入口；共享组件更新不要求重建所有原型，旧原型的样式差异不单独构成缺陷。
- 通过统一构建命令将 React 原型、组件运行代码、样式和资源编译打包成自包含 HTML。构建在开发或交付时完成，工作台继续只读已推送产物，打开预览不现场安装依赖或编译。
- 新 HTML 产物保存在所属 Change 的目录中，由工具生成并随交付提交，不作为原型工程中的长期共享输出维护。Change 归档时产物随目录一起归档；后续 Change 修改同一原型时保存自己的产物，既有 Change 的交付快照保持不变。
- Change 关联记录原型身份、产物位置、页面或组件类型、视口，以及生成该产物所用源码的确定 Git commit，使原型源码、组件实现与构建配置可追溯。具体字段、提交顺序及归档路径规则在技术阶段明确。
- 同一原型在不同 Change 中的产物共享稳定的原型身份。沿用 Change 的关联入口，不为每个组件单独新建 Change，也不另建独立组件预览服务或重复维护的展示清单。
- 将组件接入、使用、演示和维护约定落实到适当的项目指引及原型协作指引，明确个人工具、项目组件库、原型工程和工作台各自负责的事情。

## main 原型总览与 Change 页面预览

- 项目原型总览只读取 main 的当前状态。以 main 中仍存在的原型源码入口识别“现存”原型，并为每个原型展示已进入 main 的最近一次相关 Change 产物；最新针对每个原型分别判断。
- 原型从 main 移除后不再出现在总览中。后续 Change 没有更新某个原型产物时，继续展示该原型上一份交付；新产物随相关 Change 进入 main 后替换展示。仅修改源码而未重新导出的情况允许继续使用上一份参考产物。
- 未合入 main 的新增、修改或删除不影响总览。总览不汇总开发分支、不比较分支间的新旧，也不提供分支、Change 来源或历史版本切换。
- 总览以发现内容和进入演示为中心，展示可浏览的页面、组件及场景，提供直观的内容预览、清晰名称和必要的查找方式。Change、提交和文件路径等溯源信息按需查看；首批接入不要求穷举工程中全部内容。
- 进行中 Change 的原型查看与分享通过该 Change 页面的原型模块完成，从其已推送记录读取该 Change 的产物，并支持固定产物版本的分享链接；不要求先合入 main 才可分享。
- 总览不展示原型迭代历史，也不新增独立的原型历史管理能力。各 Change 的产物作为其交付记录随 Change 保存，既有归档预览的回看与链接兼容在技术阶段处理。
- main 中仍存在但尚未交付产物的原型，以及产物缺失或不可读取的原型，给出准确的可用性说明，不用其他分支或其他原型的内容替代。

## 不包含

- 主动检查素材更新、追踪上游版本、自动同步或覆盖已入库组件。
- 私人素材归档数据库、完整素材镜像、复杂的跨机器恢复或按项目管理的长期下载仓库。
- 另行搭建组件展示网站、模板商城、公共素材分发或在线编辑与构建服务。
- 全站视觉重做、全面替换现有组件、与首批复用场景无关的重构。
- 原型总览的多分支聚合、跨分支最新版本判定、迭代时间线或历史版本切换。
- 为保持原型与产品样式一致而自动重建所有原型，或在工作台运行 React 开发服务及在线编译。

# 行为变化

- ADDED — `ui-development/component-library`：维护者可在当前仓库发现、使用和修改已沉淀组件，主应用与原型共享组件源码及适用的主题规则；普通构建和维护不依赖私人资源访问。
- ADDED — `ui-development/material-intake`：资源持有者通过个人环境按需获取素材并适配入库；首次使用只初始化获取所需的最小环境，已入库组件后续按项目代码维护。
- MODIFIED — `project-knowledge/prototype-preview`：原型源码直接消费项目组件库，编译为保存在各 Change 下的自包含 HTML 并记录源码版本；总览从跨分支关联汇总改为 main 中现存原型的最新交付展示，以发现工程内容为目标；进行中原型通过 Change 页面查看和分享。
- REMOVED — `project-knowledge/prototype-preview`：总览中的多分支来源切换与原型历史版本切换。Change 内的交付记录和固定版本分享仍可使用。
- MODIFIED — `change-workflow`：组件接入与原型协作指引明确共享源码、按 Change 导出产物、版本追溯及归档约定，不要求持续同步所有参考原型。

# 验收标准

1. 在不提供个人密钥、不安装个人接入 skill 的干净环境中，协作者可按仓库指引安装项目依赖，构建主应用及已入库组件的原型，并修改这些组件。
2. 至少一个代表性组件由主应用和原型直接使用同一份实现；修改其共享样式或交互并重新构建后，两处均体现该变更，无需同步修改组件副本。
3. 展示一次按需素材接入流程：个人工具检查并准备必要环境，素材适配到项目组件库，项目产物不依赖私人 registry 或服务。凭据缺失时有明确反馈，且不会把凭据或私人连接配置写入项目。
4. 审阅新增的受 Git 跟踪文件、依赖与导出 HTML，确认不包含秘密值、个人工具配置或非必要的私人供应商标识；普通构建、测试和运行不发起私人资源请求。
5. 首批组件的展示能复用现有页面或组件入口；用户可以从总览发现代表性的页面、组件与场景并打开演示，无需先了解 Change、提交或源码路径。没有另建预览应用、重复清单或同内容的演示实现。
6. 使用统一命令构建引用共享 React 组件的原型，产物通过静态校验和实际浏览器检查，在声明视口中可操作关键状态、离线运行；工作台预览时不运行构建，不依赖真实接口或持久存储。
7. 同一原型先后由两个 Change 修改和交付时，共享源码可继续演进，两份 HTML 分别保存在所属 Change 下，并各自记录构建所用源码的确定提交。修改后者不会改写前者，归档后仍可定位对应产物。
8. 构造 main 中现存、已删除、已有多个 Change 交付，以及仅在开发分支中新增或修改的原型，验证总览仅按 main 展示现存原型的最近一份相关产物；无关 Change 或文档提交不改变选中产物，分支修改在合入前不影响总览。
9. 进行中 Change 在未合入 main 时，可以从 Change 页面打开并分享其已推送原型；固定链接保持指向分享时的产物。总览没有历史列表、版本切换或多分支来源选择；已有归档预览与固定链接的兼容经验证。
10. 原型源码或共享组件变化但没有交付新 HTML 时，既有参考产物仍可查看；缺少产物时显示准确提示。项目指引明确源码、生成产物与归档记录的维护责任，不要求为了样式同步重建所有原型。
11. 项目与个人使用指引明确：已入库组件以项目源码为准，只有明确需要获取新素材时才使用个人工具，不主动检查上游更新；展示入口仅随相关组件或场景交付维护。

# 约束与后续设计事项

- 本次需求不预设具体私人供应商、密钥名称或素材条目。实际获取与提交素材前，应核对持有者授权是否覆盖仓库的可见性、协作方式和交付用途；不能通过省略来源标识替代授权判断。
- 真实私人资源接入验证依赖合法可用的素材授权和个人环境中的凭据。尚未核实这些条件，不视为已接通；这不影响先设计和验证项目组件库与原型复用路径。
- 技术阶段明确组件库与主应用的边界、首批复用组件、主题规则的唯一来源，以及原型引用 React 组件并导出离线 HTML 的方法。不得直接假设现有 HTML 导出器或普通前端构建产物已满足这些要求。
- 技术阶段明确 main 中原型入口的发现及稳定身份规则、最近一次相关产物的确定方式、删除和重命名的行为，以及 Change 相对产物路径与源码 commit 的记录和校验方式。不要用 Change 名称、状态排序或无关提交时间冒充产物新旧关系。
- 当前严格关联契约仅允许原型包 preview 目录，读取端也按该目录限制资源范围。本次调整需同步关联校验、导出工具、工作台读取和归档流程，并验证已有归档记录与链接的兼容；已归档记录不作为新格式的人工重写对象。
- 自包含 React HTML 的体积、构建成本及按 Change 保存产物的 Git 增量需要通过代表性入口验证。具体编译工具与路径布局属于技术方案，工作台的离线、只读和沙箱边界继续适用。
