# 背景与目标

OpenFolio 需要在当前 Git 仓库内沉淀可复用的 UI 组件，供主应用和后续维护者直接使用。个人拥有的 Shadcn 相关素材可以用于按需接入，但其获取方式、凭据和私人供应商配置不应成为项目协作、构建或运行的前提。

OpenFolio 的原型模块服务于所管理的第三方仓库，读取各项目已交付的原型。本仓库自身的 UI 组件库采用独立预览页面，与被管理项目的原型展示分别维护。

本次在现有 workspace 内新增 UI 库包，集中维护组件导出、公共样式和包内预览页面。目标是形成“个人按需获取素材 → 适配并沉淀到 UI 包 → 主应用消费组件 → 包内预览页展示组件”的完整路径。预览与主应用使用同一份组件实现，组件入库后以项目源码为准，后续维护不依赖素材提供方。

本次同时改造 OpenFolio 的原型模块，使用户能从一个集中入口发现、直接打开当前所选项目的各种页面，不必逐个寻找业务入口、走完前置流程或构造特定状态。总览展示被管理项目 main 中现存页面的最新原型交付；进行中方案的查看和分享继续放在所属 Change 页面。UI 包的独立组件预览与项目原型模块均在本次范围内，各自承担不同的展示职责。

# 范围

## UI 库包与主应用消费

- 在当前仓库新增独立维护的 `packages/ui` 包，纳入现有 workspace 与 Git，对外导出可复用 React 组件、必要的主题样式及类型，并维护依赖声明与使用约定。包名及具体导出组织在技术阶段明确，不要求发布 npm 包或建立独立远程仓库。
- 主应用通过 UI 包提供的入口消费组件。业务数据获取、路由和页面业务逻辑保留在主应用，UI 包提供可由调用方传入内容、状态和交互处理的组件接口。
- 优先复用项目已有组件；接入新素材时按项目设计规范、组件接口与依赖约束适配，避免同时维护同职能的多套基础组件或公共主题定义。
- 主应用和包内预览页直接使用同一份组件实现及适用的主题规则。组件维护以共享源码为准，消费方无需复制组件代码。
- 首批接入覆盖有代表性的实际使用场景，至少一个组件由主应用真正消费，并在包内预览页展示；具体组件在技术阶段结合现有 UI 确定。不将全站组件化或视觉改版纳入本次范围。

## UI 包内独立预览

- UI 包除导出组件外，还维护自己的预览页面及必要的开发、构建和预览命令。维护者按项目指引可独立启动并浏览组件示例，入口无需经过 OpenFolio 工作台。
- 预览页提供清晰的组件名称、查找或导航方式，以及有代表性的状态和交互示例，帮助维护者发现组件并理解用法。基础组件可共用一个页面，按需组织复杂组件示例，不为每个组件建立独立工程。
- 示例直接引用 UI 包的组件，只维护实例参数、状态组合、布局及必要的内存 mock。组件实现或公共样式变化后，通过预览开发服务或重新构建即可查看变化。
- 预览页面采用适合独立浏览的普通前端构建，由 UI 包的工具链处理 React、样式及资源；不要求导出自包含单文件 HTML，也不要求将生成的预览产物作为组件源码手工维护。产物是否由部署流程保存及其位置在技术阶段明确。
- 组件预览无需登记 Change 的 `previews`，不参与原型总览、原型归档或历史版本选择，不使用现有 `packages/prototype` 作为展示载体。
- 预览页只展示组件及示例数据，不依赖配置被管理的仓库、启动 OpenFolio 的 Git 采集服务或调用真实业务接口。
- UI 包的公共导出与预览入口有明确边界，主应用正常引用组件时不引入整个预览页面或演示数据。
- 本次交付可运行、可构建的预览入口和使用指引；实际外部托管或发布另按已有授权处理。

## 被管理项目的页面总览与直接预览

- 原型总览以发现项目页面和直接进入预览为核心。用户可以看到项目已提供预览的页面及代表性场景，通过清晰的名称、内容截图和必要的查找方式定位内容并直接打开，无需知道页面在真实应用中的导航路径。
- 页面示例可呈现不容易从产品首页触达的详情、设置、空状态、异常状态及其他深层场景；演示所需上下文由项目提供的原型和 mock 表达。总览可发现的内容以项目实际交付的预览入口为准。
- 总览只读取被管理项目 main 的当前状态，以 main 中仍存在的原型源码入口识别现存内容，并为每个入口展示已进入 main 的最近一次相关 Change 产物；最新针对每个入口分别判断。
- 页面从 main 的原型入口中移除后不再出现在总览。未更新该入口的后续 Change 不改变展示产物；新产物随相关 Change 进入 main 后替换展示。原型是阶段性参考，源码或产品样式后续变化不强制重建既有原型。
- 未合入 main 的新增、修改或删除不影响总览；总览不聚合开发分支，不提供分支、Change 来源或原型历史版本切换。溯源信息可按需查看，不要求用户先理解 Change、提交或源码路径才能浏览页面。
- 进行中 Change 的原型查看与分享通过 Change 页面的原型模块完成，读取其已推送产物并提供固定产物版本的分享链接，不要求先合入 main。
- 现存入口尚未交付产物、产物缺失或无法读取时提供准确提示，不用其他分支的内容替代当前项目状态。既有项目组件原型可继续按其交付入口查看，本仓库 UI 包的独立预览不由该模块托管。

## 原型源码与 Change 产物管理

- 被管理项目继续在自己的唯一原型包中维护源码、演示入口与构建配置，后续 Change 可以继续修改这些源码。OpenFolio 不将第三方源码编译进自身应用，也不现场安装或构建第三方项目。
- 项目在需要评审、分享或交付时生成自包含 HTML，脚本、样式和必要资源满足既有离线及沙箱约束；若项目的原型使用 React，由项目自身的构建流程完成编译与导出。此机制不要求使用 OpenFolio 的 UI 包或组件预览工具链。
- 新 HTML 产物保存在所属 Change 目录，由工具生成并随交付提交；Change 归档时产物随目录归档。后续 Change 修改同一原型时保存自己的产物，既有 Change 的交付快照保持不变。
- Change 关联保留原型的稳定身份、产物位置、页面或组件类型、视口及生成产物所用源码的确定 Git commit，使产物可追溯到当时源码和构建配置。字段、提交顺序及归档路径规则在技术阶段明确。
- 当前内容由总览展示，各 Change 保存自身交付记录；不新增原型迭代时间线或独立历史管理页面。既有归档产物和固定版本分享链接继续可回看，兼容方式在技术阶段明确。
- 原型构建、关联、校验和归档指引同步上述规则，避免手工编辑生成的 HTML 或为了样式同步重建所有参考原型。

## 个人资源接入与后续维护

- 个人获取资源所用的 skill、连接配置和凭据放在用户级环境。仓库只保存协作维护需要的通用规范、适配后的组件源码及普通项目配置，不要求协作者安装个人工具或持有资源下载凭据；协作使用仍须满足适用授权。
- 个人接入 skill 说明首次使用与后续维护方式：真正需要获取新素材时，检查个人环境，按需初始化最小临时工作区；完成适配后交付项目源码。缺少凭据时说明缺失项，不向项目写入私人配置。临时工作区不作为长期维护对象。
- 项目文档、配置、提交说明和交付产物不主动记录私人供应商名称、registry 命名空间、来源链接或账户信息；依法或依授权必须保留的声明仍须保留。不承诺组件外观或源码无法被辨认来源。
- 已入库组件按普通项目代码维护，只有明确需要获取新素材时才使用个人工具，不主动检查上游更新。
- 项目与个人指引说明资源获取、组件适配、主应用使用、独立预览和后续维护各自的职责。

## 不包含

- 主动检查素材更新、追踪上游版本、自动同步或覆盖已入库组件。
- 私人素材归档数据库、完整素材镜像、复杂的跨机器恢复或按项目管理的长期下载仓库。
- 将 UI 组件库预览集成进 OpenFolio 工作台或现有原型包，或为了组件预览建设 Change 历史管理。
- 在 OpenFolio 内安装、编译或运行第三方项目源码，自动遍历真实应用路由并推定所有页面已具备预览，或为浏览原型连接真实业务后端。
- 原型总览的多分支聚合、跨分支最新版本判定、迭代时间线或历史版本切换。
- 全站视觉重做、全面替换现有组件、与首批复用场景无关的重构。
- 模板商城、公共素材分发、在线编辑服务、npm 发布或独立远程仓库建设。

# 行为变化

- ADDED — `ui-development/component-library`：维护者可在仓库内发现、使用和修改 UI 包导出的组件；主应用通过包入口消费组件及适用的主题规则，普通构建和维护不依赖私人资源访问。
- ADDED — `ui-development/component-preview`：维护者可独立运行 UI 包内的预览页面，查看同一份组件实现的状态、交互和示例；查看组件无需使用 OpenFolio 的原型模块或配置来源仓库。
- ADDED — `ui-development/material-intake`：资源持有者通过个人环境按需获取素材并适配到 UI 包，已入库组件后续按项目代码维护。
- MODIFIED — `project-knowledge/prototype-preview`：总览从跨分支关联汇总改为 main 中现存原型的最新交付展示，以发现项目页面及直接进入预览为核心；原型源码在项目中持续维护，HTML 按 Change 保存并记录源码版本，进行中原型仍在 Change 页面查看和分享。
- REMOVED — `project-knowledge/prototype-preview`：总览中的多分支来源选择和原型历史版本切换；各 Change 自身的交付记录及固定版本分享继续保留。
- MODIFIED — `change-workflow`：原型协作指引明确源码维护、按 Change 导出产物、版本追溯和归档方式，组件库独立预览不使用该关联流程。

# 验收标准

1. 在不提供个人密钥、不安装个人接入 skill 的干净环境中，协作者可按仓库指引安装依赖，构建主应用及 UI 包预览，并修改已入库组件。
2. 至少一个代表性组件由主应用和 UI 包预览直接使用同一份实现；修改共享样式或交互后，两处均可通过各自的正常开发或构建流程体现变化，无需同步组件副本。
3. 不配置被管理仓库、不启动 OpenFolio 工作台，仍能通过明确的命令独立打开预览页面，找到首批组件并操作关键状态。
4. 示例直接使用组件公共入口及适用的主题规则，演示所需数据留在预览侧；主应用消费组件不依赖预览入口、演示数据或真实演示后端。
5. 组件预览的开发、构建和浏览无需生成 Change 原型快照、登记 `previews` 或修改既有原型包；现有原型能力不成为组件库使用的前置条件。
6. 展示一次按需素材接入流程：个人工具检查并准备必要环境，素材适配到 UI 包，项目构建与运行不依赖私人 registry 或服务。凭据缺失时明确反馈，且不会把凭据或私人连接配置写入项目。
7. 审阅新增的受 Git 跟踪文件、依赖与构建产物，确认不包含秘密值、个人工具配置或非必要的私人供应商标识；普通构建、测试和运行不发起私人资源请求。
8. 项目与个人使用指引明确 UI 包的组件导出、主应用接入、预览命令、公共样式及维护方式；已入库组件不主动追踪上游更新。
9. 使用已交付多个页面及深层场景原型的项目，用户能够在原型总览发现、查找并直接打开这些内容，无需经过真实应用的层层入口或操作前置业务流程；预览在声明视口中可查看并操作关键状态。
10. 构造 main 中现存、已删除、已有多个 Change 交付，以及仅在开发分支新增或修改的原型，验证总览只展示 main 的现存入口及各自最近一份相关产物；无关 Change 或文档提交不改变选中产物。
11. 同一原型由两个 Change 先后修改和交付时，共享原型源码继续演进，两份 HTML 分别存放在各自 Change 中，记录正确的源码提交，且后一次交付不改写前一次快照；归档后仍可定位产物。
12. 未合入 main 的 Change 可以通过其页面打开并分享已推送原型，固定链接保持指向分享时的产物；总览无历史列表、版本切换或多分支来源选择，既有归档预览与固定链接的兼容经验证。
13. 源码或产品样式变化但未交付新 HTML 时，既有参考产物仍可查看；缺少产物时显示准确提示。OpenFolio 只读产物，预览时不安装依赖或编译第三方源码，不依赖真实业务接口或持久存储。

# 约束与后续设计事项

- 本次需求不预设具体私人供应商、密钥名称或素材条目。实际获取与提交素材前，应核对持有者授权是否覆盖仓库的可见性、协作方式和交付用途；不能通过省略来源标识替代授权判断。
- 真实私人资源接入验证依赖合法可用的素材授权和个人环境中的凭据。尚未核实这些条件，不视为已接通；这不影响先设计和验证 UI 包与独立预览。
- 技术阶段明确 UI 包的组件边界、首批组件、主题规则的唯一来源、包名与导出方式，以及主应用和预览构建对共享源码与依赖的处理。
- 技术阶段明确预览工具链、启动与构建命令、组件示例的组织方式和构建产物管理，复用适用的项目规范。预览页的普通前端产物无需遵循第三方原型的自包含 HTML 交付协议。
- 技术阶段明确被管理项目 main 中原型入口的发现及稳定身份规则、最近一次相关产物的确定方式、删除和重命名的行为，以及 Change 相对产物路径与源码 commit 的记录和校验方式。不要用 Change 名称、状态排序或无关提交时间冒充产物新旧关系。
- 当前严格关联契约只允许原型包 preview 目录，读取端也按该目录限制资源范围；需同步关联校验、导出工具、工作台读取和归档流程，验证旧记录及固定链接兼容，并核对单个 Change 及项目产物的容量限制。已归档记录不作为新格式的人工重写对象。
- UI 包独立预览和原型模块改造均需交付，展示入口及产物协议分别维护；OpenFolio 作为示例被管理项目时，也按普通项目的原型交付契约提供页面预览，不将 UI 包预览自动当作项目原型。

# 项目依据

- [项目能力边界](../../specs/project-knowledge/spec.md)：OpenFolio 读取已配置中心仓库，展示 Specs、Changes 与原型。
- [既有原型规范](../../specs/project-knowledge/prototype-preview/spec.md)：被管理项目的原型由各项目交付，OpenFolio 只读展示；该机制与本仓库的 UI 包预览分别维护。
- [项目 workspace 配置](../../../../package.json)：当前主应用使用 React，现有 workspace 已包含原型包；UI 包作为独立成员接入。
- 2026-10-09 本次讨论：用户明确要求组件库采用独立预览页面，不与原型混用，也不由 OpenFolio 承接展示；单独增加 UI 库包，同时导出组件并维护预览页面。
- 2026-10-09 本次讨论：用户明确原型模块也需按此前方向改造，核心是让用户直接看到当前项目的各种页面，不必自己寻找入口；总览只展示 main，进行中 Change 通过 Change 页面分享，HTML 按 Change 保存并追溯产出时源码版本。
