# 并发同步后保留有效合入识别

依据 [Requirement](./requirement.md) 与 [Technical](./technical.md)，在独立工作分支交付扫描修复、共同调用回归及使用指引，使普通同步后仍能验证原交付并安全续接清理。

## T1：同步合并后持续识别并验证原始交付

交付：在共用索引扫描中沿普通同步的其他父路径继续、在 Change 候选处排除来源路径，并按提交身份去重；复用现有候选验证及结果结构。递增索引版本，使相同集成 tip 的旧缓存重新计算；同步 skill 的集成识别及主工作区同步说明。配套回归覆盖所有受影响入口与失败路径。

验收：

- 原第一父路径和普通同步其他父路径上的有效 M 均可识别；多层同步及多路径到达不产生重复记录。来源内部的普通标记与内部合并不进入候选，无关分支不参与查找。
- 不同提交重复标记、无效父结构、被修改的归档、一次引入多个归档及所需对象不可读都按协议诊断，不被放宽为成功。
- 相同 tip 的旧索引在刷新时重新扫描。CLI 验证与清理、工作台交付及固定差异、发布 PR 检查返回一致的原 M，来源删除后仍能冷读取原交付。
- 新提交、来源依赖、工作区脏文件或忽略文件、未确认占用与远端 tip 竞争等删除保护仍生效；合入结果与逐对象清理结果分别报告。

验证：用临时 Git 仓库重现以上拓扑及保护场景，补入现有集成测试；对索引旧版本、相同 tip 刷新单独回归。运行相关集成与发布校验测试，再运行 `npm test`、skill 与 Setup 的自包含测试、`npm run typecheck`、`npm run format:check` 及生产构建。正式实现的证据记录到 Execution，并与任务完成状态一起提交推送。

## 整体验证与交付

T1 验证通过后，medium 独立评审核对完整差异、需求及失败路径；所发现问题修正并复验后记录整体验证结果。向用户提供验证证据与限制，按现有流程等待人工验收。验收后同步当前 Specs 的合入识别语义，并将完整 Change 归档。

技术方案与计划推送后建立同一条 Draft PR，后续交付沿用该 PR。归档及 CI 通过、获得合入授权后，普通 merge 到最新 `develop` 并核实远端 M；不重新合入 `skill-auto-update`，也不改写任何已有归档或已推送历史。

合入后从主工作区 `develop` 更新 `11117` 长期服务，构建前停止占用 `.next` 的实例，保留持久数据与密钥。冒烟核对主页、独立测试会话、仓库读取及工作台对 `skill-auto-update` 的原合入记录；登录使用 `withSmokeSession`，并将退出后的匿名状态与无可见绑定检查作为成功条件。

使用已交付的新扫描器重新验证 `skill-auto-update` 的原 M `11a86db`，核对其来源 tip、独有配置、构建产物及实际占用后，继续此前已授权的清理。两个 Change 的来源均按远端分支、worktree、本地分支顺序处理；保留已合并校验及条件删除，遇到新增成果或占用则暂留并报告。发布到 `main` 仍需用户另行要求。
