# 并发同步后保留有效合入识别

## 目标

有效的 Change PR 合入集成分支后，即使后续并发同步改变了 first-parent 路径，CLI 与工作台仍能识别原合入事实，并在完成交付验证后继续安全清理来源。

本次由用户在确认问题原因后提出“优化一下吧”。这是对共享合入协议的 medium 修复：实现集中在合入索引，但识别结果同时供 CLI、工作台及发布 CI 使用，涉及有效合入记录的判定语义。

## 问题与范围

`skill-auto-update` 的 [PR #22](https://github.com/iTgo-lyq/open-folio/pull/22) 已合入 `develop`，合并提交及归档内容均通过校验。随后同步提交将原合并提交放在第二父路径中，现有扫描器只读取第一父路径，因而报告没有合入记录，并阻止清理。完整提交图中仍保留原交付，服务也已部署成功；具体证据见 [Research](./research.md)。

修复共用的识别逻辑，使正常同步不会令已存在的有效合入记录消失。CLI 验证与清理、工作台交付状态与合入差异、发布 CI 应使用一致的结果；差异仍比较原合并提交与其第一父提交，不把后续同步提交当作本次交付。

保留正式交付的验证：唯一合法 Change 标记、恰有两个父提交、首次只引入目标有效归档、无同 id 活动入口、合并提交与来源的归档子树一致。普通工作提交、正文提及、未推送或不属于所选集成历史的提交不能成为合入凭据；重复、歧义及对象不可读应明确诊断。

来源清理仍须核实远端合入、原始交付、项目服务、来源归属、未合入的新提交、其他活动或取消入口的依赖以及工作区文件和占用。不能因扩大查找范围而跳过已有删除保护。

本次同步相关 skill 指引与既有缓存的重新计算方式，不新增常驻同步程序，不重写已推送历史，不修改已有 Change 归档。修复验收并合入后，重新验证 `skill-auto-update`，继续处理已获授权而暂留的源分支和工作区清理。

## 验收

1. 重现本次“PR 合入后，本地已有提交再合并远端”的图结构，CLI 和工作台均找到原合并提交；其时间、来源、归档位置及差异边界保持准确。源分支删除后仍可从集成历史读取。
2. 原 first-parent 路径上的正常合入继续识别；同一有效记录通过多条路径可达时不会被计为重复。仅存在于无关分支或尚未交付的工作分支的记录不能被当作集成交付。
3. 无效父结构、重复或歧义标记、归档内容被改变、一次引入多个归档以及缺失 Git 对象等情况不被误报为验证通过。
4. 已缓存的同一集成 tip 能使用新规则重新生成索引；CLI、工作台和发布 CI 不因旧缓存得出互相矛盾的结果。
5. 验证失败时保留来源；清理仍拒绝删除含新提交、未保存文件、独有配置或仍在使用的来源。对已部署交付的验证与来源清理分别报告，不再把清理受阻表述成 PR 合入失败。
