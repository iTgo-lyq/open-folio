# 交付计划

## 实施前置

需求已确认。Technical 与本 Plan 一并确认后才能执行；UI 还需先取得用户对 Astra 原型的明确验收。原型复用现有 quiet-changes，发布固定版本并关联到本 Change，列表、看板和详情采用同一“暂缓”语义。原型绘制不等于已获对应实现授权。

## T1：未实际移交的需求可持续记录，已移交需求保持正确归属

交付一个共享的来源判定，使工作台读取、状态命令、locate / prepare / handoff 和 pre-commit 对预填分支、实际目标与异常来源给出一致结果；按技术方案保留有效集中规划，真实目标优先，不把查询错误或已观察到的来源丢失误判为尚未启动。显式 handoff 沿用预填名称，不产生空登记提交，普通及父子移交保持安全发布和失败重试。

补充“只记录、暂不启动”的 Agent 工作流约定：允许空任务及继续澄清，保留 pause；不自动准备工作区、计划或实施。沿用现有 JSON 状态、暂停恢复及确认机制；源码分支和技能版本按项目要求同步，不另设持久化移交标记。

验收与验证：

- 用临时 Git 仓库验证未创建目标、无关同名分支、继承记录、实际所属记录、仅远端已发布、来源被删除和查询失败等场景；各入口的实际来源、可写性与诊断符合 Technical。
- 暂缓且无任务的需求可以持续澄清，不能因更新文档自行 resume、execute 或创建工作区。实际移交的 requirement 仍能在所属分支澄清，集中误提交仍拒绝。
- 运行真实 hook 验证增删、重命名、改写 branch、部分提交、普通与子项首次登记，以及失败现场保留；回归原有工作区、状态命令、父子集成、取消与归档读取行为。

## T2：暂缓在工作台独立呈现并完成场景验证

按用户确认的 Astra 原型完成现有处理状态的展示：列表和看板单独分组“暂缓”，详情说明一致，等待确认、真实阻塞和推进中各保留含义，任务阻塞原因继续可查看。不增加新持久化状态、编辑流程或页面结构。

同时按用户补充要求对齐正式列表阶段列的进度圆点及名称，以及看板按当前处理状态或阶段分组的呈现。

验收与验证：

- 使用真实的目录分组测试验证 pause 不再混入受阻或推进中，暂停与任务阻塞同时存在时仍保留任务原因；继续覆盖默认视图、无分组和保存视图行为。
- 在桌面、窄屏、浅色与深色的适用场景核对列表、看板、详情以及恢复后分类；对照已确认原型记录一致性与未验证项。
- 浏览器复用常驻 Chrome CDP，只关闭本任务创建的页面；真实登录使用 withSmokeSession 并核验清理。运行相称的回归、类型检查和构建，记录证据。

两项按默认编号串行执行，T1 完成提交推送后进入 T2；不另设并行安排。

## 验收与交付

完成后进行 medium 的独立评审，核对全部需求、原型还原及验证证据，提交推送可审阅结果并等待用户验收。收到实际验收后同步 Specs、归档并按 PR 集成协议交付；合并仍遵循实际授权。集成到 develop 后从主工作区更新长期服务、执行与本次变更相称的冒烟，再清理已交付来源。不得在等待需求、方案或原型确认期间提前改正式实现。
