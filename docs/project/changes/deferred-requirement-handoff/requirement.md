# 区分需求暂缓与实际分支移交

## 目标

用户明确要求只记录需求、短期不启动时，保存需求和暂缓意图，允许日后继续澄清，不把暂缓显示为受阻，也不自动安排实施。需求中提前填写工作分支名称，不能直接视为已完成移交。

本次延续 `transferred-change-commit-guard`：修正仅凭 branch 文本拒绝集中需求修改的判定，并统一工作台读取、状态命令和工作区定位的实际来源判断。前序归档保持只读。

## 范围与行为

### 只记录需求，暂不启动

- 沿用现有 `status: active`、`stage: requirement` 和 `waitingFor.kind: pause` 表达暂缓，摘要保存用户的暂缓原因或恢复条件，不新增状态枚举或重复状态字段。
- Agent 收到明确的“只记录、暂不启动”指令时，只保存现有目标、已知范围、未决问题与暂缓意图；不为补齐执行材料而自动创建任务、Plan、分支、worktree 或 Draft PR，不自行进入 execution。
- 后续可以在暂缓期间继续补充需求与澄清记录。记录补充不自动解除 pause，不视为允许开发；用户明确恢复推进后才解除暂缓，并继续遵循原有确认和移交规则。
- 工作台按处理状态分组时，将 pause 单独展示为“暂缓”，不归入“受阻”或“推进中”；详情中的等待说明也使用一致语义。等待确认、等待依赖和真实受阻任务保留各自的既有含义，任务阻塞原因仍可查看。

### 以实际来源判断移交

- branch 字段可以出现提前填写的目标名称，但名称本身不构成已移交证据。不新增另一套计划分支字段；正常新建仍优先将 branch 设为当前集成分支，在实际 handoff 时登记目标。
- 已有命名分支、可用 worktree 或可读取的已推送工作分支需结合其 Change 归属核实，不能把无关分支、继承的集中规划副本当成已完成移交。阶段不是移交依据：实际移交后即使仍处于 requirement，也应在所属工作区继续澄清。
- 仅有预填名称、没有可核实的目标分支或工作区时，需求材料继续从集成分支读取和记录。工作台能展示该需求；状态命令可补充需求与暂缓记录；locate 如实报告尚无实际工作区；不得自动准备 worktree 或启动执行。
- 真正执行 handoff 时沿用预填目标并核实实际基线；按原有条件创建或复用分支和工作区，成功发布后才视为完成移交。失败重试保留文件、暂存区和已创建的成果，不覆盖用户现场。
- 若目标实际存在且归属匹配，继续使用目标最新记录，拒绝在集成分支提交该 Change 的文档修改；本地没有对应 worktree 不能直接推断远端尚未移交。取消、完成归档及父子 Change 仍遵循已有归属与交付规则。
- 远端明确不存在与网络、认证、权限或读取错误分别处理；后者保留诊断，不当作不存在，也不静默回退成可写的集中规划副本。只读查询继续明确来源新鲜度。

### 提交门禁

- 沿用前序 hook 的实际提交暂存区检查，覆盖 Change 目录内增删、正文、状态、重命名和部分提交；在有本地可核实的实际移交证据时才拒绝，单独填写 branch 不再足以触发拒绝。
- hook 保持只读本地 Git、不联网；不会宣称能实时验证远端存在或不存在。读取工具和联网流程命令按已有入口定向核实远端，不增加全分支扫描或另一份持久化移交状态。
- 没有同步 Change 文档的实现提交继续沿前序约定放行；首次正常和子项登记、所属工作/任务分支及正常合并继续放行。失败时提供实际目标线索并保留现场。

## 验收

- 只记录需求时可保持空任务，保存 pause；后续补充需求不创建工作区、不进入实施、不自动解除 pause。列表/看板处理状态将其归为“暂缓”，详情可看到暂缓说明，真实阻塞任务的原因仍保留。
- 在 branch 已预填且目标尚未实际创建的场景，集中需求可展示、定位、补充状态并提交；不再仅因目标名称而报错或拒绝。
- 实际移交但仍在需求阶段时，目标工作区可继续澄清；集成分支误提交仍被阻止。仅远端已有目标、当前机器未创建 worktree 的情况不会被误判为尚未移交。
- 已存在的无关分支或继承规划副本不伪造移交事实；远端缺失、读取错误及陈旧缓存分别按实际来源报告。
- 实际 handoff、状态命令、工作台读取与 hook 对上述场景的判断一致；普通与父子移交、失败重试、取消冻结、归档集成和部分提交回归通过。
- 按实际 UI 范围验证列表与看板分组、详情说明和基本窄屏展示；涉及真实登录时使用仓库规定的 withSmokeSession，并核验退出清理。实现集成并验证后更新开发机长期服务。
