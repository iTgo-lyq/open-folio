# 读取子模块中的固定版本原型

## 目标与背景

项目使用主仓库管理 SpecTrail、Specs 和 Change，前端通过 Git submodule 纳入主仓库。原型需要放在前端仓库中，以复用已有组件、主题和构建工具，并在主项目的 OpenFolio 工作台统一展示和关联 Change。

当前 OpenFolio 只从主仓库对象库读取原型清单与 Git HTML；SpecTrail 发布工具也直接在主仓库检查源码文件和 sourceCommit，无法穿过 gitlink 读取子仓库。仅允许配置更深的 packagePath 不能解决版本读取与历史追溯问题。

本 Change 为 medium：原型来源、发布登记和历史校验共享的契约需要协同适配。创建前已确认启动范围，见需求类 Q1；该确认不代替完整需求与后续方案确认。

## 范围与行为

### 项目配置和当前原型

- SpecTrail 配置、Change 及归档继续由主仓库管理；前端子仓库无需另行维护一套 SpecTrail 或作为独立 OpenFolio 项目接入。
- 主仓库 `workflow.json.prototype.packagePath` 支持指向已记录的 submodule 根目录或内部的原型包，例如子模块为 `frontend` 时配置 `frontend/packages/prototype`。
- 当前原型以主项目配置的集成分支提交为基线，从该提交记录的子模块路径、仓库地址和 gitlink commit 读取包内 `prototype.json`、源码及适用的 Git 产物。历史读取使用对应主仓库提交中的记录。
- 子模块的工作目录当前检出版本、默认分支或最新分支不替代 gitlink commit。子仓库新增提交、移动分支或本地切换版本，都不应单独改变主项目当前原型。
- 包内源码路径与 Git 产物路径须有明确的仓库归属及解析规则，兼顾前端仓库独立维护清单、复用组件的场景。具体字段与路径表示在技术方案中确定，并保证可固定追溯。
- 当前总览、原型详情、预览和截图沿用主项目入口；入口 id 仍在主项目内唯一。保持现有入口数量、文件大小、常规文件及自包含 Git HTML 等限制。

### Change 关联与历史固定

- 主仓库 Change 可以关联子模块原型，保留当次显示信息、设备或视口及固定产物；后续当前清单变化不覆盖历史关联。
- 追溯信息能够确定主仓库来源提交、子模块路径、子仓库身份及对应的源码提交，避免把子仓库 commit 误当作主仓库对象。
- 活动 Change 从其已推送版本读取；已合入归档继续遵守现有固定合并提交的定位规则。Git HTML 继续按 Change 快照归档，hosted 继续保留固定版本、地址、摘要和截图。
- 主仓库后续升级或迁移子模块、子仓库分支移动及来源分支清理，均不得把历史原型替换成新版本。已准备的公开原型继续独立保留，匿名读取不触发仓库获取。

### SpecTrail 发布与校验

- 适配已有接入检查、构建发布准备、结果登记、Change 关联、归档和合入前来源校验，覆盖 hosted 与 Git 兜底两种模式。
- 发布前检查实际构建源码与主仓库记录的子模块版本相符；源码或依赖存在未提交变更、子模块检出版本与 gitlink 不符时，给出可操作错误，不登记为固定交付。
- 当前清单写在子仓库，Change 记录写在主仓库。发布工具应明确两个仓库的提交顺序与恢复方式；登记失败保留原固定引用，不宣称两库已经完成原子提交，不自动切换分支、提交或推送子仓库。
- 暂存校验、发布校验和版本追溯读取正确仓库中的对象，不能仅因主仓库不包含子仓库 commit 而误报，也不能仅验证父提交存在就宣称子仓库源码可用。
- 更新公开分发的 SpecTrail 使用说明及适用的示例；按仓库约定同步 OpenFolio 与 SpecTrail 版本。

### 权限、失败提示与兼容

- 读取子仓库沿用当前用户连接及平台支持的仓库访问能力。主仓库可读不代表子仓库可读，缓存不能绕过子仓库权限检查，也不把主仓库凭据发送到任意子模块地址。
- 对子仓库不存在或当前账号无权访问、gitlink 指定版本不可获取、子模块配置缺失或非法、清单或源码文件缺失等情况，给出明确原因及必要的路径、版本线索；平台无法区分不存在与无权限时如实合并提示。
- 错误不能显示为“尚未接入”或“尚未关联”的正常空态，也不能回退到子仓库最新分支。其他主仓库 Specs、Change 和正常原型仍可阅读。
- 已发布 hosted 或独立公开版本的保留规则继续有效；源码不可读时须明确追溯不可用，不能把固定产物存在当作源码验证成功。
- 保持现有普通目录原型、已发布引用和历史 Change 可读；不要求批量改写历史记录。

## 验收

| 场景 | 预期结果 |
| --- | --- |
| 主仓库配置 `frontend/packages/prototype`，gitlink 指向子仓库 A | 主项目读取 A 的清单和源码，显示其原型；子仓库无需接入 SpecTrail |
| 原型包位于子模块根目录 | 可以解析清单、源码与适用产物，路径归属没有歧义 |
| 子仓库分支推进到 B，主仓库仍记录 A | 刷新后仍读取 A；本地子模块检出 B 也不改变远端读取结果 |
| 主仓库提交更新 gitlink 到 B | 当前总览读取 B；以旧主仓库提交准备或查看的原型仍固定到 A |
| 主仓库 Change 关联 A，随后当前清单更新或删除入口 | Change 仍保留自己的标题、视口和固定产物，不借用最新清单替换 |
| 子模块 hosted 和 Git 兜底分别发布、关联、归档 | 来源对象在正确仓库校验，Git 快照留在主仓库 Change 内；归档合入后可固定读取 |
| 子模块检出版本不符或存在未提交源码与依赖 | 发布被明确拒绝，原引用保持；修正源码与父仓库版本记录后可重试 |
| 发布上传成功但引用登记中断 | 可以按说明恢复或重试，不覆盖后续用户编辑，不误报两库均已提交 |
| 子仓库无权限、不存在、gitlink 版本不可用或配置非法 | 明确提示受影响的来源和原因，不读取最新分支代替；主仓库文档正常可读 |
| 子仓库权限被撤销，已有个人缓存 | 后续私有来源读取不能绕过权限；已发布公开产物沿用既有保留规则 |
| hosted 产物可访问但子仓库源码不可用 | 固定产物保留，明确提示源码无法追溯，不将源码校验记为通过 |
| 原有普通目录原型和历史记录 | 保持现有读取、发布、Change 关联与归档行为，无强制数据迁移 |

验证使用真实 Git 父子仓库夹具覆盖版本固定、权限失败与发布恢复，结合现有服务测试及适用的浏览器冒烟。交付时提供验收证据，medium Change 由用户最终验收。
