# 通过 PR 管理 Change 集成与正式版本发布

## 目标与现状

让每个 Change 的集成交付保留可审阅的 PR，并在发布 PR 中集中说明本次版本、功能和修复，留下正式变更记录。用户在工作台能够识别交付停留在待集成还是待发布，并打开对应 PR 查看实际进展。

**范围澄清（2026-10-22）：版本变更说明由发布 PR 承载。** 用户未要求实现独立 changelog 管理；本次不新增或自动维护 `CHANGELOG.md`，不新增 GitHub Release / tag 管理、读取或多份清单一致性校验。

当前配置以 `collaborationBranch` 指定集中入口和预发布基线，以 `protectedBranches` 同时表达保护约束与正式发布去向。Change 归档后，集成脚本直接生成合并提交并推送协作分支；工作台已有 Git 合入差异，但没有 PR 关联和正式版本进度。现状依据见 [Change 状态维护](../../specs/change-workflow/spec.md#归档后的去向)与 [Change 追踪](../../specs/project-knowledge/change-tracking/spec.md#合入变更)。

本次暂按 medium：修改共享配置契约，并联动 SpecTrail 流程、托管平台读取与工作台交付展示；技术调查后根据实际实现范围复核规模。与现有分享、前端样式 Change 没有必需的交付依赖，重叠展示区域在实施时协调。

## 分支职责与集中入口

项目必须显式配置一个集成分支和一个发布分支，字段分别为 `integrationBranch` 和 `releaseBranch`。两者为不同的合法分支名；推荐名称为 `develop` 与 `main`，流程不得硬编码这两个名称，也不以仓库默认分支推断发布目标。

```json
{
  "integrationBranch": "develop",
  "releaseBranch": "main"
}
```

这是目标字段示意；配置协议版本及其余既有字段的契约在技术方案中确定。

| 分支角色 | 职责                                                                                        |
| -------- | ------------------------------------------------------------------------------------------- |
| 集成分支 | Change 集中规划与分支登记、Change 交付 PR 的目标、当前集成 Specs 和原型来源、预发布验证基线 |
| 发布分支 | 正式版本发布 PR 的目标、正式发布基线                                                        |

新的角色字段替代 `collaborationBranch` / `protectedBranches` 的职责表达。平台保护规则是写入约束，不用于推断分支角色。

**需求取舍 Q3：规划和分支登记继续直接提交集成分支。** 工作台仍从集成分支的集中 Change 入口发现记录，再按登记读取所属工作分支；PR 只用于补充已知 Change 的交付事实，不作为发现 Change 的入口，不扫描所有分支或所有打开的 PR 来建立 Change 列表。直接规划提交不能夹带产品实现、Change 集成交付或正式发布。

主工作区继续使用集成分支，Change 实现在独立工作区推进。默认通过 PR 提交指下述两条交付路径，不把它扩展为所有规划文档必须经过 PR，也不据此一刀切禁止集成分支直推。

## 两条 PR 交付路径

| 路径                       | 交付单位                      | PR 内容与完成结果                                                                       |
| -------------------------- | ----------------------------- | --------------------------------------------------------------------------------------- |
| Change 工作分支 → 集成分支 | 一个内聚的 Change             | 目标、交付行为、验证证据、关联 Change；合入后形成集成交付与归档历史                     |
| 集成成果 → 发布分支        | 一个正式版本，包含一批 Change | 版本与范围、功能和修复、升级影响、包含的 Change / PR、整体验证；PR 留存本次版本变更说明 |

两条路径默认创建或复用 PR，不能因 PR 创建失败、权限不足或平台规则阻止合入而自动退回直接推送。显式例外只按用户当次授权处理，并如实保留实际交付事实，不补造 PR 历史。

Change PR 可以在实现中提前创建为 Draft，后续持续更新；已有对应 PR 时复用。准备交付时，PR 中包含最终实现、验证依据、Specs 及归档材料；PR 合并保留提交历史，并延续现有整体合入差异和固定原型的追溯能力。

**补充确认（2026-10-22）：未归档不得合入，同时提供 Agent 规则与 CI 检查。** Agent 合入前必须通过归档预检；CI 检查 PR 当前源提交的有效归档及正文关联标记，未归档、验收未完成或返修恢复活动状态均失败。发布 PR 只核对包含清单，不要求集成分支的其他规划归档。首次接入在 Setup 推荐配置 CI 和必需状态检查，保留规划登记直推的权限安排，并如实区分 CI 结果与平台强制规则。

验收通过、归档材料准备好不表示已合入。PR 合入前发现问题，应允许在同一 Change 中返修、重新验证和整理归档；PR 成功合入集成分支后，归档作为只读历史冻结，后续需求或返修按新 Change 处理。集成成功并完成项目验证后再清理来源分支与工作区。

Change 完成集成后可以结束开发与验收流程；后续等待正式发布不使它重新变为未完成，也不阻塞已获得该集成交付的下游 Change。正式发布不要求逐个重写已归档的 `change.json`。

创建 PR、批准合入和实际合入分别依据已有授权与托管平台规则。用户只要求准备 PR 时不继续合并；用户已经明确授权交付或发布时沿用其范围，不增加重复确认。普通 Change 关闭不自动触发正式发布。

## PR 自动关联与追溯

**需求取舍 Q1：自动匹配，不在 `change.json` 保存 PR URL、编号或动态 PR 状态。** Change 的需求、任务、验收事实继续由 `change.json` 表达；PR 生命周期取自托管平台，是否合入目标分支结合 Git 核实。

- Agent 创建 Change PR 时，在正文写入稳定的 Change 标识。工作台以仓库身份、Change 标识、实际源分支及配置的目标分支核实关联，不能仅按标题相似、分支命名或最新更新时间猜测。具体标记格式和查询方式在技术方案中确定。
- 工作台为已知 Change 展示匹配 PR 的编号、可点击链接和真实状态；链接来自平台返回值。PR 改标题、源分支在合入后删除，不应丢失已有交付关联。
- PR 关闭未合入、重新打开、关闭后另建 PR 时，保留可核实的历史，并区分当前待处理 PR 与历史 PR。多个相互冲突的候选不能任取一个；缺失关联标记或无法唯一判定时明确提示。
- 发布 PR 应明确列出所包含的 Change 及其交付 PR，支持一个发布 PR 对应多个 Change。工作台能够从 Change 追溯相关发布 PR，展示其中声明的版本和合入状态；不扩展为正式版本注册或首次发版认定。
- 查询按已登记的 Change 范围收敛，可使用缓存和增量读取；不把分页未完成、权限不足、限流或网络失败解释为“没有 PR”“尚未发布”。展示最近成功结果时说明其新鲜度和失败原因。

公开版本继续使用现有 GitHub.com Provider。读取 PR 所需的权限应在接入说明与缺权反馈中表达，工作台仍为只读，不要求写权限或提供合并按钮。GitHub 的 PR 列表接口支持源 / 目标分支筛选，私有资源的细粒度 Token 需 `Pull requests: read`。参考 [PR 官方接口](https://docs.github.com/en/rest/pulls/pulls#list-pull-requests)（2026-10-21 读取）。缺少这些信息时，既有工程文档与有效 Git 合入记录仍可阅读。

## 正式版本发布与内容整理

用户明确要求发布正式版本时，Agent 依据已配置的发布分支准备或推进发布 PR。默认比较发布分支当前基线与选定集成提交中的实际变化；结合已有发布 PR 及项目版本约定整理本次范围，用户指定版本或范围时沿用。首次发布明确比较基线，不凭历史归档数量臆造发布内容。

发布审阅期间固定本次范围。如果集成分支继续接收新交付，按需使用短期发布准备分支承载候选；它不构成第三个必填长期分支。候选新增实际交付时重新整理说明与验证，不能悄悄扩大已经审阅的版本范围。准备期间产生的实质修正按正常 Change 流程处理。

发布 PR 正文是本次版本说明的载体。Agent 阅读范围内的 Change、交付 PR、实现差异和验证证据，集中整理面向用户的变化；各 Change 保留自身交付事实，不另维护重复的版本摘要。

### 发布内容整理提示词

下列内容作为后续写入 SpecTrail 的发布行为要求，具体放置形式在技术方案中确定：

> 用户要求发布正式版本时，先读取 integrationBranch 和 releaseBranch、已有发布 PR、项目版本约定及本次授权范围，固定比较基线和发布候选。核对实际差异、对应 Change、交付 PR 和验证证据；首发时明确比较边界。
>
> 根据最终交付行为整理发布说明：按需要描述新增功能、改进、修复、废弃或移除、安全相关变化及升级注意事项，不保留空分类。把多个提交或相关 Change 归并为用户能够理解的结果，排除过程性提交、重复描述、未完成工作和发布前已撤回内容；实际移除或回退已发布能力时，如实说明影响。每项重要变化能够追溯到相关 Change 或 PR，不直接拼接提交标题，不编造效果、兼容承诺或验证结论。
>
> 沿用用户指定的版本号；未指定时按项目版本规则提出有依据的版本建议，不能默默另定一套版本体系。创建或更新发布 PR，写清版本与发布范围、核心功能变化、升级影响、包含的 Change / PR、验证结果和已知限制。版本或范围仍有会影响发布的未决事项时，先提供具体候选供确认。
>
> 区分准备 PR 与批准合入的授权。遵循已有授权和平台检查合入发布 PR，核实远端结果；失败或结果不确定时先核实已有 PR，不重复创建或回退直推。如实报告 PR 合入进度，部署结果单独报告，不把合入等同于服务上线。

发布 PR 的可审阅内容至少包含：版本号与比较范围；面向用户的变化；兼容性、配置或迁移影响（如适用）；包含的 Change 和 PR；真实验证结果与限制。

本次交付跟踪到“已合入发布分支”，不要求接入 tag、GitHub Release 或部署系统来判断另一个“已发布”阶段。部署沿用项目约定，本次不新增部署平台或常驻发布服务。

## 工作台的交付标签

开发阶段继续表达需求、技术、计划、执行和验收；交付进度作为独立的小阶段展示。阶段位置和 PR 状态不能互相冒充，不以手填标签作为交付事实来源。

| 标签 / 结果    | 判定与显示                                                                                                                                       |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| 待集成         | Change 已具备交付条件，交付 PR 尚未合入集成分支；显示 PR 链接及草稿、打开、关闭未合入等实际状态。没有找到 PR 时说明缺少关联，不能暗示已经发起 PR |
| 待发布         | Change 已集成，尚未进入正式发布分支；显示可关联的发布 PR，没有发布 PR 时明确尚未发起                                                             |
| 已合入发布分支 | 发布 PR 明确包含该 Change，且合并结果已核实；显示 PR 与其中声明的版本，不表示服务已部署                                                          |

实现中的 Draft PR 可以提前显示链接，但不能仅凭存在 PR 就把 Change 从执行阶段移到待集成。PR 关闭未合入不等于 Change 取消，仍展示其实际开发状态及交付问题。信息不足、关联冲突或无法读取时显示“交付状态待核实”及原因，保留已经核实的事实。

标签至少出现在 Change 列表、相关卡片和详情中，并提供待集成 / 待发布的便捷筛选或入口。已归档但待发布的 Change 仍能从待发布入口找到，不要求用户逐个进入历史归档查找；筛选不改写原始开发状态，详情可查看 Change PR、发布 PR 和版本信息。

发布 PR 的包含清单由 Agent 根据实际差异整理；已撤回的内容从本次清单移除，原因在正文说明，不能仅凭 Git 祖先关系判定本次包含。后续回退不抹去过去发布 PR 的合入历史。旧记录没有可靠的 PR 依据时如实显示缺少关联，不自动回填链接。

## 现有项目与范围边界

**需求取舍 Q2：旧项目升级由用户自行指导。** 本次只交付新配置契约及对应功能，不设计旧字段兼容、自动迁移、历史记录批量修补或升级提示词。本轮需求整理仍使用现行语义命令和现有配置，不提前替换工作区配置。

本次包含 SpecTrail 的两类 PR 流程、发布 PR 内容整理、PR 自动关联及工作台交付标签。Skill 自身的版本发布、分发流程升级与自动更新明确排除；当前已有的分发同步也不因本次需求整理改变。

Skill 修改保持措辞精炼：直接替换失效规则，合并重复说明；主入口只保留分支职责、交付约定与必要引用，发布细节按需读取，不把需求全文或通用检查清单复制进 skill。

不新增独立的 Release 需求审批生命周期，不为每次普通发布强制再建一个产品 Change；仅当发布准备产生新的实质需求或实现变化时，按正常 Change 规则处理。工作台保持只读；版本发布与 PR 写操作由执行任务的 Agent 使用其授权完成。

## 验收标准

1. 项目要求配置合法且不同的 `integrationBranch` 与 `releaseBranch`，自定义名称能够贯穿接入、Change 集成、发布及展示；不再用默认分支或保护分支列表推断正式发布目标。
2. 规划与分支登记仍直接提交集成分支，工作台从集中入口发现 Change。产品交付默认通过 Change PR 合入集成分支，正式版本默认通过发布 PR 合入发布分支；失败不静默退回直推。
3. 创建 PR 时附稳定关联标识。工作台自动展示关联链接和真实状态，`change.json` 不新增 URL、编号或 PR 状态；改标题、合入后删分支、关闭重开、关闭后重建及多个候选均有明确结果。
4. 同一 Change 在 PR 合入前可完成返修、复验和重新整理归档，合入后归档冻结。集成后的 Change 无需等待发版即可供下游使用，也不因发布而改写归档。
5. 用户要求正式发布时，Agent 按上述提示词整理实际变化、发布范围、版本、升级影响、关联 Change / PR 与验证证据，形成可审阅发布 PR；不使用简单提交标题拼接，不混入未完成或已撤回交付。
6. 发布 PR 留存版本说明与包含的 Change / PR；准备 PR 与合入遵循实际授权。首次发布、候选变化和合入失败均如实报告，不要求生成 CHANGELOG.md、tag 或 GitHub Release。
7. 工作台展示待集成、待发布及已合入发布分支，能够直接找到已归档但待发布的 Change，并查看关联 PR。开发中的 Draft、关闭未合入和实际合入均能区分，不引入依赖外部发布物的额外阶段。
8. PR 缺权、网络失败、限流或关联歧义不被当成“没有记录”或“已合入”，不遮蔽既有文档和有效 Git 合入证据；读取权限和结果新鲜度有清楚反馈。
9. 已撤回的交付不列入本次发布 PR 的包含清单，既往 PR 合入历史保留；关联不能只凭 Git 祖先关系推断，没有可靠关联的旧记录不补造链接。
10. 本次不包含独立 changelog 管理、GitHub Release / tag 管理、skill 发布、自动升级、旧项目迁移与升级提示词；保留既有预发布服务、原型历史和用户数据，PR 合入与部署结果分别报告。
11. Skill 修改明确且精炼，没有并存的旧合入规则、重复发布提示词或新增的通用审批层。
12. 未归档的 Change PR 无法通过归档 CI；归档推送后重新校验，正文变更也重跑。检查复用既有状态契约，不增加字段、后台服务或另一套验收状态。Setup 提供可复用接入方式及必需状态检查建议，说明规划直推和绕过权限的边界。
