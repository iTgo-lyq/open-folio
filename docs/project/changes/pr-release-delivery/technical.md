## 双分支配置与读取入口

`workflow.json` 升为 `schemaVersion: 3`，必填合法且不同的 `integrationBranch`、`releaseBranch`；移除 `collaborationBranch`、`protectedBranches`。保留既有 prototype、服务地址等无关配置，Change schema 仍为 1。共享校验器、Setup、CLI、Provider、仓库发现、API 和展示统一使用新角色名称，不双读旧 workflow。

本仓库目标仍为集成 `develop`、发布 `main`，实现和样例使用同一新契约；测试必须覆盖自定义名称。平台保护规则不写成发布目标列表，也不自动调整。工作分支不得使用这两个长期分支名，主工作区仍在集成分支。

工作台从选定的集成分支读取配置与集中 Change 登记，再读取登记来源；额外定向读取配置的发布分支及候选版本的精确 tag，不枚举其他分支来发现 Change。发布分支或版本对象暂不可读时，交付信息局部降级，已有集成文档仍可阅读。规划与分支登记继续直推集成分支；hook 保持本地结构校验，不联网检查 PR，也不禁止所有集成分支提交。

发现缓存和快照版本更新后按原策略重建。账号、凭据、设备会话、公开原型和用户偏好不重置；个人存储中既有偏好键在边界映射为运行时 `integrationBranch`，不因此增加旧 workflow 兼容。现有项目升级由用户处理，不编写迁移工具或升级提示词。

## Change PR 与归档返修

### 关联与合入协议

Change PR 的末尾独立段落保留唯一标记，标题可自由表达交付行为：

```text
SpecTrail-Change: pr-release-delivery
```

精确解析末尾元数据段，不从标题、代码示例或普通正文提及建立关联。核对稳定仓库身份、登记源分支、`integrationBranch` 和合法 Change id；同仓库分支是本次支持范围。PR 已合入时还核对平台合并提交与 Git 中的有效 M；未合入 PR 的 `merge_commit_sha` 不能作为合入证据。[GitHub PR 接口](https://docs.github.com/en/rest/pulls/pulls#list-pull-requests)

沿用现有 M 协议：恰有两个父提交，末尾唯一同名标记；M 位于集成分支主链，只首次引入该 Change 的有效归档，且归档子树与第二父提交一致。Agent 使用普通 merge 合并 PR，显式保留 trailer 并核对预期源 SHA；平台规则仅允许 squash/rebase 或无法保留消息时，报告受阻，不绕过规则。手动合并也须保留该协议，否则显示无效合入记录，不伪造修补历史。[GitHub 合并接口](https://docs.github.com/en/rest/pulls/pulls#merge-a-pull-request)

`integration.mjs` 收敛为 `preflight → verify → cleanup`：预检给出源提交、目标及所需消息；Agent 通过现有授权工具创建/复用 PR、补齐最终说明并按授权合并；verify 刷新远端完整集成历史，确认实际 M；项目验证后才 cleanup。删除默认直推合并实现，不在 skill 内新增平台写入 SDK。受理、排队或响应丢失都先核实平台与 Git，不能当作合入成功或直接重建 PR。[异步合并接口](https://docs.github.com/en/rest/pulls/pulls#merge-a-pull-request-asynchronously)

Draft PR 可提前建立，交付前持续更新同一 PR。合入授权沿用会话，准备 PR 不自动授予合并。源或目标推进后重新检查受影响差异与验证；不静默扩大已审阅内容。清理继续复用有效远端 M、项目验证提交、来源 tip、依赖占用和脏工作区检查。

### 归档与完成的区分

保留 `archive` 在源分支写 completed 并移动目录的行为；这只说明开发关闭材料齐备。工作台根据有效 M 判断是否完成集成，不能把源分支 completed 单独当成交付成功。依赖与父项关闭仍核对集中路由和实际交付可用性，不等待正式发布。

扩展既有 `rework`，只允许尚未集成的归档在登记工作分支恢复：刷新集中入口与完整合入索引，确认没有有效 M、中央归档或已经合入的源提交，再移回活动目录，恢复 Git 原型路径、active 与目标阶段，清除失效关闭记录及确认，保留已完成任务并追加返修任务。移动失败沿用现有回退处理，返修提交保持普通历史。

Agent 返修前核实 PR 未合入并取消已有自动合并请求，必要时恢复 Draft；本地锁不承诺阻止远端并发合并。重新交付时复验最新远端状态及源 SHA。已集成、路由冲突、疑似无标记集成或读取不完整均不自动恢复归档；已集成历史继续只读。

## 正式版本内容与发布关联

发布由用户明确触发，不为每次发版建立新的审批生命周期。Agent 按[发布整理要求](requirement.md#发布内容整理提示词)选定版本、上一正式版本与固定集成候选，阅读实际 diff、Change / PR 和验证记录，编写根 `CHANGELOG.md` 的版本章节。提交标题只作线索，不能替代内容整理。

默认从固定候选建立短期 `codex/release-<version>` 分支承载版本文件与 changelog，PR 指向 `releaseBranch`。它不是第三个必填长期角色。候选变化须更新说明和验证；新的实质修复先按 Change 集成，再更新候选。发布完成后，版本与 changelog 通过 PR 回流集成分支；回流 PR 不使用 Change 合入标记，不冒充一次新的 Change 交付。

### 版本章节的最小机器标记

同一版本的变更正文只维护在 changelog 章节，末尾 HTML 注释保存版本 tag 和本次实际包含的 Change。发布 PR 与 GitHub Release 复用该章节及注释；PR 可另外附比较范围、交付 PR 和验证证据。

```markdown
## 1.2.0 — YYYY-MM-DD

本次面向用户的变化，以及相关 Change / PR 链接。

<!--
SpecTrail-Release: v1.2.0
SpecTrail-Includes: change-a
SpecTrail-Includes: change-b
SpecTrail-Withdraws: change-c
-->
```

`SpecTrail-Release` 为唯一、精确的 tag；Includes 为本次交付的 Change id 集合，不是所有历史能力清单。Withdraws 可省略，只标识本次候选在正式发布前撤回的未发布 Change；不能同时 Includes 同一 id。已发布后撤回能力由后续版本正文和新的 Change 描述，不删除原版本事实。无 Change 的纯发布维护允许空 Includes。标记使用共享的小型纯解析模块，不另建 release.json 或写入 change.json。

清单由 Agent 审阅实际行为后维护；程序只核对清单与提交事实，不能从祖先关系自动识别语义回滚。重要条目在正文关联 Change / PR，机器清单用于可靠查询而非替代人工可读说明。

### 可核实的发布证据

| 时点           | 内容与结果依据                                                                                                                                                    |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 发布 PR 未合入 | 读取固定 head 的版本章节，核对 PR 的 tag 和清单；保留 Draft、打开、关闭未合入状态。                                                                               |
| 发布 PR 已合入 | 读取其实际合并提交中的版本章节，核对目标发布分支及提交可达性；只表示版本待发布。                                                                                  |
| 正式发布       | 存在非 draft、非 prerelease 的 GitHub Release；tag 解引用到该发布 PR 的实际合并提交，且该提交属于发布分支。以 tag 中的章节为准，核对 PR / Release 的 tag 和清单。 |

Includes 中的 Change 还须有有效集成交付，并位于候选的祖先链；这只能证明来源，实际包含仍以审阅后的清单声明为准。重复版本、多候选、清单冲突、tag 指向不符或内容不可读时保留已知事实并提示待核实。只创建 tag 不算正式发布。[GitHub Release 接口](https://docs.github.com/en/rest/releases/releases#list-releases)

发布 PR 普通合并，保留历史。Agent 核实远端合并结果后创建精确 tag 和 Release，复用审阅正文、使用实际日期；失败从已有事实继续，不覆盖版本或重复创建。tag 已存在但指向其他提交时停止该次发布。部署单独报告，不由 Release 状态推断。

历史按实际发布时间排列；读取完整时才称“首次正式版本”。部分历史已证明发布时可以展示已知版本，同时说明首发未核实。当前候选撤回不抹去过去正式版本；旧记录无可靠标记时只显示缺少关联。

## 平台读取、刷新与降级

在现有 Provider 增加只读分页方法，覆盖 PR 列表/详情、提交关联 PR 和 Release；沿用绑定的 credential lease、请求取消及限流错误，不新增独立身份或写权限。

1. 先由 Git 得到已知 Change、登记源分支和有效 M，再按 head/base/state 查询其 PR。已知 M 可以定向反查 PR，用于来源分支删除后的恢复；返回结果仍核对完整关联条件，不直接相信接口命中。[提交关联 PR](https://docs.github.com/en/rest/commits/commits#list-pull-requests-associated-with-a-commit)
2. 发布 PR 仅按配置的发布目标查询，与已知 Change 清单相交；Release 列表用于定位正式版本，再读取精确 tag 的章节。PR 查询始终不参与发现 Change。
3. 关闭、重开和重建按稳定 PR 身份合并历史；多个当前候选显示冲突，不按更新时间任选。源分支删除后的冷缓存路径必须有测试，不能仅靠旧缓存保住链接。

Snapshot 增加 `deliveryByChange`，包含交付阶段、Change PR 历史与当前项、发布 PR、正式版本及局部诊断。阶段可为 `pendingIntegration / pendingRelease / releaseMerged / released / unknown`，未具备交付条件时不赋交付阶段；PR 事实仍可提前显示。查询批次保存 `complete / stale / unavailable` 与最近成功时间，未完成分页不能产生“没有 PR”或“未发布”的否定结论。

保留正常读取的刷新节流、仓库锁和请求合并。Git 未变时复用文档与 blob，继续刷新交付元数据；只有有效内容或可见诊断变化才发布新快照，不因检查时间变化不断制造快照。扩展现有刷新检查记录，按信息来源保存最近成功时间并随响应提供；时间更新不改变不可变快照，失败检查不能延长成功有效期。新的元数据快照仍执行既有发布前权限复核。

PR / Release 的 403、404、限流和网络错误只影响对应信息；权限提示说明需要 `Pull requests: read`，Release 沿用 `Contents: read`。401 或确证仓库内容失权仍走现有授权失效路径。局部失败保留文档、有效 M 和标明过期的最近成功结果；冷缓存没有结果时显示待核实。请求受既有总超时与有界分页控制，不引入 webhook、后台扫描或独立缓存服务。

## 工作台呈现

**Q4（技术，round 2）：用户选择复用现有界面，不单独绘制原型。** 实现复用 `@open-folio/ui` 的 Badge、现有列表、筛选与详情组件，验证桌面及窄屏。

| 展示       | 派生条件与交互                                                                                                      |
| ---------- | ------------------------------------------------------------------------------------------------------------------- |
| 待集成     | 交付归档有效且尚无有效 M；显示当前 PR 状态，没有可靠关联时给出诊断。执行中的 Draft 只显示 PR 状态，不提前赋此阶段。 |
| 待发布     | 有效 M，尚无包含它的已合入发布 PR 或正式版本；可显示正在准备的发布 PR，以及候选撤回说明。                           |
| 版本待发布 | 已合入发布 PR 的清单包含该 Change，正式版本尚未完成；归入待发布筛选。                                               |
| 已发布     | 已核实的正式版本明确 Includes 该 Change；保留历史，不宣称当前能力生效或服务已部署。                                 |
| 待核实     | 必要信息缺失、冲突或读取失败；同时保留已核实的集成 / 发布事实与最近成功时间。                                       |

在现有列表、卡片显示简短交付徽标，详情概览增加交付区，包含 Change PR、发布 PR、版本链接和可展开的历史/诊断。列表行本身是按钮，不在其中嵌套 PR 链接；链接放详情的独立交互区域，外链只使用经过 Provider 校验的 GitHub 地址。

增加“待集成”“待发布”范围入口，跨活动/已完成记录筛选；待发布包含版本待发布，不能把归档待发布藏在完成列表里。交付筛选与开发阶段分开，切换交付范围清除不适用的阶段条件，保留类型、紧急程度等通用筛选；不增加新的开发看板列，不改写 change.json 的 status/stage。取消记录、未知状态和已发布记录均不凭空纳入待交付计数。

## 精简取舍与验证

| 处理 | 依据、影响与最小方案                                                                                                      |
| ---- | ------------------------------------------------------------------------------------------------------------------------- |
| 保留 | M 协议、预期源 SHA、清理检查分别保护历史 diff/原型、已审阅范围和未合入工作；复用现有校验，不增加第二套交付审计。          |

主 SKILL 仅保留分支职责、两条 PR 路径、归档冻结边界及发布触发入口；替换现有集成参考，发布整理与标记集中在一份 `references/release.md`。Setup 说明新契约及读取权限，原型和其他引用只同步必要角色用语，不复制整套发布规则。

验证使用现有 Node 测试、临时 Git fixture、Provider HTTP fixture 与 Playwright：覆盖自定义分支、规划直推、普通 PR 合入和拒绝非标准 M、归档返修闭环、删源分支冷启动、多 PR 候选、分页与缺权、Git 无变化的元数据刷新、完整发布及撤回历史。浏览器检查待发布归档可达、实际链接、筛选组合及手机布局；保护既有登录和偏好。具体任务与验收映射见 [Plan](plan.md)。

无待用户决定的技术缺口。真实平台写入和正式版本发布仍按实际任务授权执行；本 Change 不为验证发布规则而擅自发布正式版本。实施结束按项目约定评审、人工验收、集成并更新长期开发服务。
