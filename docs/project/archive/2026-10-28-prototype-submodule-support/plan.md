# 子模块原型支持的实施计划

## 交付目标

按 [需求](./requirement.md) 与 [技术方案](./technical.md)，使主项目从固定父提交读取子模块原型，并完成 Change 历史、两库发布与来源校验。普通目录原型保持现有数据格式和行为。

任务默认按 T1 → T2 → T3 → T4 串行推进；每项包含对应实现、有效测试和使用说明，不另设只做测试或文档的任务。方案与计划确认后才能开始实现。实现时若发现影响架构或兼容的数据契约缺口，先补齐方案，不用临时分支头回退绕过固定版本规则。

## T1：按固定父提交读取子模块当前原型

交付主仓库当前总览和固定当前预览的完整读取链路：

- 共用的来源解析与路径映射，覆盖普通目录、子模块根目录/内部包、经过嵌套 gitlink 的配置路径，以及历史 `.gitmodules` 的地址解析。
- 子仓库凭据与可读权限检查、按固定 SHA 获取对象、个人缓存隔离和相应取消/限额；子仓库无需配置 SpecTrail 或集成分支。
- 当前清单、源码和 Git HTML 的正确读取，以及现有详情来源字段中的父/子提交展示。权限或版本失败明确提示，主仓库文档仍可阅读。
- 缓存响应的来源权限复核，包括未改变父 tip、旧 snapshot、对象命中和权限撤销后的拒绝；读取语义变更更新可重建缓存指纹。

验收：父仓库 P 固定 A 后，即使子仓库分支和本地检出推进 B，当前原型仍是 A；父提交更新 gitlink 后才显示 B；旧父提交保留 A。包在子模块根目录、嵌套路径和独立前端源码路径均能解析。不支持的 URL 在传输前拒绝；缺配置、无权限、对象或文件缺失给出具体错误，普通目录原型回归通过。

验证：新增真实父子 bare/工作仓库夹具及可注入 provider 的来源测试，复用 `tests/prototypes.test.ts`、`tests/repositories.test.ts`、`tests/repository-permissions.test.ts`，断言实际返回清单、源码对象、HTML 和凭据目标。权限测试覆盖 5 分钟复验窗口与已知拒绝立即失效，不只检查文案或函数调用。非法地址测试断言未向目标发送凭据或执行网络获取。

## T2：保持子模块 Change 原型与历史来源固定

交付主仓库 Change 的子模块原型阅读与追溯：

- 活动 Change 读取其已推送固定版本；归档合入继续以唯一有效 M 定位，不新增 sourceCommit 或当前清单回退。
- 主仓库 Change 的 Git 快照与 hosted 固定地址可独立阅读；从 artifact.sourceCommit 对应父提交推导并验证真实子仓库源码，显示正确来源及不可追溯原因。
- 子模块迁移、当前清单更新或删除、子仓库分支删除和父配置变化后，历史引用仍读取原固定版本。普通目录历史范围策略保持不变。
- 公开准备与 Change 分享子资源沿用入口范围和快照限制；从子仓库直接派生的私有内容受子权限约束，已公开版本匿名读取仍完全离线。

验收：A 版本被 Change 关联后，更新到 B、重命名/删除当前入口或迁移子模块，都不改变历史标题、设备、Git HTML、hosted URL 或源码归属。子权限撤销后不能通过旧快照读子源码；主仓库已保存的产物保留且明确标记源码不可追溯。新公开发布即时检查实际依赖的子权限，已有公开版本不重新访问私有仓库。

验证：复用 `tests/previews.test.ts`、`tests/integration-previews.test.ts`、`tests/public-previews.test.ts` 与父子仓库夹具，覆盖活动分支、归档未合入、归档合入 M、路径迁移、旧快照及来源对象不可用。对旧公开 URL 比较产物字节并断言匿名请求没有 provider/Git 调用；对历史预览比较 HTML、产物标识和父子来源，防止只凭链接存在判为通过。

## T3：完成子模块原型两库发布、恢复与校验

交付可以实际使用的 SpecTrail 本地流程：

- 从主仓库配置接入已有前端包，使用子仓库相对路径，避免向父包管理器登记子模块 workspace 或覆盖前端已有工程。
- hosted prepare/upload/register 与 Git 兜底登记均识别子模块来源；验证干净源码、实际检出版本与固定 gitlink 一致，继续使用原主仓库发布协议及 sourceCommit 语义。
- 本地登记更新子仓库清单、主仓库 Change 和 Git 快照，复用并扩展参与仓库锁和恢复日志。完整说明“源码提交 → 父 gitlink 基线 → 发布登记 → 子清单提交 → 父 gitlink/Change 提交”的顺序；工具不自动提交或推送子仓库。
- pre-commit 按父 index 的配置/gitlink 校验子对象，不以子 HEAD 代替；previews-set、归档及 integration preflight 正确校验父基线与子源码。缺少本地对象时明确提示准备步骤，hook 不联网。
- 维持 archive CI 的父仓库结构校验边界，说明它不证明私有子源码可读。更新技能与公开说明，应用和 SpecTrail 同步递增到实施时最新基线的下一个补丁版本，保留 LICENSE。

验收：hosted 与 Git 两种模式均能从 A 完成发布、登记、两库提交、主项目读取及归档预检；发布后 A1 的清单与 P/A 的源码基线可区分。检出错版本、源码或依赖未提交、错误的暂存 gitlink 均拒绝。上传后登记失败可重试；事务中断可恢复；遇新编辑或提交边界变化停止恢复；失败时旧固定引用不被成功结果替换。子仓库未初始化、对象缺失和推送未完成的提示足以指导修复，无自动切分支或追最新行为。

验证：在 `tests/prototype-publishing.test.ts`、`tests/prototype-tools.test.ts`、`tests/prototype-contract.test.ts`、`tests/state-commands.test.ts` 和 setup hook 测试中补齐双仓库场景，用真实提交和暂存树验证对象归属；覆盖中断写入、上传结果重用、锁冲突及用户新编辑。最终将相同夹具走完发布、Change 关联、归档、固定读取的闭环，同时复跑普通目录的现有用例。

## T4：前端独立发布并由主仓库单次关联

按用户最新指令和 Technical 替换原发布顺序；T1–T3 保留原交付定义与证据。本任务同时交付来源契约、前端发布及主仓库关联，避免新产物产生后工作台无法读取。

- 可选来源对象明确 repository/packagePath，sourceCommit 在新模式属于前端，旧引用仍按父基线读取；新请求身份包含包路径，旧 requestId 不变。
- --package 模式在无 workflow 的前端仓库准备、上传、登记并提交清单；父仓库零预提交。移除新流程的跨库联合写入，保留旧日志恢复兼容。
- associate 导入已提交 B 的固定引用和适用 Git 快照，记录已有父映射 Q 与清单 B，核对来源与 A/B 历史，只写主仓库；父仓库最后一次提交 gitlink、Change 与快照。
- 读取、权限、index/hook、previews-set、归档与 preflight 支持新旧来源；skill 说明保持精简。

验收：真实父子 Git 仓库中前端先完成 hosted/Git 发布及清单提交，期间父 HEAD 不变；最终仅一次父提交完成关联。根目录、嵌套路径、失败恢复及普通目录/旧引用均可用，身份不符、非祖先和脏源码拒绝。主仓库关联不写子清单，历史在父/子后续提交后保持固定。

验证：新增端到端提交计数、源身份/历史关系、旧请求身份和旧引用回归，复跑相关发布、预览、权限、hook 及语义归档测试；完成类型检查、完整测试、构建与独立评审。源码或契约变化后重跑对应验证，保留旧任务证据。

## 整体验证与人工验收

验收映射如下；各任务自己的失败路径和测试证据在任务完成时随实现提交，不等待整体验证才发现。

| 需求场景 | 交付任务 | 主要证据 |
| --- | --- | --- |
| 子模块内部/根目录包、复用前端清单 | T1、T3 | 父子仓库实际清单与源码读取、已有工程接入用例 |
| 子分支推进不漂移、更新父 gitlink 才改变当前 | T1 | A/B 提交矩阵及固定父 revision 的实际 HTML |
| 当前清单删除或迁移后 Change 历史固定 | T2 | Change previews、M 和快照/hosted 固定引用对照 |
| hosted/Git 发布、归档与追溯 | T2、T3 | 两库发布提交链、真实子对象检查和归档读取 |
| 错版本、脏源码与暂存区差异 | T3 | prepare 与 hook 按各自版本拒绝及修复后通过 |
| 登记中断与失败恢复 | T3 | 文件前后字节、保留日志、后续编辑不被覆盖 |
| 无权限、撤权、配置或固定版本不可用 | T1、T2 | provider 失败注入、缓存命中拒绝和主仓库文档可读 |
| hosted 可用但子源码不可追溯 | T2 | 产物仍可访问且明确 sourceAvailable=false 及原因 |
| 普通目录及旧历史不迁移 | T1、T2、T3 | 现有普通目录发布、预览和归档回归 |

完成所有任务后，按实际变更运行 `npm test`、`npm run typecheck`、修改文件的格式检查、SpecTrail skill/setup 测试及生产构建；仅在失败、新变化或未消除疑点时补跑。worktree 缺少依赖时按锁文件安装，构建使用 `.next`，先确认没有服务占用同目录产物。

浏览器验收覆盖当前目录、Change 关联、详情来源和失败状态，复用共享 Chrome CDP 并只关闭本任务页面；带真实账号的检查使用 `withSmokeSession`，全程在回调内并核实登出清理。已有公开预览的离线保留通过接口测试验证。没有可用的真实私有子仓库授权时，用可控 provider 拒绝场景和真实本地 Git 对象验证，报告该真实环境验证缺口，不声称已实测远端私有授权。

medium 整体验证默认安排与实现上下文隔离的独立评审，修复发现后复验；向用户交付需求映射、实际验证、未验证项和原型链接，等待用户最终验收。当前只补充已有来源详情和错误状态，不新增页面布局；若实施中需要重做交互，先按原型规则处理。

## 交付与环境

工作分支为 `codex/prototype-submodule-support`，唯一交付目标为 `develop`，没有其他 Change 的实现依赖。Plan 推送后创建或复用带 `SpecTrail-Change: prototype-submodule-support` 标记的 Draft PR，方案与计划一起确认后进入 execution。当前不修改生产代码、不构建或重启长期服务、不提交正式发布 PR。

验证及用户验收完成后同步 Specs、归档，按现有 PR 流程完成交付；合并遵循实际授权，不以计划确认代替最终合入授权。集成后从主工作区 develop 构建并执行 `service:update`，对长期端口 11117 进行适用冒烟，确认运行提交。持久数据兼容，沿用现有数据目录与密钥，无例行备份或重置。验收失败在本 Change 返修，保留原公开产物及用户数据。
