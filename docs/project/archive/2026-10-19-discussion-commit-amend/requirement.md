# 合并同阶段讨论的小补充提交

## 目标与范围

同一 Change、同一阶段内的讨论补充和措辞修订可以合入最新一次讨论提交，减少碎片提交。改动仅调整 SpecTrail 的提交策略及对应说明，不改变 Change 状态结构或归档合并协议，规模为 small。

用户明确允许协作分支尝试带 lease 的强制推送；发现远端有新提交时取消改写，改用普通提交和推送（需求澄清 Q1）。原有账号密码登录 Change 继续独立维护。

## 方案要点

- 只 amend 属于同一 Change、同一阶段的最新普通讨论提交，且本次为小补充，没有夹带其他工作。阶段确认、任务完成、取消、归档、分支移交、合并以及已被固定原型版本引用的提交保留。
- 该例外适用于协作分支和独立工作分支，保护分支不适用。尚未推送的合格提交 amend 后正常推送。
- 已推送时记录改写前的原提交与本次增量，确认远端仍指向原提交，再 amend；使用显式绑定该原提交 SHA 的 `--force-with-lease=refs/heads/<branch>:<原提交>`，不使用裸 `--force`，不重新获取新 SHA 后反复尝试强推。
- 预查发现远端变化或 lease 检查拒绝时，保留原提交及别人新增的提交，仅将本次增量作为普通新提交，同步后正常推送。amend 已在本地发生时，应恢复本次操作改写的原提交关系并保留增量；不以旧完整文件快照覆盖远端新内容，不撤销其他会话的修改。
- 推送响应不明确时先查远端，确认 amend 是否已经发布，再决定后续处理；其他错误不冒充并发冲突。
- 更新主 skill 和工作区说明中的一般规则，让例外与普通推送、分支移交、归档集成的边界一致；不引入额外提交工具或常设审核流程。

## 验收

1. 规则允许同 Change、同阶段的小补充 amend 最新讨论提交，明确保护分支及有意义流程节点不适用。
2. 用本地临时 Git 远端验证：远端不变时显式 lease 能成功替换最新提交，补充内容保留且不多出一条讨论提交。
3. 验证预查已变化时直接追加普通提交；验证预查之后的并发提交会使固定 SHA 的 lease 拒绝，即使后台 fetch 更新跟踪引用也不能放行。
4. 验证拒绝后普通提交和推送保留原提交、别人新增的提交及本次补充，未将被拒的 amend 提交带回远端历史。
5. skill 校验通过，相关规则无矛盾，流程状态和长期 Specs 按实际交付更新。
