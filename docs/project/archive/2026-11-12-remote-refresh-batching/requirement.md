# 批量获取远端分支并缩短冷刷新等待

真实仓库的 110 个有效发布归档在完全空缓存下，列表可用 12.319 秒、历史补齐 15.049 秒。Git 远程操作 7 次耗时 9.589 秒，GitHub API 3 次耗时 3.443 秒，主要等待来自串行网络往返。该测量覆盖完整工程的 112 个 Change、472 份文档，包含实际 Git 获取、网络和落盘，不含登录及浏览器渲染。

用户在审阅计时及优化建议后要求：“优化吧，远程操作尽量并发、批量。”本 Change 延续 release-archive-detection，减少远程往返并重叠独立查询，不改变单发布分支、当前有效归档、首次引入与 PR 关联、未知时间分类和版本识别规则。

## 方案与边界

- 读取集成分支配置和集中入口后，一次查询发布分支与登记的工作分支，批量 fetch 需要更新的 refs。一个 bare Git 缓存的 fetch 串行，避免对象及引用写入冲突；保留末尾集成配置/路由复核、来源缺失和强推处理。
- GitHub 仓库 PR 目录读取与独立 Git 采集重叠，仍复用同一缓存查询，不逐 Change 请求；首屏不等待 PR，完整历史等待查询完成。PR 失败继续保留有效归档，凭据失效、取消及发布前权限检查仍生效，失败结果不提前写入持久缓存。
- 发布分支不可读不拖垮本可读取的工程内容；批量获取失败时只做保持既有降级所需的有界处理，不增加全局重试或并发框架。
- 不扩大超时，不改 UI、存储格式、版本来源或发布协议。预计少于 300 行有效实现，属于 Git 获取与刷新调度的局部优化。

## 验收

- 相同发布与工作分支数据下，正常刷新减少 Git 远程调用；未变化的暖刷新不多发 fetch。缺失/删除/推进的分支及批次失败不得以残留 ref 冒充当前来源。
- 当前列表可以在 PR 请求未完成时可用，历史结果、PR 条件缓存、权限拒绝和取消行为保持正确；不遗留未观察的异步失败或跨刷新请求。
- 用独立临时目录、新进程和真实 GitHub 网络重测 110 个发布归档，报告列表和历史耗时、Git 及 API 次数、原始记录和计时边界。与既有基线比较；如远端工程条目变化，明确说明差异，不伪称固定样本。
- 通过针对性回归、类型检查和构建；集成后更新开发机长期服务并按实际改动冒烟。测量不得写入现有服务数据目录。
