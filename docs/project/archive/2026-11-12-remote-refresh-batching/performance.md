# 真实远端冷刷新对照

测量日期：2026-11-12。基线实现为 `62dd4ee`（生产实现与 `efbf26e` 相同，仅新增本 Change 的规划登记）；优化实现在 `481db37` 上应用本次 Git/Store 差异，差异 SHA-256 见 [原始指标](performance.json)。

六次测量串行执行，顺序为旧、新、新、旧、旧、新；测量期间没有运行本任务的构建或测试。全部使用同一批远端提交：113 个 Change、475 份文档、110 个有效发布归档、61 个 PR。相较最初 112 个 Change 的调查，本次新增了优化 Change 及其登记分支，所以采用重新测量的旧实现对照，不能直接当作原 12.319 / 15.049 秒样本。

三次中位数：列表 15.112 → 10.415 秒，下降 31.1%；完整历史 17.362 → 13.314 秒，下降 23.3%。优化后列表范围 10.105–11.838 秒，历史范围 10.468–14.196 秒。

旧实现为 4 次 ls-remote + 4 次 fetch；优化后为 3 次 ls-remote + 2 次 fetch，其中第二次 fetch 同时获取发布分支和两个工作分支。Git 总调用从 140 降为 133。仓库/权限 API 2 次、PR 全仓分页 1 次均保持不变；另有计时前 Token 身份验证 1 次，即每轮含初始化共 4 次 API，没有逐 Change 请求。

PR 查询与 Git 获取实际重叠，网络事件分别记录开始、响应头和完整响应结束时间；并发后的各请求耗时之和不能与总墙钟时间相加。各轮 API 耗时有明显波动；这是本机、该仓库与当时网络的三组小样本，不是跨网络保证，也不据此承诺固定秒数。

六轮均完成历史、无过期 PR 降级，110 个有效归档全部进入已归档，32 个具可靠 PR 合入时间、78 个按既有规则归入合入时间未知。查询完成不代表所有旧历史均能追到 PR。

## 计时与隔离

每轮新 Node 进程，新临时私有数据目录，Git bare 仓库、blob、快照、PR、版本和权限缓存均从零开始。使用真实 Repositories、权限核实、GitReader、GitHubProvider 和 SnapshotStore；计时自发起仓库读取到工作台 JSON 可读/历史完成，包含 HTTPS Git 获取、完整 API 响应体、解析校验、当前文档及归档读取、历史追溯、版本与落盘。使用原有 120 秒刷新限制，未提高 Git 或 API 并发上限，仅重叠一份仓库 PR 查询和 Git 采集。

脚本加载与临时账号/Token 绑定单列，未计入主表；不含 Next.js 启动、HTTP 路由和浏览器渲染。操作系统及 DNS 缓存未清空。六轮结束均删除临时凭据、密钥和缓存，未操作现有服务数据。

第一次探索性旧实现测量与全量测试重叠，未纳入上表或中位数。历史千级 fixture 测量仍属于前序 Change，本轮没有重跑或宣称改善其具体耗时。

## 复现

使用 `OPENFOLIO_VERIFY_TOKEN` 所在的环境目录，显式传入待测实现工作区。脚本每轮输出独立结果目录，只保留无凭据的指标与清理记录：

```sh
node --conditions=react-server scripts/benchmark-release-remote.mjs /path/to/implementation /path/to/env-root iTgo-lyq/open-folio 1432892350 110
```

示例最后的 110 为期望的有效发布归档数；真实仓库发布后应按实际集合调整，失败不能当作完成。源码可使用前序提交的独立 checkout 作为对照，不向待测实现写入代码或复用其运行缓存。
