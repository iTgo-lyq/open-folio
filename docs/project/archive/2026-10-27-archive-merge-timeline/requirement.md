# 按合入时间浏览归档 Change

## 目标

同一天可能有多批、多个 Change 合入发布分支，当前归档列表按创建时间排列、逐行显示归档日期，难以看清交付历史。交付标签“已发布”也会让人误以为已经部署，实际只核实了代码进入配置的发布分支。

本次按 medium 推进：需要补充平台 PR 合并时间及已核实合入批次的共享数据，再调整归档列表。已有归档资格、流程状态和 PR/Git 核实规则继续适用。

## 范围与行为

- 统一 Change 交付文案为“待集成 → 待合入 → 已合入”，异常仍为“交付待核实”；覆盖列表、详情及共用详情的分享页。实际目标分支随合入批次显示，不将其硬编码为 main/master。原型产物本身的“发布”文案不在此范围。
- 保留“已归档”入口，单独浏览已归档状态时默认使用合入时间线。日期倒序，同一天按真实合入 PR 分批；显示日期、Change 数量，以及批次的版本（存在时）、目标分支和 PR 链接。
- 每批先显示 3 个 Change，超过时可展开全部、再收起；Change 标题仍可进入原详情。批次内保留类型、规模等必要信息，减少重复的状态与日期。
- 时间来自经现有 PR/Git 逻辑核实的发布分支 PR 的真实合并时间，不使用 PR 更新时间、Change 创建时间或文档归档时间替代。一个 Change 被多个有效 PR 包含时只展示一次，归于最早有可靠时间的合入批次。
- 历史补记或旧记录没有可靠合入时间时，放在时间线末尾“合入时间未知”，仍可打开材料；不修改历史归档来补造时间。
- 现有类型、紧急程度、创建者等筛选继续生效，日期和批次数量反映筛选结果。时间线固定按时间排列，不受创建时间、紧急程度排序或阶段分组干扰；混合状态的个人视图沿用现有列表。
- 适配现有浅色、深色和手机布局；键盘可操作展开、收起与详情链接，从详情返回仍能定位原 Change。

需求 Q1：用户确认时间线方向，并将建议的“已合入主分支”缩短为“已合入”，对应“待合入”。需求 Q2：用户选择不单独绘制原型，沿用现有样式实现。

## 验收

1. 同一天两次合入、每次多条 Change，以及跨天、跨年记录按正确日期和批次展示；每条 Change 只出现一次。
2. 大批次默认只展示 3 条，展开能访问全部 Change，收起与详情返回的焦点行为正确；筛选后数量与结果一致。
3. 多个发布 PR 中仅采用已核实合入证据；关闭未合并、Git 不包含、时间缺失及历史补记不被伪装成某一天的合入。
4. 文案在列表、详情与分享页一致，状态判定不变；非归档列表和混合状态视图保持原有筛选、排序与详情导航。
5. 使用共享 Chrome 的独立测试页面检查桌面、手机、明暗主题及键盘交互；登录真实工作台时使用 withSmokeSession 并确认退出清理。
