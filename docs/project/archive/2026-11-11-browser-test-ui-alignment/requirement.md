# 浏览器回归对齐当前目录分组、交付与导航

## 目标与范围

修复当前 main 上因界面演进而过期的浏览器断言，恢复看板、连续交付与详情导航的有效回归覆盖；修正恢复断言后暴露的看板相邻导航顺序不一致。按 small 推进：不增加产品能力或调整无关行为。用户已明确要求在 develop 创建 Change、独立分支实现并提交 PR。

## 方案要点

- `changes` 的上下文保留与 `change-labels` 的紧急程度排序使用默认处理状态分组，断言「按处理状态看板（只读）」及四列。`change-reader` 入口已显式指定 `group=none`，切换看板不改变分组，断言「不分组看板（只读）」及一列。`change-directory` 已显式选择阶段，其「按阶段看板（只读）」及五列断言保留。
- 连续交付保留产品逻辑：已完成范围先按交付阶段分组，同一延续组可在不同阶段各出现一次。测试先验证「待集成」与「交付待核实」各包含正确的唯一成员，再显式选择「不分组」，验证整组展示、排序、筛选和深链接。
- 连续交付的成员数量、顺序与位置仅通过「打开 …」标题链接判断；当前每行还提供规模详情链接，不能把全部链接数当成员数。
- 全量回归发现同一归档时间线改动遗留的 `delivery` 断言：详情应显示「已合入」，已归档目录使用合入时间线，不再在每行重复交付标签。缺少可靠合入时间的测试记录应位于「合入时间未知」。先在未修改 main 单独复现，再仅对齐这些断言。
- 详情相邻导航复用目录现有分组函数，遵守当前选择的处理状态、阶段或不分组。修复前桌面看板详情硬编码按阶段，导致不分组看板首条记录可能在导航顺序末尾、下一项被禁用。这是原相邻导航验收暴露的直接缺陷，保留原断言修复；仅删除重复的阶段分支，不增加契约，仍为 small。没有视觉或交互设计变化，无需新增原型。
- 每项修改前在最新远端 main 的未修改测试上复现；核对 `change-directory` 已显式选择阶段的断言是否本来通过。测试使用独立 fixture 数据与端口，不接触长期服务数据。

## 连续交付判断依据

[连续交付需求](../../archive/2026-10-18-change-follow-ups/requirement.md) 要求延续链分组、各成员保留真实状态和独立入口，当时验收要求两个归档成员放在同一外框。后续 [界面重构方案](../../archive/2026-10-22-frontend-style-interaction-refactor/technical.md) 明确「已完成按交付标签分组」；[归档时间线需求](../../archive/2026-10-27-archive-merge-timeline/requirement.md) 则要求归档记录按真实日期与 PR 批次组织，每条 Change 只出现一次，方案明确跨日期连续交付不挪动真实日期。当前 [Change 追踪 Spec](../../specs/project-knowledge/change-tracking/spec.md#pr-与交付进度) 明确「已完成按待集成、待合入、待核实分组」。这些规则保留成员的真实交付阶段，未要求延续组跨阶段合并。

因此本次采用后续已验收规则：分组标题可在不同交付阶段重复，每个 Change 仍只出现一次；选择不分组时，匹配的连续交付成员聚合在一处。额外核实 Git 历史：分阶段逻辑由 `9d1a92b2` 引入，`0a3b016b` 在此处统一交付文案并增加归档时间线，并非首次引入该逻辑。连续交付产品逻辑、Specs 与数据契约无需改变。

## 验收

1. 记录当前 main 的提交及五个目标场景的原始执行结果，区分实际失败与本来通过项。
2. 看板断言与测试所选分组一致：处理状态四列、阶段五列、不分组一列；原有筛选、排序、详情导航及上下文检查继续有效。
3. 连续交付分组的处理有两边需求与当前 Spec 的依据，测试覆盖真实交付阶段与筛选、排序、深链接，避免通过移除有效断言掩盖失败。
4. 六个相关 spec 与完整 `npm run test:e2e` 均执行，记录结果；不改变无关产品行为。
5. 自查、按 small 自验收并归档，通过目标为 develop 的 PR 交付。

相关 spec 包含原五个及全量回归发现的 `delivery.spec.ts`，均属于同一目录与交付界面演进；不修改交付判定或归档时间线行为。
