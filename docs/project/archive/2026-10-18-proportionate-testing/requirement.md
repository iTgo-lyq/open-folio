# 测试策略按实际风险设计

## 目标与范围

用户要求将 `testing-strategy` 直接装入当前 skill 包，并明确「制定技术方案的时候，关于测试这部分，绝对不能过度设计」。

将 Anthropic 官方 `anthropics/knowledge-work-plugins` 的 `engineering/skills/testing-strategy` 安装到 SpecTrail 包内，由技术方案阶段引用。保留来源、固定版本及许可证，并按本项目要求适配通用测试建议；不安装整个插件或写入全局 skills。

本次为 small：只修改 skill 文档、包含上游 skill 及许可证并同步流程 Spec，不修改应用、测试工具链或状态契约。用户已明确安装与规则方向，无方案级未决项。

## 方案要点

- 从当前验收行为、真实风险和已有测试出发，复用现有验证，在能发现相关缺陷且维护成本合理的层级补缺口；必要验证不因避免过度设计而省略。
- 测试金字塔和组件类型建议是选项，不要求凑齐层级、数量、覆盖率或完整测试矩阵；不重复验证实现细节，不默认添加框架、复杂 mock、测试基础设施、性能或混沌测试。
- 低风险文档、样式等变更可采用审阅、静态检查或必要冒烟，不强制新增自动化测试。关键数据与权限等风险仍需相应验证。
- 策略留在 Technical，small 留在 Requirement 方案要点；只记录验证对象、方式与判定依据，重要缺口才说明限制，不另建固定测试计划文档。
- 执行沿用同一策略，无新增变化、失败或疑点时不反复扩大测试。

## 验收

- 包内存在可读取的 testing-strategy、固定来源和上游许可证，主 skill 具有明确调用入口。
- 主规则与子 skill 均明确禁止过度设计，没有默认数值覆盖率、全层级测试或独立测试体系要求。
- 低风险修改与关键风险修改的验证边界清楚，既有项目必需检查仍保留。
- skill 校验、链接/差异检查与来源核对通过，流程 Spec 同步。
