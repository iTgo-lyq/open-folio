# 统一依据 PR 识别 Change 集成

## 目标

OpenFolio 与 SpecTrail 通过 PR 记录识别 Change 的正式集成交付。平台生成默认合并消息、未在消息中保留 `SpecTrail-Change` 时，已合入的 Change 仍能准确显示交付状态、定位合入差异，并用于 CLI 验证和发布检查。

用户明确要求“统一以 PR 记录为依据，不再依赖合并提交消息中的标记”，并选择“新建独立 Change，保留现有 Change”。本项为 medium：改变 CLI、工作台及发布检查共用的集成证据契约，需要共同适配，不能仅修正工作台的显示兜底。

## 范围与行为

Change 与 PR 仍通过同仓库身份、登记的来源分支、配置的集成目标分支和 PR 正文末尾唯一合法的 `SpecTrail-Change` 标记关联。已合并 PR 提供真实合并提交，Git 核对它是否属于当前固定的集成历史。提交标题、提交正文及分支命名不再提供 Change 关联证据；没有对应 PR 的历史提交不通过消息标记补认。

统一 OpenFolio 的集成状态与差异索引、SpecTrail CLI 的正式合入核实，以及发布 PR 检查的 Change 集成依据。PR 的已合并事实与差异能否展示分别处理；差异仍取原合并提交的第一父提交到合并提交，不把后续同步提交当作本次交付。来源分支删除、原合并提交进入第二父历史后仍可识别。

保留归档 CI、来源是否实际纳入的 Git 检查和清理时的防误删保护。PR 读取失败、关联不唯一或合并提交尚不可读时给出明确诊断，不把读取失败记作从未合入，不任取一个候选，也不退回提交标记判断。

刷新应同时反映 PR 和 Git 的变化；同一 Git tip 的旧索引必须重算，PR 正文修改或状态更新也不能被同 tip 缓存遮蔽。复用 OpenFolio 已有批量分页 PR 读取，不逐 Change 增加平台请求。既有归档、提交历史和用户数据不改写。

## 与现有 Change 的关系

`integration-history-recovery` 已通过 PR #25 合入 develop。本项依赖其已确认的“合入事实、差异读取、来源清理分别判断”实现，再替换其中剩余的提交标记识别。保留原 Change、PR 和验收记录，不修改其归档材料。

## 验收

1. PR 正文正确关联、平台已合并、合并提交属于集成历史时，即使合并消息完全没有 Change 标记，CLI 与工作台仍认定已合入，双亲合并的差异和发布检查使用同一原始提交。
2. 来源分支已删除，或合并提交只经后续同步的第二父路径可达时，冷缓存仍识别相同 PR 和提交；其他分支上的提交不算当前集成交付。
3. 只有提交消息标记、PR 未合并、仓库或源目标分支不符、正文仅提及标记或有重复标记时，不误认正式交付；多个匹配的已合并 PR 明确报歧义。
4. PR 读取失败、分页未完成、合并提交暂不可读时保留诊断，允许后续重试；差异不可展示不抹去已经核实的 PR 合入事实，来源清理继续拒绝未纳入的新提交及不安全工作区。
5. 升级后同 tip 的旧索引重新计算；随后只修改 PR 正文关联、保持 Git tip 不变，也能更新集成状态。原差异读取、归档原型与发布状态不发生边界漂移。
6. 回归通过并完成人工验收、归档及获授权合入后，从 develop 更新长期服务并完成相关冒烟；不在本项发布 main。
