# PR 集成识别实施计划

落实 [Requirement](./requirement.md) 与 [Technical](./technical.md)，以 PR 记录统一定位真实交付，不再扫描合并消息。按 T1、T2 顺序实施；前置 `integration-history-recovery` 已合入当前基线。

## T1：以 PR 记录统一 CLI 与发布检查的集成证据

交付共用 PR 关联与 Git 核实逻辑，移除消息标记扫描；接通 CLI 和发布检查的完整分页 PR 读取，同步 SpecTrail 指引与 CI 模板。正式合入结果、差异结果和来源安全检查保持各自职责，默认合并消息不会阻断核实。

验收对应需求 1–4：同仓库、登记来源、配置目标及 PR 正文精确匹配；已合并 PR 的 M 在目标历史中可达；无 PR 或未合并不被消息标记误认；多个已合并候选不任取；来源删除和第二父路径不影响识别，平台失败及对象缺失有明确诊断。来源新提交、依赖、文件和占用检查仍拒绝不安全清理。

用临时 Git 仓库及注入的 PR 数据覆盖默认合并消息、误关联、分页失败、歧义、冷读与删除保护；发布检查在同一 fixture 中核对 M、候选包含关系和归档。运行相关集成测试及 skill/Setup 自包含测试；不依赖真实网络完成回归。

## T2：使工作台状态与差异共同使用 PR 记录并完成整体验证

交付复用 PullRequestCache 的快照集成，将 PR 关联计算放到完整集合就绪之后；移除旧消息索引优先、PR 兜底的双路径。递增索引版本，同时把集成结果与交付状态纳入快照变化判断。

验收对应需求 1、4–6：默认消息下的交付状态和双亲合并差异使用同一 M；差异缺失不否定可验证的 PR 合入；同 tip 旧索引重算，只改变 PR 正文也能更新结果；读取失败不冒充成功；来源删除后仍能读取差异和归档原型。平台请求复用既有批量分页，不随已知 Change 数量逐条增长。

运行集成状态、快照缓存、交付状态、差异与原型相关回归，以及完整项目测试、类型检查、格式检查、构建和独立评审。人工验收后同步 Specs、归档并更新原 Draft PR；获合入授权后更新 develop 长期服务，选择真实 PR 状态与差异进行冒烟，登录遵守 withSmokeSession 的退出与清理验证。

## 整体验收

以同一份无消息标记、已合并的 PR fixture，证明 CLI、工作台与发布检查得到相同 M，并核对 Requirement 各项失败路径。记录实际命令、结果、评审结论及任何尚未验证的限制；未完成人工验收不归档，未合入不更新长期服务。
