# 个人工作台交付计划

依据 [需求](./requirement.md)、[技术方案](./technical.md) 与 Change 固定原型。交付从个人 GitHub token 连接、自动发现 SpecTrail 仓库，到读取、分享和公开原型的完整路径；保留既有侧边玻璃胶囊、顶部仓库选择和白色工作面。

按 T1 至 T9 顺序串行执行。先验证平台与凭据隔离，再接入会话、发现和授权读取，最后完成公开原型、工作台交互与旧部署迁移。每项包含对应实现、异常处理、测试与使用说明；在同一 Change 分支形成可独立审阅的提交。中间提交保持可构建、可测试，完整迁移前不作为正式升级版本发布。不存在其他 Change 的交付依赖。

## T1 建立可扩展的 GitHub 仓库适配契约

交付：服务端显式注册的 RepositoryProvider、归一化身份与仓库模型、稳定仓库标识和标准错误。GitHub.com 实现身份验证、分页枚举、按稳定身份解析仓库、读取权限检查和固定提交的工作流探测；业务层不依赖 GitHub 原始字段。测试适配器仅使用虚构平台，不加入其他真实平台实现或界面入口。

验收：区分 token 无效、发现权限不足、读取被拒、限流、网络失败和配置缺失；改名或转移后仍核对同一仓库 id。探测普通文件与树类型，不跟随符号链接、重定向或任意 continuation；默认分支不硬编码为 main。

验证：适配器契约测试覆盖多页、重复或跨域分页、限流、树截断、目录／符号链接／子模块、空仓库和 Metadata 可读但 Contents 被拒。虚构第二适配器通过相同契约，证明公共层无需改写。

## T2 让 Git 读取只使用指定连接的 token

交付：显式 GitTransport 与隔离的 Git 运行环境；经校验的 GitHub HTTPS 地址使用该连接的凭据执行 refs、fetch 和后续内容读取。保留必要代理、可信 CA、资源限制及既有 bare Git 读取能力，测试 file transport 只由测试工厂提供。

验收：没有、错误或无权的 token 都无法借宿主 credential helper、netrc、SSH agent、继承的鉴权头或旧仓库配置成功读取。秘密不进入命令参数、磁盘 Git 配置、remote URL、日志或公共错误；并发操作不会串用 token。重定向、子模块递归及仓库脚本执行被禁用。

验证：受控 HTTPS Git 远端记录实际鉴权，植入有效宿主凭据后测试失败仍然成立；有效 token 完成 ls-remote、fetch 和固定 blob 读取。覆盖取消、超时、代理／CA 与并发隔离。在授权凭据可用时执行真实 GitHub fetch，按下文联调约定保留脱敏证据。

## T3 提供个人会话与连接生命周期

交付：个人会话以及连接、替换、移除、退出接口；服务端加密持久化 token、Cookie 轮换、连接标签、credentialRevision 和操作取消。会话拥有连接集合，同一 GitHub 账号的多个 token 可独立存在。

验收：首次验证成功才建立连接；重启可恢复有效会话。替换失败保留原连接，替换为其他身份引导新增连接；移除、退出、过期和版本变化使在途操作失效。跨会话无法查询或操作他人连接；密钥缺失或密文损坏不覆盖原数据。普通连接不授予部署管理能力。

验证：持久化与 HTTP 集成测试覆盖 nonce／AAD、私有文件权限、密钥首次生成及丢失、Cookie 属性与轮换、同源校验、输入限长和控制字符、替换回滚、跨会话访问与取消。扫描响应及捕获日志，确认不回显凭据。

## T4 自动发现并诊断 SpecTrail 仓库

交付：所属连接的有界发现作业、进度与重试接口、个人仓库目录，以及按 GitHub HTTPS 地址检查的补充入口。复用工作流契约验证配置、守护分支与默认阅读来源；发现只读取必要元数据、配置和 ref，选择仓库后才完整采集。

验收：能区分有效且有内容、有效但无内容、未接入、配置损坏、来源异常及检查失败。ready／attention 进入目录并展示对应状态；未完成分页或限流不显示完整空结果。遵守并发、超时与 Retry-After；进程重启、连接版本变化和移除有明确终止状态，一个连接失败不影响其他连接。目录返回前重新验证当前授权，不直接返回旧发现结果。

验证：发现服务与 HTTP 集成测试覆盖六类仓库、多页、限流恢复、取消、进程重启和多连接；记录请求数量及 Git 调用，验证不会全量 fetch 候选仓库。非法 URL、任意主机、无权仓库不能进入正常目录；真实 GitHub 联调补齐自动发现到工作流识别的证据。

## T5 按个人仓库权限读取工程记录

交付：ReadContext、按连接与 revision 隔离的 Git／快照／任务缓存，及新的仓库读取、搜索、刷新、文档与附件接口。复用已有 Specs 阅读、Change 聚合、分支与归档标签解析；当前原型配置的来源改为实际默认分支，Change 固定引用仍保留原来源规则。

验收：每个受保护请求重新验证身份、仓库权限及指定 token 的 Git 读取能力；缓存命中不跳过授权，长操作交付前重新检查远端权限和本地连接版本。两名用户可读取共同仓库的同一提交，无法借对方的连接、快照或文档 id 读到私有内容。权限无法确认时不返回旧正文，刷新失败仅在仍有权时保留旧快照。旧工程 API 和管理员／邀请码凭证不能成为旁路。

验证：HTTP 与 Git 集成覆盖 GET／HEAD、列表、搜索、深链接、历史快照、附件、刷新及并发取消；植入其他连接缓存后测试撤权、scope 缩小、过期和平台不可达。公开仓库也必须验证 token 身份。既有阅读、Change 来源与固定引用回归同时迁移至显式授权夹具，增加非 main 默认分支。

## T6 独立交付可匿名访问的固定原型

交付：有权限用户准备原型的接口、独立公开产物目录、publicationId 预览页及最小公开元数据、资源与截图响应。兼容 Git、内置 hosted 和外部 hosted；保留沙箱与固定版本完整性。

验收：准备阶段使用当前用户授权；匿名 GET／HEAD 只读已发布目录，不能调用平台或 Git，也不能自动准备缺失版本。连接移除、token 过期或后续关闭仓库原型开关不删除已发布版本；未就绪与运维撤回分别明确响应。公开接口不泄露工程正文、完整 Change、连接信息或上传秘密。

验证：三类来源集成测试覆盖准备失败原子性、重复发布、摘要、资源清单、截图、断网、发布者失效、未知版本与撤回。匿名路径触发 Git／平台客户端即测试失败；浏览器验证 opaque-origin iframe、宿主隔离和既有静态托管链接。

## T7 在玻璃外壳中完成连接与仓库发现流程

交付：正式工作台的首次连接、我的连接、仓库首页、搜索／筛选、重新发现及地址检查。复用已确认的窄侧轨、玻璃胶囊、白色工作面与移动底部胶囊；基础组件和主题经 UI 包入口复用，业务组合留在应用层。

验收：用户无需空间、邀请码或服务密码，从连接 GitHub 进入自己的仓库。生成 token 的入口和只读权限说明可见；连接归属、同账号多 token 标签及选中连接明确，失败不自动切换凭据。未连接、发现中、无仓库、部分失败、未接入及过期状态都有恢复动作；移除或退出清理对应页面内容。没有可读仓库时禁用阅读模块。

验证：浏览器测试以全新匿名和两个独立个人会话开始，替换原有全局管理员 storageState；通过受控平台与 Git 服务演练连接、恢复、发现、替换、移除和退出。检查错误文案、可见焦点、Escape 恢复、无浏览器凭据持久化及桌面／平板／手机／320px 布局。

## T8 贯通仓库阅读与协作分享

交付：顶部仓库与连接上下文、侧边 Specs／Changes／原型导航、来源栏与目录、刷新反馈、工程记录分享及独立公开预览。保留侧栏收起／恢复、移动目录和已有文档阅读能力；仓库切换保留模块并重置文档位置。

验收：工程分享链接只表达稳定仓库身份和阅读位置，不含连接 id、token 或访问授权。接收者用自己的连接验证后回到目标；多连接时明确选择，无权时不能显示旧内容。仓库改名仍可解析，浏览器前进后退可恢复位置；原型链接可在匿名浏览器中直接打开。

验证：双会话浏览器测试覆盖共同仓库分享、无权账号、重新连接后恢复、分支／文档／Change 定位、历史导航和连接失效。跨设备尺寸对照固定原型截图，检查玻璃导航、目录、刷新失败和公开预览；回归既有 Specs、Changes、原型、截图和固定版本场景。

## T9 完成旧部署迁移与运维边界收敛

交付：旧配置私有备份与迁移映射、旧项目深链接的本人鉴权恢复，以及新版部署、密钥备份／轮换、会话过期和回退说明。删除剩余项目登记与邀请码维护界面和旧授权路径；资源限制、存储与上传地址获取保留为独立运维能力。

验收：旧 projects、inviteCode、管理员 Cookie 和缓存不导入任何个人授权；鉴权前不泄露旧仓库映射。可定位的旧链接经本人验证恢复，无法定位时提示重新选择；旧原型只有准备过的公开版本可以映射。上传地址仍受管理员保护，SpecTrail 获取地址协议及既有公开资源继续工作。备份和旧缓存不被破坏，按文档停机后可回退。

验证：旧部署 fixture 覆盖邀请码、管理员 Cookie、已采集缓存、上传设置和损坏配置；演练升级、重启和回退。穷举旧／新工程入口的权限矩阵，确认无旧 API 旁路；回归内置上传、公开静态资源与 skill 协议。同步部署说明，已实现能力 Specs 在最终验收后统一更新。

## T10 修复整体验证与独立评审问题

交付：在已确认范围内修复评审发现的授权交付、发现限流与原型回归问题，独立编号与证据写入 Review，不改变产品或技术边界。

验收与验证：增加能复现问题的针对性用例，修复后复验；重跑受影响的浏览器场景、完整单元／类型／格式及生产构建，并由独立评审者核对修复结果。按 T9 后串行执行。

## T11 修复运行实例的反向代理同源校验

交付：连接写请求以实际 HTTP Host 和可信代理协议恢复外部来源，兼容 Next.js 请求 URL 的内部主机；仍拒绝跨源、缺失来源与远程明文 HTTP。

验收与验证：请求级测试覆盖内部 URL／外部 Host、跨源和伪造 forwarded-host，真实生产实例请求复验同源写入、TLS 约束及新工作台页面；更新原 Merlin 预览地址，保留回退备份。按 T10 后串行执行。

### 测试与真实联调

受控测试平台使用虚构身份、两名隔离用户、共同及独占仓库、有效／无效 token 和可切换权限，配合受控 HTTPS Git 远端验证实际传输。CI 不依赖真实 token，不以 mocked Git 命令成功代替鉴权隔离测试。只供测试的注入入口不能由生产 HTTP 输入启用。

真实 GitHub 联调使用用户已授权仓库与 token 可见的 SpecTrail 仓库，覆盖身份、仓库发现、固定提交工作流探测、fetch 和正文读取。凭据由用户通过私有文件或临时环境注入，仅记录引用、权限范围和脱敏结果，不复述聊天中的秘密，不修改远端仓库。已有 ls-remote 实验不算完整联调；凭据失效或缺少正向样本时明确保留未验证项，继续其他可独立验证工作，不以模拟结果宣称完整验收。

每项按影响范围运行测试及类型检查；整体验证运行 `npm test`、`npm run typecheck`、`npm run format:check`、生产构建和 `npm run test:e2e`。UI 包有改动时增加其组件预览验证。沿用 `.next` 和 `.next-e2e`；仅在保留运行中生产预览时使用 `.next-verify`，同目录构建串行，临时产物用后清理。

实施前按根 AGENTS 阅读所用 Next.js 本地指南，UI 包开发前读取包内 README。验证记录归入 Execution 的对应任务，包含实际命令、结果及限制。完成后进行与实现上下文隔离的独立评审，覆盖完整差异、权限边界、迁移、需求映射和测试证据，问题及复验记录归入 Review。

向用户交付可运行工作台、多设备截图、完整验收证据及明确限制。人工验收后同步访问、配置、Spec 阅读、Change 跟踪、原型公开生命周期和必要工作流来源说明，归档并保留原型固定版本。计划不预授权生产部署或合入 main。
