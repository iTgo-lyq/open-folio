# 执行证据

## T1：批量读取与复用 PR 页面

交付采集按集成、发布目标分支分别查询，使用本轮共享目录建立关联索引，删除逐 Change 的详情、head 与 commit 补查路径。PR 页面按 created 降序读取，来源目录下持久化完整分页、ETag、原始数量和标记摘要，不保存正文；完整查询成功后替换，失败保留对应旧集合。未变化快照发布缓存前也复查权限。

验证：`npm run typecheck` 通过；provider、delivery、delivery-override、pull-requests、store、repositories 共 44 项通过。随后新增真实 collectDelivery 的 138 Change 请求计数回归，与页面缓存测试共 11 项通过：冷、热两轮都仅两次 base 查询，同 base 合并为一次。

模拟 HTTP 证据：74 个重复读取仅发一次请求；两个 base 冷缓存共 2 次 200、热缓存共 2 次 304。1001 个 PR 完整读取 11 页，末页旧 PR 标题与标记修改后前 10 页 304、末页 200。无 Link 的满页 304 仍能读取新增尾页；未标记和跨仓库 PR 不进入索引。缓存损坏、缓存大小上限、第二页失败、其他 base 独立成功和无 ETag 路径均有回归。

## T2：统一冷却与限流错误传递

GitHub 请求入口共用进程内实例＋账号冷却状态。只有实际 403/429 限流才写入截止时间；解析 Retry-After、主限流 reset 和有界错误正文，二级限流不再被误判为权限错误。HTTP 成功即使剩余额度为 0 也不主动节流；不存在自动重试、动态预算或切换读取来源。

发现、已有绑定切换及相同 Token 重复绑定都传入已知身份；首次未知 Token 保留一次必要的 `/user`。PR 首个限流立即终止刷新，错误和等待时间传到浏览器，当前快照、完整缓存及成功检查时间保持不变；冷却过期后的正常调用可继续。评审 R1 的修复和复验详见 review.md。

专项验证：身份、冷却与账号测试 14 项通过；独立评审另跑 17 项通过。浏览器 API 与交付共 6 项通过（首轮新增用例遇到 Next 路由播报器与业务 alert 的选择器歧义，限定业务文本后单项复跑通过）。浏览器在限流失败后展示“至少 90 秒后再试”，保留原 PR 链接。

## 整体验证

最终实现执行 `npm test`，331 项全部通过；`npm run typecheck`、`npm run build`、改动文件 Prettier 与 `git diff --check` 通过。生产构建在所属 worktree 的 `.next` 完成，浏览器验证使用 `.next-e2e`。独立评审覆盖完整差异并复验 R1；无未解决问题。

未对真实 GitHub 服务进行压力测试，所有请求次数和限流复现均来自可控模拟响应。每轮请求次数等于两个目标分支需要读取的页数之和；各自单页时共 2 次，304 仍是 HTTP 请求，收益是缓存复用与条件请求的配额节省。不会承诺任意仓库都只有 2 次或彻底杜绝限流。

开发机长期服务的正式更新在人工验收及集成后进行；本轮未改动真实用户数据、没有构建或替换主工作区的服务产物。
