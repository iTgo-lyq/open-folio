# 减少 GitHub 重复请求与历史 PR 扫描

## 背景与目标

OpenFolio 已出现 GitHub 限流。当前一次仓库刷新即使 Git 内容没有变化，也会逐个查询全部历史 Change 的 PR；已归档、已补记发布或此前查不到 PR 的记录仍反复参与查询。后台扫描与多个工作台绑定叠加，使日常读取成本随历史记录数量增长。

本次从查询组织和缓存复用上减少不必要请求，优先交付统一冷却、查询去重和历史 PR 缓存。减少请求应在额度充足的正常路径中就能成立，不能依赖接近限流时临时改变行为。已有量化证据见 [调查记录](./research.md)。

用户明确约束：“不要硬补快限流时候的规则，尽量从根本算法设计上减少请求，依然触发限流该报错就报错，不要引入其他兜底。”

## 范围与行为

### 查询去重

同一凭据工作台、仓库和查询语义下，相同的 PR 列表或详情请求合并执行，查询结果供多个 Change 的交付判定共同使用。已有同来源刷新合并机制继续承担并发刷新去重，不为同一目的新增多套任务调度。

区分平台数据采集与逐 Change 的本地交付计算。多个 Change 引用同一分支、PR 或发布信息时，不因消费者数量增加而重复获取同一远端结果；列表已具备所需信息时，不机械地为每个条目再查询详情。分页不完整和查询失败不能被缓存为“没有 PR”。

### 历史 PR 缓存

复用既有历史关联和查询结果，避免每轮刷新重新验证全部已知历史 PR、搜索全部历史无 PR 记录。没有新证据、缓存仍有效的历史记录可以继续参与本地交付计算，不必逐条请求 GitHub；正常刷新成本不再随这类记录数量线性增长。

已合并 PR、已发布 Change、历史发布补记和有效的“未找到 PR”结果应有适合其语义的复用与失效依据。已补记发布的旧记录不需要每分钟重新搜索 PR 来维持其交付状态。缓存不能把失败变成空结果，也不能以“Git 未变化”为由认定 PR 元数据永不变化。

保留现有 PR 关闭、重开、重建、合并及关联正文修改的识别能力，保留发布清单和 Git 祖先关系的交付证据约束。技术方案明确哪些变化触发读取、历史元数据何时重新核实，以及手动刷新如何使用缓存；不默认将所有历史记录永久冻结。

### 统一冷却与错误

识别 GitHub 已经返回的限流事实，按适用的 `Retry-After`、`x-ratelimit-reset` 统一约束后续请求。共享同一限额的调用入口在有效冷却期内不继续请求；已经在途的请求可以结束，尚未发出的查询不再因逐 Change 循环继续执行。手动刷新、后台刷新和其他 GitHub 读取入口共同遵守该状态。

冷却是对明确限流响应的处理，不是根据剩余额度预测限流的调度系统。限流时仍明确报告限流及已知恢复时间；没有可信恢复时间时如实说明未知，不伪造精确时间，也不新增自动重试循环。冷却结束后由正常读取或既有调度再次尝试，不积压并集中补发失败期间的查询。

当前请求失败不能更新对应的成功检查时间或伪装成成功。沿用已存在的旧内容展示及错误提示语义，不新增故障后借用其他凭据、其他数据来源或扩大扫描的兜底。二级限流应与真实失权区分，不能因限流撤销已有权限结论。

## 边界与取舍

- 请求冷却按实际共享限额的 GitHub 身份协调；私有内容、查询缓存与权限结论继续遵循工作台隔离，不以减少请求为由跨账号共享内容或凭据。
- 不增加“剩余请求低于某阈值”的临时降频、动态预算分配、备用 Token、失败重试队列或失败后全量扫描。
- 不通过普遍延长所有刷新间隔、放宽权限复验来代替查询算法改进，不承诺任何规模下永不触发限流。
- 不将 GitHub App、Webhook、GraphQL 迁移、监控平台或管理面板纳入本次交付。必要请求计数用于验证实际算法效果，不扩展为独立可观测性项目。
- 不改变 Change 交付含义、用户账号绑定及现有原型能力。缓存作为可重建数据，其具体持久化与失效方案在技术阶段确定。

暂定规模为 medium：涉及 PR 数据采集、可复用缓存以及 GitHub 错误与刷新调度三类职责的联动。本次没有其他 Change 的前置交付依赖。

## 验收标准

1. 在远端信息不变的模拟场景下，多个 Change 使用相同查询时，每个相同请求只实际执行一次；并发刷新不绕过既有合并机制。
2. 在历史缓存有效且不存在失效依据时，增加稳定历史 Change 不导致常规刷新逐条增加远端查询；与当前基线比较，能用实际请求计数证明减少了重复列表、历史详情及历史空结果查询。
3. 活跃 PR 的关闭、重开、重建、合并，发布关联正文变化以及相关 Git 提交变化，能够按明确的刷新与失效规则更新交付信息；分页未完成或接口失败不产生新的“无 PR”事实。
4. 首次明确限流后，同限额范围尚未发出的查询停止，冷却期内各入口不继续向 GitHub 请求；响应中给出的恢复时间得到遵守，并向调用方报告限流。主限流与二级限流不被误报为失权。
5. 限流和其他查询失败不更新对应成功时间，不触发新增自动重试、凭据切换、备用来源或全量扫描；冷却结束后正常查询仍失败时继续明确报错。
6. 工作台之间的内容与权限隔离、成功快照的既有展示方式，以及 Git 证据参与交付判定的规则保持有效；普通路径的请求减少不依赖剩余额度阈值。
