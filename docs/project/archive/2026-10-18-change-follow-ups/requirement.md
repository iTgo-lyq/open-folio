# 连续交付通过延续关系分组展示

## 目标与范围

用户围绕同一交付结果连续补充时，已经归档的 Change 保留独立交付事实，后续 Change 声明延续关系，工作台以带标题的外框分组呈现，减少平铺记录造成的碎片感。用户明确要求关联 technical-clarification 与 independent-clarification-budgets 两个已归档 Change，并在实际页面验收中要求分组始终展开，只保留标题和原有记录。

- 一个后继通过可选 followUpOf 指向同仓库已有效归档的直接前序；正文说明补充或修正的具体决定。关系与规模、执行依赖、父子拆分独立，不引入新的话题生命周期。
- Change 列表按延续链分组，首次关联时单独生成概括共同目标的分组标题，后续默认沿用；每次交付保留自己的标题。成员始终可见，无展开或收起操作、统计说明、当前记录文案及组级操作按钮。每条记录沿用原入口与真实状态，进行中范围展示符合筛选的活跃后继。组标题嵌在外框上沿，层级高于成员标题；组内分割线两侧留白，外框上下均有间距，末行不叠加底部分割线。
- 规模、阶段、等待和能力筛选继续按各 Change 生效；详情深链接、任务与依赖视图保持可用。详情可查看直接前序及本组交付。
- 缺失、自指、成环或不可判定的延续关系显示明确提示，相关记录仍可独立查看；这些阅读关联不影响已有执行依赖或验收事实。
- 对用户指定的两个历史记录执行一次性关联迁移：只在 independent-clarification-budgets 的 JSON 增加 followUpOf，保留全部正文、任务、关闭记录和时间；迁移用普通提交记录，不新增通用归档编辑入口。
- 本轮根据用户明确指定，再为上述组补充独立标题“完善技术方案问询机制”，只在后继元数据增加 followUpTitle；保留两条交付的原标题及原验收事实，以独立提交记录此次补写。

## 验收

1. 新建或修改 active Change 可用语义命令登记合法前序，非法目标、未归档目标、自指和循环拒绝且不写状态；旧记录缺失字段仍兼容。
2. 两个已归档 Change 在同一个带标题的外框内直接展示，可分别打开，直接深链接仍定位原记录。
3. 归档根存在进行中后继时，进行中可见后继；筛选只展示匹配成员，标题不包含合并状态或额外统计文案。
4. 同一前序的多个后继及多跳链可聚合；非法关系安全降级，取消成员保留真实状态，不合并任务进度或阶段。
5. 键盘可直接打开成员，窄屏无横向溢出；分组与相邻普通记录、分割线之间有间距，单独 Change 沿用现有布局。
6. 更新 SpecTrail 指引和当前 Specs，完成单元、命令、浏览器、类型与生产构建验证，独立评审通过后提供可验收交付。
