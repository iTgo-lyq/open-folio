# 并发同步后保留有效合入识别

## 目标与取舍

PR 已合入后，普通同步不能使系统把它重新判成未合入，也不能仅因无法定位历史差异而阻止安全清理来源。用户在评估原方案后要求简化，并以“继续吧”确认：取消 first-parent 位置要求，不做自定义历史路径遍历，归档完整性主要在合入前 CI 检查，保留防止丢代码和文件的检查。

原问题来自 [PR #22](https://github.com/iTgo-lyq/open-folio/pull/22)：合并提交仍在 develop 历史中，但离开第一父链后，格式校验阻止了清理。证据见 [Research](./research.md)。本次仍为 medium，涉及 CLI 合入确认、工作台交付判断及共用差异索引的职责调整。

## 行为

- CLI 用远端集成分支是否包含当前来源提交确认代码纳入，不要求匹配某个特定格式的 M，不重复证明归档首次引入或与来源逐字节一致。
- 来源清理独立检查代码纳入、归属、其他任务依赖、未保存或忽略文件、占用和新增提交，使用条件远端删除和非强制本地删除。实际交付/服务验证仍由 Agent 完成。来源已经不存在时清理幂等，不伪造可比较的来源提交。
- 工作台通过目标历史中的带标记合并提交定位差异，采用普通 Git 历史查询；缺失或歧义只让差异不可用。已合并 PR 的合并提交在远端目标历史中时，交付判断不依赖差异索引是否成功。
- 合入前 CI 继续检查归档与流程记录。合入后不再重复验证整个归档交付格式；这是用户接受的保证收窄，文件和提交的删除保护保留。
- 保留原提交的差异边界，不把后续同步提交当作 Change 的 diff。旧索引缓存刷新重算，不修改已推送历史、归档或用户数据。

修复通过验收并合入后更新开发服务，按新规则继续此前已授权的 skill-auto-update 来源清理。发布到 main 不在本次授权内。

## 验收

1. 重现 PR 合入后本地同步使 M 位于第二父路径的场景：CLI 确认当前来源已纳入，工作台定位原 M。
2. 差异标记缺失或歧义时，已经由 PR 及 Git 证明的合入事实仍成立，安全清理可以独立进行；普通提交中的文字标记不会成为合并差异。
3. 来源有未纳入的新提交、其他任务依赖、未保存内容或占用时不删除；远端 tip 竞争不误删，部分清理可重试。
4. 相同集成 tip 的旧索引重新生成；保留来源删除后的冷读取，以及固定的 M^1 到 M 差异。
5. 合入前 CI 保留归档校验；新逻辑不把缺失 Git 对象当成成功证据，分别报告代码纳入、差异可用性和清理结果。
