# 跨构建模块稳定识别服务错误

## 目标与范围

发布生产冒烟发现：未登录访问私有仓库接口及设备列表返回 `503 / INTERNAL_ERROR`，预期为 `401 / SESSION_REQUIRED`。后台刷新从 instrumentation 启动并创建全局会话、仓库实例；API 使用这些实例时，构建模块中的 `AppError` 构造器身份不同，`instanceof` 无法识别原本正确的业务错误。同一原因也影响共享 Provider 抛出的错误分类。

本次以 small 修复同一进程内 `AppError`、`ProviderError` 的跨模块身份：保留现有构造签名、继承、错误码、消息、HTTP 状态与重试提示，未知异常仍转成通用 `503`。修复集中在错误类型定义，预计不足 100 行实现，不改变 API、认证协议、后台刷新策略和持久数据。

需求澄清 Q1：发布前是否先修复生产状态码异常？推荐先修复并补生产回归；用户选择“先修复，再发布（推荐）”。

## 方案要点

在现有服务端全局单例机制下复用两个错误构造器，使 instrumentation、API 与共享实例使用相同的类身份。保持真正的类继承与 `instanceof` 检查，不将任意带有相似字段的对象当成可信业务错误。

## 验收

- 分别加载错误模块的独立副本后，两类错误均可跨副本识别，Provider 错误继续继承 AppError，状态码和重试提示不丢失。
- 普通 Error 和伪造字段对象仍被归为通用 `503 / INTERNAL_ERROR`。
- 生产构建保留后台启动流程，匿名私有仓库和设备接口返回 `401 / SESSION_REQUIRED`，匿名会话读取仍正常。
- 真实账号读取 Spec、Change、原型以及匿名分享通过，测试会话由 `withSmokeSession` 正常退出并确认匿名，账号原绑定保留。
- 修复通过独立工作分支 PR 合入 develop，再纳入原发布 PR；继续完成 main 发布与常驻服务验证。
