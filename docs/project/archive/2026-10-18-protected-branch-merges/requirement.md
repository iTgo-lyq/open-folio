# 保护分支保留合并历史与规划文档

## 目标与依据

延续 central-change-routing 的分支规则，修正单父快照发布造成文件相同但提交历史仍分叉的问题。用户明确：“正在讨论的东西合入 main 没关系，并没有形成真正的变更。develop 是持续交付的分支，但是是否上线看 main。”沿用本轮将 develop 合入 main 的授权。

## 范围与方案

- develop 承担集中讨论与持续交付，main 等保护分支作为正式上线基线；开发验证服务仍按项目约定运行。
- 用户要求发布时正常合并完整协作分支，保留提交历史与 docs/project/changes；规划文档进入 main 不表示 Change 已完成或对应能力已上线。不再过滤规划或创建单父交付快照。
- 保护分支独立修复按实际差异合回协作分支；使用保留协作 first-parent 历史的合并，确保已归档 Change 的 M 仍可定位。
- 更新主 skill、Setup 指引和当前 Spec；保留旧归档及已推送历史。用真实 merge 连接本仓库 develop/main，核实远端祖先关系和内容，再清理本次工作区。

## 验收

1. 规则一致允许规划文档随正常 merge 进入保护分支，区分讨论、持续交付和正式上线。
2. 临时仓库验证规划保留、连续发布、独立修复回流及协作 first-parent 历史保留。
3. 实际 main 包含最新 develop 的提交历史，两端交付内容一致；SpecTrail 自动同步成功，本次来源清理完成。

本次仅修改工作流文档和 Git 合并关系，不改变应用实现，无需重复构建开发服务。
