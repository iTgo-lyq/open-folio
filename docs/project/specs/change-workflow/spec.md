# Change 状态维护

SpecTrail 通过仓库内的语义 JavaScript 命令维护 docs/project 下的 Change 状态。change.json 是流程事实来源，并保存澄清问答；Markdown 保存需求、方案和证据，Git 保存版本与已推送记录，OpenFolio 工作台继续只读展示。

## 规模判断

规模依据核心契约变化、预期实现范围和独立交付数量。核心契约不变、预计不足 300 行有效实现代码且少于 3 个需联动修改的职责模块时，通常为 small。实质改变核心契约，或达到 300 行，或至少 3 个职责模块需联动新增、重写逻辑时，至少为 medium；达到 1000 行，或至少 5 项需要分阶段集成的独立交付任务时，默认 large。需要独立推进、验收和合入的子 Change 时采用 xlarge。

核心契约指多个模块或外部调用方共同依赖、变化后需协同适配或考虑兼容迁移的稳定接口、持久化数据结构和协议。普通局部配置项、权限或安全主题、一次用户澄清不自动提高规模。有效实现量按新增、实质改写后的手写生产代码估算，同段替换只计一次；排除空行、注释、配套测试、文档、生成代码和纯删除、格式化、搬移、批量替换等机械改动。模块按职责而非文件计数，同步调用和类型引用不单独计入；任务按独立交付而非工作步骤计数。

默认取满足的最高档位，数字用于事前估算，不逐行审计；临界情况结合职责边界和验证范围判断，偏离默认档位需给出具体依据。信息不足先调查或澄清，后续按同一标准调整。具体指引见 [SpecTrail 规模规则](../../../../.agents/skills/spec-trail/SKILL.md#创建与规模)。

## 类型与紧急程度

Change 使用可选 `types: string[]` 描述工作内容，支持自由命名和多选，不限定候选池。每项为无首尾空白的非空单行文字，区分大小写、不得完全重复，保留顺序；省略或空数组表示无标签。使用简短词并优先复用项目已有同义词，用户指定名称沿用；推荐词集中维护在 [SpecTrail 创建指引](../../../../.agents/skills/spec-trail/SKILL.md#初始化)。

可选 `urgency` 为 `urgent / high / normal / low`，对应紧急、高、普通、低；省略等同普通。根据用户安排维护，不从类型、规模或标题推断，不补写历史记录。两字段不改变规模、阶段、任务、确认、完成判定或执行依赖，Change 仍采用 schemaVersion 1。

`create` 可以填写两字段，活动 Change 通过 `labels` 独立更新传入项。类型参数为 JSON 字符串数组，命令 trim 后按首次出现顺序去重，拒绝空白、换行和非字符串；清空类型及设置普通分别删除对应字段，未传项保持原样。原始 JSON 中重复或非法值由共享校验拒绝；归档及取消记录仍只读。命令、hook 和工作台读取共用字段规则，展示与筛选见 [Change 追踪](../project-knowledge/change-tracking/spec.md#标签筛选与紧急排序)。

## 需求与技术澄清

需求按决策树分轮澄清，每轮只问前置已明确的 frontier 问题，逐题给出推荐与理由，等待回答后重算；事实由 Agent 调查，未决调查只阻塞相关分支。技术问询复用同一分轮机制，额度与需求分别计算、互不扣减，不设共用总额度。具体指导见 [分轮澄清](../../../../.agents/skills/spec-trail/SKILL.md#分轮澄清)。下表为需求澄清预算：

| 规模   | 最多轮数 | 每轮最多问题 | 总问题上限 |
| ------ | -------- | ------------ | ---------- |
| small  | 1        | 3            | 3          |
| medium | 2        | 3            | 6          |
| large  | 3        | 4            | 12         |
| xlarge | 4        | 4            | 16         |

创建前提问按所属类别计入，各类额度跨阶段、跨会话累计，返工不重置；上限不是配额，明确时零追问，不拆碎或藏题。用户要求收敛时按其要求停止；某类到限只停止该类扩展，集中说明关键缺口，追加该类轮次须用户明确要求。另一类可在自身额度内继续询问前置已明确的问题，缺口影响的推进仍暂停。子 Change 继承父级结论，只补齐自身未决细节；阶段确认沿用规模规则。

技术问询在每轮必要问题之前简短说明实现路径、主要复用或新增机制及其对使用和维护的影响，帮助用户理解本次实现重点；后续轮次只补充新信息。无须追问时也说明重点，解释不占题数、不增加审批。常规选型和局部实现由 Agent 按需求、项目约定与证据决定，只询问需要用户或责任人取舍的关键影响，并说明实际差异、推荐理由和主要代价。

数据模型不兼容升级必须由用户决定是否接受不兼容及旧数据如何处理。Agent 先查明影响并说明选项与代价；直接接受不兼容是有效方案，重建、一次性迁移或保留兼容按实际需要选择，不默认要求向后兼容或擅自加入防御性兼容机制。已有明确决定直接沿用；未明确的取舍阻塞相关方案定稿与实施，small 同样适用，兼容迁移只按已确认需要设计。

技术问询独立使用较小额度：small 最多一轮一题，在需求阶段完成但独立计数；medium 最多一轮两题；large / xlarge 最多两轮、每轮两题、共四题。需求额度用满不影响技术剩余额度；创建前或需求阶段已问的技术问题同样计入技术额度，不能通过切换阶段或改类重新获得额度。实现重点说明不变成理解测验，技术问答不代替方案确认；small 不新增技术阶段。具体指导见 [技术问询](../../../../.agents/skills/spec-trail/SKILL.md#技术问询)。

可选 clarifications 以稳定 Q 编号保存 round、question、recommendation，以及可选 answer、source、withdrawn。需求与技术共用连续 Q 编号和 round，同轮共享，跨阶段不重启。记录实际提过的问题与用户最终有效回答，用于回溯遗漏和澄清偏差，不记录思考过程；更正覆盖同题答案，含糊冲突先澄清。撤回保留原问答及原因，不退额度；返工不清空问答，记录不授予阶段确认。

每题按首次提问所要决定的内容归入需求或技术，只消耗一类额度；正文取舍处保留类别及 Q 引用，包括未答或撤回的问题。分别统计各类题数、每轮题数与不同 round 的数量，不以全局 round 最大值代替已用轮数，不另存计数器。同轮含两类问题时各计一轮及本类题数；medium 需求用完 round 1、2 后，首次技术问题可使用 round 3，仍只计技术第 1 轮。

需求结论同步 Requirement，技术结论同步 Technical（small 写入方案要点），较长调查证据放 Research。跨文档引用或回答引发需求返工不改变原问题归属；改变目标、范围、行为或验收时按需求返工，仅补齐技术证据继续完善方案。

问答通过 clarification-ask / clarification-answer / clarification-withdraw 维护，命令保存已发生事实，预算由 Agent 在发问前执行。共享校验与工作台读取使用同一问答契约，旧记录可以省略该字段。

## 暂缓需求与实际移交

用户明确只记录需求、短期不启动时，保存已知目标、范围、未决问题，并通过 `wait --kind pause` 记录原因或恢复条件；可保留空任务，不自动创建 Plan、工作分支、worktree、Draft PR 或进入实施。暂缓期间可继续澄清和补充材料，更新不自动解除 pause；用户明确恢复后才 resume，并继续遵循确认与移交条件。暂缓与真实任务受阻分别表达。

branch 中的目标名称不证明已完成移交。CLI、工作区命令和工作台定向核对命名分支中的所属 Change：目录 id、记录可读性及 branch 归属必须匹配，继承的集中副本和无关同名分支不构成移交。没有实际来源且集中记录为 active、requirement/technical、任务全部未开始且没有关闭记录时，可继续从集成分支澄清，保留原始 branch 名。实际目标优先，需求阶段也在实际所属工作区继续；取消、有效归档及父子交付沿用原规则。

locate 报告集中规划来源和实际工作区，不自动创建执行目录；prepare 不替代 handoff。显式 handoff 沿用预填名称，核实基线并按既有发布顺序完成移交，未发生 branch 登记变化时不制造空提交。父子都仅预填时允许集中澄清，但创建子项工作区仍要求父项实际移交。失败保留文件、暂存区及已创建成果。

联网入口区分目标尚未建立、已知来源丢失和查询失败。已观察所属来源被删除时，既有 Git 跟踪元数据仅用作历史归属证据，不作为当前发布材料；连续刷新仍保留缺失诊断。网络、认证、权限、记录损坏或身份冲突不静默回退成可写集中规划。只读查询标明新鲜度，不全量扫描分支或增加持久化移交状态；所有可核实证据消失时，不仅凭分支名推断历史。

## 技术方案复杂度

技术方案采用 `anti-bloat-review` 的中文主体，完整规则见 [对抗式审核：用第一性原理压缩冗余](../../../../.agents/skills/spec-trail/SKILL.md#对抗式审核用第一性原理压缩冗余)。保留原文判断与取舍方式，建议随技术方案按既有阶段规则审阅。

## 文档配图

medium 及以上 Change 涉及数据结构、时序流程等明显变化时，建议按变更模块分别评估配图，在相关需求或技术方案中说明。差异较大的模块分别说明，不以“已有配图”代替判断；图型与数量按需，简单内容不强制配图，small 按需。图片存入文档旁的 assets 目录，以相对链接引用。

## 发布版本与更新检查

SpecTrail 直接从本公开仓库 `.agents/skills/spec-trail/` 分发，保留 MIT LICENSE。skill 根目录的 `version.json` 使用 `major.minor.patch`，首次版本为 `0.1.0`；修改技能时在同一提交中递增补丁号，内容未变或重复发布不增加版本。源码和安装包使用同一版本文件，不再同步到独立仓库。

`change.mjs` 是唯一更新检查入口，在状态操作成功且释放锁后检查，并保持原 JSON 字段、流程记录与退出码。show 同样检查；help、dry-run、无效参数和原操作失败不检查。目标项目 workflow v3 的可选布尔字段 `checkForUpdates` 省略或 true 为开启，false 为关闭；关闭后不读取检查缓存、不联网或展示缓存提醒。项目从当前目录或 --repo 定位，skill 与 OpenFolio 的严格配置校验共同接受该字段，旧配置无需迁移。

本地版本从实际执行的 skill 安装读取，最新版仅从本公开仓库 main 的 `.agents/skills/spec-trail/version.json` 获取，无需 Token，不发送项目地址、路径或正文。请求与响应体共用 3 秒超时，响应最多 16 KiB；检查结果在 Git common-dir 的 `spec-trail/update-check.json` 缓存 24 小时。worktree 共享结果但分别读取项目开关，每次比较实际安装版本，缓存失败不影响状态操作。

确认有新版时在 JSON 外层追加 `skillUpdate`，包含 available 状态、当前版本、最新版本与说明；已是最新时省略字段。缺少安装版本或检查失败时提示 unknown，不将未知当成新版或已是最新，不使用过期结论。旧安装需先手动更新一次以取得检查逻辑与版本文件，源目录开发副本无版本时不联网猜测。该能力只提醒，不下载、替换或安装 skill。

## 命令与责任

主 skill 自带 scripts/change.mjs，使用 Node.js 内置模块，无第三方依赖。命令覆盖创建、修改展示标题与标签、阶段确认、任务登记/执行/阻塞/完成、等待与恢复、返工、关闭四步、取消及原型关联。修改标题和标签保留 Change id 与已有流程记录。具体调用参见仓库 [.agents 状态命令说明](../../../../.agents/skills/spec-trail/references/state-commands.md)。

Agent 根据实际用户授权、验证与评审结果传入摘要和来源，脚本负责既有 JSON 契约、阶段前置、时间、失效字段清理与本地写入。脚本不判断正文质量、不替用户确认、不运行测试，不自动提交/推送或合入分支。命令成功不等于中心仓库状态已持久化。

confirmations 下所有 summary 均为阶段内容简述：requirement 写目标与行为，technical 写机制与取舍，plan 写交付与顺序，merge 写合码策略与关键决策。优先 20–40 字符、最多 60 字符、单句，省略确认措辞及常规验证清单；确认依据写 source。confirm 按 Unicode 码点拒绝超长或换行的新摘要，内容质量由 Agent 核对，历史读取不追溯长度限制。

创建 Change 前先定向 fetch 集成分支，按最新远端记录检查关联 Change，再决定复用、延续或独立新建。

新 Change 在配置的集成分支整理需求，推荐名称 develop，主工作区不随任务切换。需求文档提交并按规模确认后，从最新交付目标移交到独立工作分支和 worktree（子项为父分支，其余为集成分支），small 沿用现有确认规则。原型、技术方案、Plan 和实现均在所属工作区推进；绘制原型前协调与其他进行中 Change 的重叠范围。新 worktree 默认位于主工作区同级的 `<项目名>-worktrees/<工作区名>`，Change 默认用 id；已有登记优先复用，显式路径按用户约定。集成分支保留需求目录，仅用 branch 登记目标，不镜像执行状态。普通 Change 不在集成分支执行，xlarge 父项在工作分支聚合与关闭；继承副本只读。

工作分支只推进所属 Change，同一分支只有一个普通执行/关闭中的 Change；取消冻结所属工作分支，集成分支上的规划取消只冻结该记录。未集成归档可经 rework 恢复原 Change 返修，清除失效关闭记录并保留已完成任务；已集成归档只读，branch 保留历史归属。用户明确要求历史勘误时最小修正并保留普通提交，不改写已推送历史。

历史发布补记是归档只读的限定例外：核实确已合入发布分支后，仅在集成分支有效归档的 change.json 增删可选 `deliveryOverride: "releaseMerged"`，以普通提交留痕，不改写其他关闭记录。字段只覆盖交付展示，不替代 Git/PR 证据或 CI；缺省恢复自动判定。版本升级步骤见[升级说明](../../../../.agents/skills/spec-trail/references/upgrade.md)。

workspace.mjs 的 handoff 检查已提交的 Requirement，非 small 还须需求确认；不等待 Technical、Plan、任务或依赖交付，显式暂缓仍阻止移交。执行与关闭继续检查原有前置条件，保留旧 xlarge 父项的关闭移交校验。普通 Change 先推送共享的 branch 登记提交，再快进集成分支；子项从 active 父分支建立，将独立的集中登记提交合入子分支后先推送子分支，再仅向集成分支推送登记提交，避免泄漏父项实现。中断重试核对准备时父基线，父 tip 已变化时保留现场并拒绝静默沿用旧基线。失败重试检查完整所属目录和真实引用，保留无关脏文件与暂存现场，不制造指针文件、规划清理或执行状态镜像提交。locate 只读报告来源、新鲜度和本地 worktree 状态；prepare 定向刷新并复用或准备工作区，不重置、rebase 或 prune。创建 worktree 不证明会话已绑定，客户端无法自动绑定时使用人工打开与续接提示，再核对 cwd、命名分支及仓库身份。

## 提交整理

同一 Change、同一阶段的小幅讨论补充或措辞修订，可 amend 当前分支最新的普通讨论提交，原提交与本次修改都只属于该 Change。该例外适用于集成分支和独立工作分支，发布分支、阶段确认、任务完成、取消、归档、分支移交、合并及固定原型版本的来源提交保留独立记录。

已推送时先保留原提交和本次增量，确认远端未变，再用显式绑定原提交 SHA 的 `--force-with-lease` 尝试一次；后台 fetch 不改变预期 SHA。预查或 lease 检查发现远端变化，取消本轮改写，保留原提交与他人提交，仅将本次增量作为普通提交，同步后正常推送，不换用新 SHA 重试强推。响应未知时先核实远端实际发布结果。具体操作和本地恢复条件维护在[主 skill](../../../../.agents/skills/spec-trail/SKILL.md#同阶段讨论的小补充)。

最终归档前检查本 Change 短期工作分支和尚未合回的任务分支，合理压缩试错、纯格式及反复修测试等无独立交付价值的提交，保留有意义的任务交付和流程检查点，不强求单提交。不改写集成/发布分支、已合入历史、移交登记、取消/归档记录、合并边界或固定原型来源提交。已推送整理须先核实无人依赖待改写提交，保留原始提交及远端 tip，使用单次固定预期 SHA 的 lease，远端变化即停止改写；无法安全整理时保留历史并说明原因。

整理前后核对最终文件树、Change 正文和 JSON、任务提交定位线索及 PR 标记；追踪缺失或失效时依据原始证据及时补齐，保留真实确认、验收、验证与时间，无法恢复事实时暂停归档。内容不变复用有效验证，内容变化重新验证，整理推送后复查 CI。该分支内整理不替代交付时的普通 merge，操作规则见[归档前提交整理](../../../../.agents/skills/spec-trail/SKILL.md#归档前提交整理)。

## 延续交付与分组命名

同一目标在未集成时继续原 Change 返工；已集成交付的补充或修正以新 Change 的可选 `followUpOf` 指向同仓库已推送、有效归档的直接前序。Requirement 说明具体延续内容，仅属于同一模块或标题相似不构成关联；整体目标改变时独立建 Change。延续关系可多跳或分叉，与规模、执行依赖及父子关系独立，各次任务、阶段、验收和归档事实分别保留。

`create --follow-up-of` 与 active Change 的 `follow-up --target` 登记前序，定向核对已推送的关闭记录及其历史，拒绝缺失、无效归档、自指或循环；常规命令不修改归档前序。`follow-up --target none` 解除关系，不影响执行依赖和已有确认。

首次建立延续组时单独生成概括共同用户目标的简洁单行标题，用户指定名称时沿用；各 Change 的 `title` 描述自身交付。通过上述命令的 `--group-title` 将可选 `followUpTitle` 保存在后继，后续关联先读取完整组名，通常省略新声明并继承，分叉同样沿用。移除或更换前序时清除自身旧声明；无关联不可命名，显式名称不得与前序已有声明冲突。旧组没有名称时在当前后继补充，不为每次补充重新命名或改写原交付标题。

历史关联与命名只在用户明确授权的迁移中限定记录和字段，以独立普通提交保留证据，原正文、任务、验收及时间保持不变。工作台分组、筛选和异常降级见 [Change 追踪](../project-knowledge/change-tracking/spec.md#延续交付分组)。

## 接入与提交校验

首次或更新接入先核实默认分支、权限和保护规则，在 workflow.json v3 必填合法且不同的 integrationBranch（推荐 develop）和 releaseBranch（推荐 main）。集成分支承担集中规划和预发布集成，接收 Change PR；发布分支接收用户要求的正式版本 PR。规划和分支登记继续直接提交集成分支。准备集成分支并让干净主工作区使用实际配置，执行使用独立工作区。SpecTrail 的 [Setup 子 skill](../../../../.agents/skills/spec-trail/setup/SKILL.md) 提供 Node.js 20+、Git、配置及校验资源的只读准备检查，并输出调用命令和 Git 入口信息。检查不创建或复制文件、不修改 core.hooksPath，也不执行业务 hook；准备就绪与 hook 接入分别判断，hook 与远端权限状态均为未验证。已知本地/跟踪引用不证明远端仍存在，需精确查询。

首次接入明确提醒用户不要开启自动 squash；Change 和正式发布的 PR/MR 均使用普通 merge。Agent 代创建、更新、合并 PR/MR 或配置自动合并时，核对仓库/目标分支规则、本次选项及自动合并/合并队列的最终方式，显式选择普通 merge，取消本次 squash，不依赖默认值。平台提供 squash 选项及普通 merge 的自动合并不构成受阻；只有 squash/rebase 可用、无法取消本次 squash 或无法核实实际方式时报告限制，不擅自改全局规则或回退直推。本地预检及归档 CI 不代替此项平台核实，统一操作见[合并方式检查](../../../../.agents/skills/spec-trail/references/integration.md#合并方式检查)。

入口检查要求先配置 workflow v3，仅接受当前协议，只读取基线、已登记 worktree 与显式工作分支，输出固定提交、覆盖依据和冲突，不联网、全量枚举分支或改写现场。归属冲突、目标缺失、未归档 completed、未集成交付的归档和基线上的普通执行项均先处理。后台接入直接指定集成分支，配置与校验器只需在该集成分支就绪，不以默认或发布分支发布为前置。CLI、hook、Setup 与后台统一拒绝旧 workflow 契约；Change 本身仍采用 schemaVersion 1。发布分支只定向读取以核实发布交付，不作为文档发现入口，不回退全量扫描。

用户或业务项目的 Agent 根据现有提交管理方式接入校验器，沿调用链修改项目维护的入口并保留既有检查，管理器生成的转发文件不作为接入维护位置。SpecTrail 不规定 hook 目录或管理工具。接入应传播非零退出码，并通过实际提交的成功路径和失败传播验证；文件存在、字符串匹配或准备检查通过均不代表已接通。

校验器和接入文件随仓库共享；本机 Git 配置不随 clone 传递，新克隆沿业务项目的启用方式接入。同仓库 worktree 的入口调用当前工作区校验器。提交校验检查本次实际暂存区，保留 GIT_INDEX_FILE 以兼容部分提交；实际确认、交付、依赖与合码条件由流程命令和 Agent 核对。

集成分支的普通提交涉及 `docs/project/changes/<id>/` 任意文件时，若 HEAD 中该 Change 为 active、登记到独立工作分支且本地命名分支或已有跟踪记录含该 Change 的实际归属证据，则拒绝整个提交，提示所属分支和本地已登记 worktree；本地没有工作区时提示 locate 命令。仅预填名称或目标只有继承副本且集中记录仍符合规划条件时允许提交；损坏、重复或冲突证据保留诊断。hook 不联网，跟踪记录不代表实时远端状态。新增、修改、删除及重命名来源均在检查范围内，以提交前的分支登记为准，实际归属已核实时不依赖集中副本的 stage，也不因同次改写或删除 change.json 放行。未移交规划、首次移交登记、工作/任务分支和正常合并继续按既有规则提交；不涉及 Change 文档的实现提交不作归属推断。检查只读取本地 Git 数据，失败保留文件与暂存区；此机制在提交时拦截，不提供文件写入隔离。

## 状态与证据边界

完成任务的定义与记录保留，返工追加任务并清除失效的关闭步骤及阶段确认。small 默认自验收后归档；用户要求人工验收或人工验收提出问题后，该 Change 后续均须用户确认，并在 Requirement 保留此要求。其余规模人工验收，不能把测试通过或预先笼统指令替代实际授权。等待解除与确认记录分别维护。

前置 Change 从集成入口定向解析，必须有一致的已推送关闭记录且所需交付在当前分支可用；通常在上游合入配置的集成分支后同步；同一父项内的子项依赖可在真实 PR 已合入父分支、交付已同步至当前分支后满足，无需等待父项整体集成或正式发布。父项关闭要求全部子项完成或取消，已完成子项在父分支的 PR 交付核实通过；人工可用性说明不替代 PR 合入事实。状态写入定向核对依赖远端，不消费已删除远端的残留 tracking ref；只读查询明确标记缓存新鲜度。祖先关系是集成证据之一；squash 后不能推定缺少交付，也不能自动推定已集成。Agent 核对具体交付并记录依据后，可传 availability-note；命令输出源/目标提交与说明，保留证据类型区别。

新记录时间统一为 UTC 三位毫秒 ISO 字符串。关闭步骤按整体验证、验收、Specs、归档严格非递减；时钟早于前一步时拒绝写入，不加读取容差，不伪造未来时间。读取接受有效且含时区的 ISO 8601 时间。

## 任务执行安排

普通 Change 默认按任务编号数值递增串行，例如 T1、T2、T10，不取 JSON 属性顺序或正文排列。small 无需创建 Plan；medium/large 仍需 Plan 正文，但执行顺序表可选。xlarge 按子 Change 组织。

需要并行或特殊安排时，Plan 中唯一的“执行顺序”章节用一份“任务 / 前置任务”表覆盖默认安排，完整且不重复地列出 JSON 任务。前置为“无”或存在的任务编号，不能重复、自依赖或成环。仅有标题或文字说明仍使用默认；显式表存在但无效时拒绝推进，不退回默认。代码、引用、列表和 HTML 块中的示例不构成实际声明。

流程命令与工作台共用任务顺序规则。任务开始和完成要求整条前置链均已完成；进入执行及验证、验收、Specs、归档步骤重新检查安排。错误安排和未完成前置的失败操作不写入状态；阻塞、重试和返工仍可用于修复。提交 hook 保持结构校验，不解析任务安排。

## 写入与失败恢复

字段校验由主 skill 的 state-schema.mjs 共享给命令与提交 hook，hook 继续只验证实际 index，支持部分提交及 GIT_INDEX_FILE。原型引用区分 hosted 与 git，校验项目开关、源码提交、当前清单、引用及适用的暂存 HTML；继承的其他 Change 仍检查本次修改 JSON 的结构，但不要求其远端原型产物存在于本地，hook 不联网；宿主上传和浏览器验证不由 hook 执行，详细协议见[原型浏览与预览](../project-knowledge/prototype-preview/spec.md)。

命令使用仓库级锁、原文复查和同目录临时文件 rename；错误参数、错分支、符号链接、越级关闭、重复覆盖与归档目标冲突均拒绝。提交失败的 task-retry 仅恢复 HEAD 尚未完成的任务；同时修正该任务已暂存的 done，保留其余部分暂存差异。已提交完成任务不回退；推送失败保留提交并重试推送。

archive 移动完整文档目录并标记 completed，不重建原型工程。Git 原型固定到本 Change 的 previews/<id>/index.html；仍引用共享目录时先复制 HTML，目标内容不同则停止，保留 sourceCommit。所有规模均在独立分支归档，不创建保留标签。目录移动与状态/index 更新不提供跨文件断电事务保证，异常终止后根据 Git diff 与实际文件恢复；普通写入失败尽量回退并报告。

## 材料分享链接

`docs/project/workflow.json` 的可选 `openfolioUrl` 保存服务根地址，沿用原型配置中的同一字段。服务入口须允许匿名访问且存在可读取目标仓库的已接入来源；不另设分享账号、密码或 Token。

材料提交推送后，Agent 直接提供对应 Change 材料链接，不验证工作台接口、远端正文或原型内容，不等待同步。可用零依赖 `share.mjs --change <id> --document <相对路径>` 或 `--preview <入口id>` 生成地址；省略材料参数分享概览。脚本只读取本地 origin 和 workflow，返回含仓库、集成分支、Change 及材料定位参数的 `url`，不附带服务分支或提交信息。

未配置服务地址时提供仓库材料链接。分享页跟随已推送内容，用户打开网页后由页面刷新获取；生成链接不表示工作台已同步最新材料。完整用法见 [Skill 分享链接](../../../../.agents/skills/spec-trail/references/sharing.md)。

## 归档后的去向

Plan 在工作分支写完并推送后创建或复用 Draft PR，不等待计划确认；small 在移交后推送真实执行状态、实施前创建。后续推送同一源分支自动更新 diff。归档前在独立 Change 工作区同步最新实际目标提交并验证；归档推送后通过 preflight，更新同一 PR 的交付说明与验证并转为可审阅，按实际授权普通 merge 合入交付目标（子项为父分支，其余为集成分支），保留双亲提交和历史。PR 正文末尾独立段落保留唯一 `SpecTrail-Change: <id>`，合并消息允许平台默认生成，并核对预期源 SHA；失败不自动回退直推。verify 通过 PR 记录核实正式合入，并独立核实当前本地及远端来源提交是否均已纳入集成历史；主工作区只在干净时安全快进。命令与清理见 [PR 集成流程](../../../../.agents/skills/spec-trail/references/integration.md)。

工作台、CLI 与发布检查统一以 PR 记录识别正式集成。同仓库身份、登记来源分支、集成目标及 PR 正文唯一标记精确关联后，唯一已合并 PR 提供 M，Git 核实 M 属于固定远端交付目标历史；不要求 M 位于 first-parent 链，也不依赖来源分支仍存在。提交标题、正文及分支命名不提供关联证据，多个已合并候选明确报歧义，PR 读取失败或分页未完成不能退回消息标记或旧成功结果。

差异读取独立检查 M 的双亲结构及归档目录，以 M 与第一父 B 确定差异；差异不可用不撤销已核实的 PR 合入。合入前 CI 检查目标归档、来源归属及 Git 原型快照位置，合入后不重复证明归档首次引入或与来源逐字节一致。不在 change.json 保存 M，也不回写已归档状态或正文。子项各自归档并通过 PR 合入父分支，随后修正走后继 Change。xlarge 父项完成整体验证、验收和关闭后，PR 携父项及所属已完成子项归档整体交付到项目集成分支；CI 拒绝无关新归档、未结束子项或错误目标，并覆盖动态父分支。父项 M 表达整体交付，各子项保留自己的 M。旧流程中已直接集成的子项继续按真实证据读取，不改写历史。本地 CLI 使用已认证的 gh 完整分页读取 PR，发布 CI 使用只读 PR 权限。

源或目标推进后重查差异、预检和受影响验证；合入响应未知、排队或受理时先查询平台与远端，已证明的合入不重复执行。verify 的 sourceIncluded=true 表示当前来源提交已纳入；来源引用均不存在时 sourceAbsent=true、sourceIncluded=null，说明没有来源可继续比较，不代替平台 PR 事实。差异定位失败只影响差异可用性，不否定已核实的 PR 合入；远端来源无法核实或不满足删除条件时保留现场。其他 Change 的继承规划可保留，取消入口不自动合入或删除。

核实当前来源提交已纳入远端目标及交付后（子项验证父分支，整体集成后按项目要求验证服务），默认按远端源分支、worktree、本地源分支顺序清理。清理独立于差异索引，使用 Agent 已完成交付/服务验证的实际 Git 提交；该提交属于远端实际目标历史、当前工作区包含它，待删来源均已纳入它，无须匹配某个 M。删除前核对归属、有效来源依赖、实际会话/服务占用、Git 操作及未保存/未跟踪/忽略文件；assume-unchanged 或 skip-worktree 标记须先解除并检查。引用不可读不能当作引用不存在。保护主工作区、集成及发布分支，保留新提交、独有配置、用户资料和不可判定的对象。远端按预期 tip 条件删除，本地使用非强制删除；逐对象报告 cleaned/retained/failed，部分失败或来源已删除时可幂等重试，不重复合入。

旧历史不回填关联或重写提交。新读取端生效并停止旧标签写入后，按重新核对的精确清单退出 spec-trail/archive-v2/\* 标签与其专用可重建缓存引用；外部产物、公开版本、当前清单及用户持久数据保留。

用户明确要求正式版本时，固定发布目标基线与集成候选，核对实际 diff、Change、关联 PR 和验证记录，在发布 PR 中整理版本、用户可感知的功能与修复、升级影响、包含清单及验证结果。默认源为集成分支，需要冻结候选时使用短期发布准备分支；不以提交标题替代内容整理，不额外维护 CHANGELOG.md、tag 或 GitHub Release。正文末尾独立段落使用 `SpecTrail-Version` 和逐项 `SpecTrail-Includes`。候选变化时更新范围、说明和验证；准备 PR 不等于授权合入。

发布 PR 使用普通 merge 保留历史和规划文档，确认实际合并提交属于发布分支后报告合入；规划存在或 PR 合入不等于服务上线。发布分支独立修复回流时用 --no-ff 保留集成 first-parent 历史。Change 完成集成即可供下游使用，不等待正式发布，也不因发版改写归档。

未归档 Change 不得合入；Agent 合入前通过预检与已接入的归档 CI。Setup 提供 GitHub workflow 模板并推荐配置必需检查，保留规划直推的授权例外。CI 在 PR 源提交或正文更新后重跑：Change PR 校验唯一有效归档、归属和集中登记；发布 PR 仅校验清单内的归档、有效集成 M 与候选祖先关系，不要求其他规划归档。平台必需检查与实际 CI 运行分别核实，有绕过权限的身份仍遵守 Agent 规则。

正式上线以发布分支为基线，构建与部署沿用项目约定，SpecTrail 不要求另建服务 checkout。本仓库长期服务用于开发验证，从主工作区的 develop 构建并使用其 `.next`，保留现有运行数据。
