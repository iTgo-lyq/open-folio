# Change 追踪

Change 追踪在[项目知识工作台](../spec.md)中展示变化目标、实际流程记录、任务和依赖。工作台提供阅读依据，流程推进由 SpecTrail 执行。

## 状态与主来源

流程状态唯一取自 `docs/project/changes/<id>/change.json` 或 `docs/project/archive/YYYY-MM-DD-<id>/change.json`，按 SpecTrail `schemaVersion: 1` 严格校验。Markdown 保存正文和证据，Git 保存来源；二者都不替代 JSON 状态。

同一仓库的 Change 按 id 聚合。只有唯一候选的所在分支与其声明的 `branch` 一致时，才采用该主记录；其他分支副本供查看，不重复计数或拼接状态。主记录非法时保留错误，不以较正常的副本替换；多个主记录、主分支缺失、同一主分支 live／archive 重复等情况显示来源异常与原始候选。

整体结果 `active / completed / cancelled`、阶段、等待事项、任务阻塞和来源质量分别展示。默认展示进行中 Change，另有已取消、已归档、来源异常和全部入口。取消保留原阶段、材料和取消原因；有效完成要求关闭四步、归档目录、任务／Plan 和关系满足规则，且原 live 目录已移除。异常完成声明不计为有效完成。

## 浏览、任务与材料

- Change 提供列表、阶段看板和依赖视图，可按名称／id、规模、阶段、等待和关联能力筛选。看板只用于浏览。
- 任务粒度提供列表和四种状态的看板，按任务编号／标题及状态筛选。任务状态取 JSON 的 `todo / doing / done / blocked`，保留验证、阻塞原因和任务分支；提交标题只作查找线索。
- 详情包含概览、任务或子项、文档、依据，以及主分支来源、确认、返工和验收记录。关闭详情保留列表筛选、位置和焦点。
- small 任务直接读取 JSON；medium／large 结合 Plan 的交付定义和执行顺序；xlarge 展示子 Change 和子项结束数量，不创建父级实现任务或把子任务数量作为父项进度。
- 实际存在的 Markdown 材料可以阅读；缺失、不可读、当前规模不要求和尚未进入要求阶段的材料分别提示，不生成正文补空。全文搜索命中具体材料时打开该材料并保留所属 Change 上下文。

## 阶段与完成标记

原始阶段为 `requirement / technical / plan / execution / close`。small 使用需求、执行、验收路线；medium／xlarge 将技术与计划合并展示；large 分别展示技术与计划。省略的阶段不显示为遗漏审批。

需求、技术和计划的勾选依据实际确认记录，合并阶段仍要求对应的两个确认。阶段位置、已有文档或历史提交不自动证明确认发生。确认的时间、摘要和来源、返工的原因和处理方式均可查阅。

当前处于 execution／close 时，普通 Change 的非空任务集合全部为 done 才显示执行完成勾选；xlarge 的非空子项集合对应流程关系全部满足时显示执行完成。空集合、未完成任务、未知子项或退回规划不自动打勾。执行完成不代替人工验收或整个 Change 完成。

close 的通用名称为“验收”；active 且整体验证通过、没有人工验收记录时显示“验收中”。“验收与归档”按整体验证、人工验收、Specs 同步、归档提交展示各步真实结果、时间与摘要。缺项显示未记录，验证失败保留失败事实，Specs 无需变更显示原因；部分记录不等于完成。

## 关系与依赖证据

Change 前置关系取 `dependsOn`，父子关系取 `parent / children`。缺失、重复、自指、循环、父子不对称、嵌套父项或子依赖父均有诊断；children 顺序不代表串行依赖。关系异常影响有效完成判断，并沿依赖传播，不能成为下游已满足的前提。

流程前提与交付可用性分开显示。有效归档的前置 Change 满足流程前提；已取消前置不满足。父项的子 Change 可由有效完成或有效取消记录满足结束条件。来源异常或目标缺失保持不可判定。

Git 祖先关系仅证明含有归档记录的固定来源提交在当前分支历史中；无法证明、历史不足或 squash 情况显示可用性待核实。不根据提交标题猜测对应关系，不把祖先存在当作代码未被撤销的证明。

任务前置只解析 Plan 中唯一“执行顺序”章节下含“任务／前置任务”两列的 GFM 表格。每个 JSON 任务需要唯一一行，前置为“无”或合法任务编号，不能自依赖或成环。表格缺失、歧义、覆盖不全或无法解析时保留原文和位置依据并提示不可判定，不按编号或正文顺序推断依赖。
